# External-MCP credential injection

External-MCP credential injection authenticates approved external HTTP Model Context Protocol (MCP) calls at a Consul terminating gateway. Provider credentials remain at the egress point that needs them instead of being distributed to agent applications.

This page describes the Consul Agentic Mesh Platform (CAMP) component architecture and its boundaries. Refer to the [CAMP overview](/consul/docs/agentic-mesh) for the scope of these architectural descriptions.

## Introduction

External MCP services can require a bearer token or API-key header even when callers already have Consul workload identities. These credentials solve a different problem from mesh authorization: they authenticate the gateway to the external provider.

The architecture separates two inputs:

| Input | Owner | Information supplied |
| --- | --- | --- |
| Route and authorization | Consul configuration plane | Approved destination, mesh policy, external TLS settings, and a non-secret credential-binding identifier. |
| Credential delivery | Vault and the gateway-local credential runtime | Credential material for the fixed binding, with validity and rotation information. |

Consul does not fetch the provider credential from Vault for inclusion in proxy configuration. Vault does not publish provider secrets into Consul. A gateway-local authentication processor connects the trusted route binding to the delivered credential.

## Authorized request path

The MCP Gateway maps an approved tool request to a configured logical service. Mesh connectivity carries the call to the terminating gateway, where workload authentication and applicable intentions precede credential injection.

The matched route supplies trusted credential-binding metadata to the local authentication processor. The processor uses that binding to obtain a usable credential and return the allowed authentication-header mutation. It must not change the already-authorized destination or route.

The terminating gateway establishes an external TLS connection with certificate verification and the configured server name. It forwards the authenticated HTTP request only when both the route and its credential are usable.

## Trusted bindings

Operators bind a logical destination to an approved external endpoint, authentication-header policy, and credential source. A caller cannot select a Vault path, provider account, credential-binding identifier, header name, or external TLS server name.

Do not accept caller-supplied binding headers as trusted metadata. Credential injection must not become a mechanism for sending an approved provider credential to a caller-selected host.

Only the processes that require credential material should be able to read it. Applications and MCP gateways must not receive provider secrets, and the authentication processor must not receive the Vault Agent's authentication token merely because it can read rendered credentials.

## Readiness and rotation

Processor readiness and destination credential readiness are distinct. A running processor does not establish that every binding has a usable credential. A missing, invalid, or expired credential must fail the affected call closed rather than forward it without authentication.

The credential runtime validates updates and replaces the active credential without exposing partially written values. Stale generations must not overwrite newer accepted credentials. Rotation and expiry policy determine how long a last valid credential can remain usable when Vault or credential delivery is unavailable.

An outage does not authorize indefinite use of cached credentials. Observe binding health and validity deadlines independently of the overall gateway process health. A problem with one binding need not prevent unrelated, valid bindings from serving requests.

## Security and evidence

- Keep provider credentials and Vault tokens out of agent configuration, Consul configuration, proxy configuration snapshots, logs, traces, and error messages.
- Limit credential mutations to the configured authentication headers without changing the route or disabling external TLS verification.
- Record bounded binding status, policy outcomes, and rotation failures without recording secret values.
- Preserve caller authorization checks even when a provider credential is available.

## Dependencies and boundaries

The external-MCP design covers HTTP services using supported bearer-token or API-key-header authentication backed by Vault. It depends on an approved terminating-gateway route, protected credential delivery, a local authentication processor, and verified external TLS.

This component owns credential delivery, injection, readiness, and rotation for that scope. It does not define managed-model authentication, OAuth delegation, request signing, client-certificate authentication, arbitrary secret managers, or non-HTTP MCP transports.
