# Intelligent circuit breaker

The intelligent circuit breaker is a proposed Consul Agentic Mesh Platform (CAMP) component for agent-specific containment. It analyzes observed behavior and publishes protection state that enforcement processors can apply to subsequent requests.

This page describes a design proposal, not an available circuit-breaker service or deployment procedure. It does not establish support in a Consul release.

## Introduction

Ordinary mesh resilience addresses failures such as unavailable or overloaded upstreams. Agent workflows can also repeat tool calls, cycle between agents, or continue work after an application-level failure. Those patterns can occur even when individual network requests succeed.

The proposed circuit breaker complements ordinary resilience with agent-scoped behavior policy. Its goal is to contain an affected agent without automatically blocking every agent that uses the same backend.

## Analysis and enforcement

The design separates asynchronous analysis from request-time enforcement:

| Component | Responsibility |
| --- | --- |
| Application instrumentation | Emit correlated workflow, agent, and tool-call spans. |
| Trace storage | Make the relevant workflow evidence available to analysis workers. |
| Analysis workers | Evaluate available trace evidence against behavior policy. |
| Protection-state storage | Publish agent-scoped state and its validity information. |
| Enforcement processor | Consult applicable state before allowing a subsequent request. |

The reference proposal uses queued analysis work, a trace backend, and shared state. Workers can wait for trace indexing without blocking the original application request. These dependencies require deployment and operational qualification. They are not supplied by enabling ordinary mesh circuit breaking.

## Protection state and recovery

The proposal describes open and closed protection states. Closed state permits requests that pass the other required controls. Open state contains requests for the affected agent according to enforcement policy.

State changes require a defined agent identity, policy context, reason, and validity period. Recovery depends on the component's expiry or reset rules. Resetting protection state is not evidence that an earlier operation was safe or that its side effects were reversed.

Use the component's recovery policy to distinguish automatic expiry from an operator decision. Do not assume generic circuit-breaker states or retry behavior that the agent-specific design does not define.

## Detection limits

Detection follows execution, trace export, trace indexing, analysis, and state publication. This delay allows additional activity before a protection decision reaches enforcement.

Consequently, the proposed component cannot:

- Prevent every unsafe first action.
- Recall a request or reverse a tool action that already completed.
- Establish that a completed operation was safe because no circuit opened.
- Infer missing workflow semantics from network success alone.
- Detect patterns that missing or sampled-out instrumentation does not expose.

Keep synchronous authorization, usage limits, approval requirements, and application validation in place. Behavioral containment supplements those controls rather than replacing them.

## Degraded operation

Incomplete traces, analysis backlog, unavailable state storage, and stale protection state require explicit degraded-operation rules. Missing evidence must not be interpreted as proof of healthy behavior.

Before adopting the proposed architecture, define the effect of each dependency failure on admission, state expiry, recovery, and operator alerts. The proposal does not justify a universal fail-open or fail-closed policy for every workload.

Monitor analysis lag and state freshness as well as circuit transitions. A functioning request path does not establish that asynchronous protection is functioning.

## Dependencies and boundaries

The circuit-breaker component owns analysis dependencies, agent-scoped state transitions, recovery, and degraded behavior. It requires adequate application instrumentation, correlated traces, a behavior policy, and enforcement that consumes its state.

It does not own application planning, tool business logic, durable workflow recovery, or proof of model quality. Its asynchronous evidence must remain subject to the platform's telemetry privacy requirements.
