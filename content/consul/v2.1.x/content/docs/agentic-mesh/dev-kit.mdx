# Consul Development Kit and upstream watcher

The Consul Development Kit provides application-local integration with Consul Agentic Mesh Platform (CAMP). Applications explicitly configure its components to observe upstream connectivity, handle human-approval callbacks, manage component lifecycles, and optionally host agent-card metadata.

The kit is not an agent framework or a mesh data plane. Refer to the [CAMP overview](/consul/docs/agentic-mesh) for the scope of these architectural descriptions.

## Introduction

The kit runs in the application process beside a Consul-managed proxy. It observes the local proxy's view rather than querying the Consul control plane for every application. Consul and Envoy remain responsible for service registration, workload identity, routing, and service intentions.

The runtime defines four components:

| Component | Responsibility | Boundary |
| --- | --- | --- |
| `UpstreamWatcher` | Observe local Envoy clusters and notify the application of additions, changes, and removals. | Events are observations, not authorization decisions or complete endpoint inventories. |
| `HITLWatcher` | Receive human-in-the-loop (HITL) approval requests and invoke application callbacks. | A separate interceptor verifies approval evidence and enforces the result. |
| `CompositeWatcher` | Coordinate startup and shutdown of configured components. | Process-local lifecycle management does not establish mesh readiness or service dependencies. |
| `CardServer` | Optionally serve agent-card metadata. | Hosting a card does not implement an agent protocol or confer trust. |

## Upstream observation

The upstream watcher polls the protected local Envoy administration interface and compares snapshots. Applications consume change events to update their view of configured upstreams.

Observed connectivity has important limits:

- A visible cluster does not establish permission to perform an application operation.
- A resolved address is not necessarily a safe application destination. Calls must use the approved proxy path.
- A failed poll is not proof that an upstream disappeared.
- No change event does not prove that discovery remains fresh.
- Callback delivery is not a durable event queue or an exactly-once notification mechanism.

Protect access to the proxy administration interface. Do not expose it as an application discovery API to untrusted callers.

## Approval integration

An application supplies the callback that presents a challenged action for human review. The approval endpoint denies the request unless the callback explicitly approves it. The application must validate untrusted arguments before displaying or using them.

The kit can return approval evidence bound to challenge fields, including the operation, destination, arguments hash, nonce, and trace context. A separately configured enforcement processor must verify that evidence against the original request before forwarding the operation.

The kit does not intercept arbitrary application traffic, verify its own evidence on behalf of the destination, or distribute signing keys. A returned approval token is not sufficient without trusted verification and destination authorization.

## Lifecycle and agent cards

Lifecycle coordination groups application-local startup and shutdown. Applications remain responsible for configuration, readiness decisions, failure handling, and appropriate drain deadlines. A running watcher does not establish that every dependency is available.

Optional agent-card hosting publishes descriptive metadata. A card is not evidence that an agent is authorized, that its declared skills are correct, or that a remote endpoint is safe to call. Protocol compatibility and approved destinations require separate validation.

## Proposed automatic upstream management

<Note>
Automatic upstream client management is a separate design proposal. The baseline upstream watcher does not create Agent2Agent (A2A) clients, install routes, or enforce discovery freshness.
</Note>

The proposal extends observation with trusted routing bindings, a qualified A2A protocol adapter, reconciliation, and a process-local client registry. A client becomes usable only when its observed destination matches an approved proxy binding and its protocol profile passes validation.

The proposed manager owns client creation, replacement, bounded drain, and retirement. It must stop admitting calls when bindings become invalid or observations exceed their freshness limit. It must not turn the first reported backend address or an agent-card URL into an unrestricted connection target.

Consul and Envoy still own network configuration and authorization. The application still chooses which agent to invoke and how to manage its workflow. Automatic client management does not replay business operations or provide durable task recovery.

## Dependencies and boundaries

The kit requires explicit application integration and access to the intended local proxy. Approval workflows also require a separately configured enforcement processor and trusted verification configuration.

The kit does not provide an identity service, durable memory store, telemetry backend, OAuth token exchange, or provider credentials. Its component lifecycle is separate from those systems' lifecycles.
