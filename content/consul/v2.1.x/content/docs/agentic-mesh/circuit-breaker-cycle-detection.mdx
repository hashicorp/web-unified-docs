# Circuit breaker cycle detection

Cycle detection is part of Agentic Analytics in Consul Agentic Runtime Fabric.
The primary pattern covered here is an agent repeatedly calling the same tool
with the same argument values without producing new results. Consul uses these
findings to detect unproductive agent workflows and open the affected agent's
circuit according to behavior policy.

## Introduction

An agent can repeatedly call the same tool with the same arguments while every
request returns successfully. Ordinary mesh resilience does not identify this behavior
because the upstream services remain available and responsive.

For example, an agent might repeatedly invoke `query_records` with
`{"filter":"status:active","page":1}` and receive the same records on each call.
Repeating that call and summarizing unchanged results does not advance its task. Cycle detection
analyzes the workflow's steps and results to identify this unproductive repetition.
An agent-scoped circuit contains the affected agent without automatically blocking
other agents that use the same upstream service.

Analysis runs asynchronously. Agentic Analytics evaluates trace evidence, and
Consul's enforcement path checks the resulting protection state before allowing
subsequent requests. Enabling ordinary mesh circuit breaking alone does not enable
cycle detection.

## How cycles are detected

A cycle finding requires both a repeated structure and repeated results. Focus on
whether the same agent repeats a tool call with the same argument values within a
workflow, rather than merely counting calls to the same tool. Repeated tool names
or identical arguments alone are not sufficient evidence of an unproductive cycle.

### Structural check

The detector reduces the trace to an ordered sequence of workflow steps, including
tool calls, delegations, and summaries. It finds maximal runs of a repeating unit
and collapses duplicate matches. The configured minimum repetition count determines
which runs qualify for semantic analysis.

Repeated invocations of `query_records` with the same filter and page values are
the primary example. A call followed by a summary can also form a repeating
two-step unit. In that case, examine the arguments of the corresponding tool call
across repetitions, not the inputs of different steps within one repetition.

### Semantic check

The detector compares outputs at the same position across repetitions: each
retrieval result is compared with the other retrieval results, and each
summary is compared with the other summaries. It does not compare the retrieval
result with the summary within the same repetition.

Outputs are reduced to their values before comparison. Shared field names alone
must not make different tool results appear identical. Identical outputs match
directly; otherwise, the detector compares text embeddings against a configurable
similarity threshold.

A candidate pattern is reported as unproductive when at least one position repeats
the same or sufficiently similar result across passes. This does not require every
position in the repeating unit to remain unchanged. Review this behavior when
setting policy for workflows with deliberately stable intermediate results.

An agent that changes the `page` argument to retrieve new records can repeat the
same tool name while making progress. Conversely, a call with unchanged arguments
can return new data as the underlying state changes. Neither the tool name nor
argument equality alone establishes a lack of progress; the semantic check remains
necessary. Structural repetition alone must not open the circuit.
Cycle findings are evidence for behavior policy, not proof that the entire task has
failed or that all repeated work is unnecessary.

## Detection and enforcement

| Stage | Responsibility |
| --- | --- |
| Proxy auto-instrumentation | The AI Inference Gateway and MCP sidecars emit correlated spans for supported model and tool exchanges, with tool identity and approved argument and result evidence required for analysis. |
| Trace producer | Enqueue trace IDs onto a BullMQ queue as workflow evidence arrives. |
| Trace backend | Store spans and make the available trace evidence queryable. |
| Agentic Analytics | Consume queued trace IDs, fetch spans, and run structural and semantic checks. |
| Behavior policy | Evaluate cycle findings and determine whether to open the affected agent's circuit. |
| Protection-state storage | Publish agent-scoped circuit state, its reason, and its validity period. |
| Enforcement processor | Consult applicable state before forwarding a subsequent request through the Consul data plane. |

The [specialised proxies automatically instrument supported traffic](/consul/docs/agentic-mesh/Auto-instrumentation-KPIs) without application tracing SDKs or manual spans. Applications preserve trace context across calls and supply business outcomes that are not visible in network exchanges. Missing context or unsupported traffic limits the evidence available to the detector.

The queue carries trace IDs; the worker retrieves the corresponding spans from the
trace backend. A trace ID can be queued multiple times as the workflow grows.
Detection passes for the same trace run serially, while different traces can be
analyzed concurrently up to the configured limit.

Trace export and indexing can lag behind queue delivery. Schedule a later pass when
evidence is not yet available; do not treat an empty or incomplete trace as proof of
healthy behavior. Analysis must not hold the original application request open
while waiting for evidence.

Consul uses the policy decision to open an agent-scoped circuit. The enforcement
processor rejects subsequent applicable requests while that circuit is open. The
agent-specific design uses HTTP `503` for this rejection. It does not cancel calls
that have already passed enforcement or reverse completed tool actions.

## Set up cycle detection

Deploy Agentic Analytics alongside the other Agentic Runtime Fabric components.
Pulling the analytics image and its dependencies is required, but the images alone do not connect trace
production, analysis, protection-state storage, and enforcement.

### Prerequisites

- A configured Consul Agentic Runtime Fabric deployment, including agent services, Envoy data-plane proxies, and the required external processors. Use Consul Enterprise with the license required for external processing.
- The AI Inference Gateway and MCP sidecars for the model and tool paths used by your application, plus applicable identity and credential integrations.
- Configured [proxy auto-instrumentation](/consul/docs/agentic-mesh/Auto-instrumentation-KPIs), application trace-context propagation, an OpenTelemetry collection path, and a trace backend that the selected analytics release supports.
- A BullMQ-compatible Redis or Valkey deployment for queued analysis work and a configured protection-state store.
- Registry access to the `csl-ag-ana` image and its required dependencies, `<registry>/csl-ig-pro:latest` and `<registry>/csl-nod-rly:latest`, plus compatible versions of the other Agentic Runtime Fabric components.
- A behavior policy that defines agent scope, detection thresholds, circuit validity, recovery, and dependency-failure handling.

### Pull Agentic Analytics and its dependencies

Pull `csl-ag-ana` together with the required `csl-ig-pro` and `csl-nod-rly`
dependency images. These are required in addition to the images for Consul, the
data plane, and the other gateway, external-processing, telemetry, and storage
components used by your deployment.

Use the registry and analytics release tag supplied for your Agentic Runtime
Fabric distribution. Here registry denotes IBM Container Registry(ICR). Replace `<registry>` in all image references and `<version>`
in the analytics image reference before running the commands:

```shell
docker pull <registry>/csl-ag-ana:<version>
docker pull <registry>/csl-ig-pro:latest
docker pull <registry>/csl-nod-rly:latest
```

For Podman deployments, use the same image references:

```shell
podman pull <registry>/csl-ag-ana:<version>
podman pull <registry>/csl-ig-pro:latest
podman pull <registry>/csl-nod-rly:latest
```

Authenticate to the registry using your container runtime's credential mechanism
when required. The dependency commands use the `latest` tags; for reproducible
deployments, pin approved compatible release tags or digests in the deployment
manifest. Do not assume that an unqualified image name resolves to the intended registry.

### Connect traces and queued analysis

1. Propagate W3C Trace Context across agent, model, delegation, and tool calls. Include a stable, trusted agent identity that can also be resolved by enforcement.
2. Configure span export to the collector and storage in the trace backend. Confirm that a workflow's spans can be retrieved by trace ID.
3. Configure the trace producer to enqueue trace IDs as evidence arrives. The local integration uses a span relay; an inference-path producer must also provide enough triggers to analyze later workflow activity.
4. Configure the producer and Agentic Analytics consumer to use the same queue backend, queue name, and prefix. A mismatch can leave both services running without delivering analysis work.
5. Configure the analytics worker's trace-query endpoint and access credentials. Confirm that the backend is reachable from the worker's network, not only from the operator's machine.

Use a `noeviction` memory policy for the BullMQ backend so queue data structures
are not independently evicted. Configure persistence and capacity for the required
delivery guarantees; an in-memory development queue can lose pending analysis
triggers on restart.

To inspect repeated calls, provide tool identity and comparable argument values
within the correlated workflow evidence. Semantic analysis also needs comparable
output values. Use only representations supported by the analytics component and
approved under your data-handling policy. Do not enable unrestricted capture of
prompts, tool arguments, tool results, credentials, or personal data merely to supply
the detector. Missing or redacted evidence can prevent assessment of argument
equality or limit the findings that semantic analysis can produce.

### Configure analytics and circuit enforcement

Use the configuration schema and deployment manifest supplied with the selected
`csl-ag-ana` release. The following table describes required configuration inputs,
not literal environment-variable names or configuration keys.

| Configuration input | What to configure |
| --- | --- |
| Analytics image | The fully qualified `csl-ag-ana` release image pulled in the previous step. |
| Dependency images | The `<registry>/csl-ig-pro:latest` and `<registry>/csl-nod-rly:latest` images, or approved compatible pinned versions, in their corresponding deployment services. |
| Queue connection | Backend endpoint, authentication, queue name, and prefix shared with the producer. |
| Trace source | A supported trace backend's query endpoint and access credentials. |
| Cycle detector | Enable cycle analysis and set the minimum repetition count and semantic similarity threshold. |
| Analysis scheduling | Bound concurrent traces and indexing waits, and preserve serial passes for each trace. |
| Agent attribution | Map findings and requests to the same trusted agent identity and policy scope. |
| Circuit policy | Define when a finding opens a circuit, the reason recorded, and its validity and recovery rules. |
| Protection-state connection | Give the decision publisher write access and enforcement processors the access needed to check applicable state. |
| Dependency failures | Define handling for unavailable queues, missing traces, stale state, and failed state reads or writes. |

Start the queue and state services, trace backend, and collection path before the
analytics consumer and trace producer. Deploy the analytics service with the
configured image, network access, and credentials. Confirm that its cycle detector
is enabled and consuming the expected queue.

Connect the analytics decision path to protection-state publication, and configure
the agent enforcement processors to read that state before forwarding requests.
Detection logs alone do not establish that Consul can open or enforce a circuit.
Keep storage and analytics endpoints private and grant only the access each
component needs.

### Verify the complete path

Use a non-production agent workflow and a test model or bounded usage
budget to verify both detection and enforcement.

1. Run a healthy workflow that calls the same tool with different argument values, such as successive `page` values, and receives new results. Confirm trace delivery and analysis without a cycle finding for that pattern. Also test unchanged arguments with changing results to verify that argument equality alone does not trigger a finding.
2. Run a controlled workflow in which the same agent repeatedly calls `query_records` with `{"filter":"status:active","page":1}` and receives unchanged results. Exceed the configured repetition threshold and confirm a finding for that exact trace and agent. If the workflow includes summaries between calls, keep those results unchanged as well.
3. Confirm that behavior policy publishes an open circuit for the affected agent, with a reason and validity period.
4. Send another request through the protected route. Confirm an HTTP `503` rejection and that the request does not reach the protected upstream.
5. Send a request from an unaffected agent using the same backend. Confirm that agent-scoped containment does not block it.
6. Exercise the configured expiry or reset procedure and confirm that admission resumes. Separately test the defined behavior when analytics or protection-state storage is unavailable.

Inspect worker activity as well as queue state. An empty queue does not prove that
all scheduled detection passes have finished, and a cycle finding does not prove
that enforcement has consumed the resulting state.

## Protection state and recovery

Closed state allows requests that satisfy the other applicable controls. Open state
contains requests for the affected agent. Store the agent identity, policy context,
reason, and validity period with the decision so enforcement can distinguish
applicable protection from stale state.

Recovery follows the configured expiry or reset rules. A time-to-live can provide
automatic expiry; operator reset is a separate recovery action. Neither establishes
that the agent's underlying behavior has been corrected. Do not assume a half-open
probe state unless the deployed component explicitly supports it.

## Detection limits and degraded operation

Detection follows execution, trace export, indexing, analysis, and state
publication. Additional activity can occur before enforcement sees an open circuit.
The mechanism cannot prevent every unsafe first action, recall an in-flight call,
or undo a completed side effect.

Missing spans, sampling, unavailable output evidence, and analysis backlog can
prevent or delay a finding. Absence of a finding does not establish that a workflow
is healthy. Monitor analysis lag, failed jobs, trace availability, state freshness,
circuit transitions, and enforcement rejections.

Define dependency-failure behavior explicitly for each workload. There is no
universal fail-open or fail-closed choice for unavailable analytics or state
storage. Keep synchronous authorization, usage limits, human approval requirements,
and application validation in place independently of cycle detection.

## Dependencies and boundaries

Agentic Analytics owns cycle analysis; Consul uses its findings through behavior
policy and agent-scoped enforcement. Applications supply workflow semantics and
remain responsible for planning, tool business logic, and recovery from side
effects. Cycle detection does not prove model quality or successful task completion.

Trace evidence, comparison inputs, and findings remain subject to telemetry privacy,
access-control, and retention requirements. Do not copy sensitive comparison values
into circuit reasons, metrics, or routine logs.
