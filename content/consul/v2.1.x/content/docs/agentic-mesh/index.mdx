# Consul Agentic Mesh Platform

Consul Agentic Mesh Platform (CAMP) extends service mesh governance to AI application interactions with models, agents, and tools. This section describes component responsibilities, their interactions, and the boundaries between network controls and application behavior.

<Note>
These pages describe the CAMP architecture. Design capabilities, including automatic upstream management, intelligent circuit breaking, token-aware admission, and audit delivery, are not guarantees of availability in a Consul release. Component pages distinguish these from implementation-backed behavior. Confirm component support before planning a deployment.
</Note>

## Introduction

An AI application can call a model, delegate work to another agent, and invoke tools on behalf of a user. Each interaction requires a distinct decision: whether the workload can connect, whether the user has delegated authority, whether the requested model or tool is permitted, and whether the operation requires human approval.

CAMP separates these decisions across gateways, identity integrations, application-local development libraries, and observability components. Consul workload identity and service intentions remain the foundation for mesh connectivity. They do not replace delegated user authorization or application policy.

## Components

| Component | Responsibility | Architectural boundary |
| --- | --- | --- |
| [AI Inference Gateway](/consul/docs/agentic-mesh/inference-gateway) | Govern model access, routing, provider translation, usage controls, and data protection. | Honor permitted explicit model choices and caller-approved fallback. |
| [MCP Gateway](/consul/docs/agentic-mesh/mcp-gateway) | Govern Model Context Protocol (MCP) tool discovery and invocation. | Catalog visibility does not grant permission to invoke a tool. Backends own tool business logic. |
| [Consul Development Kit and upstream watcher](/consul/docs/agentic-mesh/dev-kit) | Observe local proxy connectivity and integrate application lifecycle, approval callbacks, and optional agent-card hosting. | The kit neither installs routes nor grants authorization. |
| [Identity plane and on-behalf-of (OBO) delegation](/consul/docs/agentic-mesh/identity) | Carry destination-scoped delegated user authority alongside workload identity. | Customer identity and access management (IAM) remains the token issuer. |
| [External-MCP credential injection](/consul/docs/agentic-mesh/credential-injection) | Authenticate approved external HTTP MCP calls at the terminating gateway. | Callers cannot choose secret locations or override trusted destination bindings. |
| [Intelligent circuit breaker](/consul/docs/agentic-mesh/circuit-breaker) | Provide proposed agent-scoped containment based on observed behavior. | Asynchronous detection affects subsequent requests and cannot establish that a completed action was safe. |
| [AI observability, audit, and higher-order KPIs](/consul/docs/agentic-mesh/observability) | Correlate gateway decisions, usage, and application-provided outcomes. | Network success does not establish task success or model quality. |

## Workflows

### Govern model access

The AI Inference Gateway receives an application model request, evaluates operator policy, and routes eligible requests to a provider. Provider translation preserves the supported client-facing interface. Model attribution and usage connect the request to operational evidence and accounting consumers.

### Govern tool access

The MCP Gateway combines workload identity, delegated user authority where present, and tool policy. Human approval supplies additional evidence when policy requires it. Approved in-mesh tools use mesh connectivity; external HTTP MCP tools use a terminating gateway with trusted credential bindings.

### Integrate applications

Applications explicitly configure and consume Development Kit integrations. The upstream watcher reports the local proxy's view of connectivity, while application callbacks connect approval workflows to a separate enforcement processor. Neither observation nor a callback creates authorization.

### Investigate operational outcomes

Metrics, traces, and audit evidence describe model access, tool calls, and policy decisions. Application instrumentation supplies workflow outcomes needed for higher-order key performance indicators (KPIs) and behavioral analysis. Sensitive request content and credentials must not enter telemetry.

## Shared security boundaries

- Authenticate workloads and validate delegated user authority separately. Their credentials, policies, and lifecycles are distinct.
- Keep model-provider authentication separate from OBO delegation and external-MCP credential injection.
- Bind human approval to the original action. Approval evidence does not replace destination authorization.
- Treat request identifiers as correlation values, not identities or authorization evidence.
- Treat telemetry as operational evidence, not a durable audit store or billing ledger without additional delivery and retention controls.
