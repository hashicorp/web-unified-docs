# Upgrade Consul to v2.1.x

This page describes the process to upgrade a Consul Enterprise deployment running Consul Enterprise 2.0.x to Consul Enterprise 2.1.x.

## Introduction

This guide explains how to upgrade a Consul Enterprise datacenter running Consul Enterprise 2.0.x to a currently supported Consul Enterprise 2.1.x maintenance release. Review the release notes and changelog for your exact target release before you begin.

If you have multiple Consul datacenters, upgrade the primary datacenter first, followed by secondary datacenters one at a time. Before starting, confirm that ACL replication, CA federation, and WAN federation are healthy between all datacenters. Consul supports a mixed-version cluster of the source and target releases only for the duration of the rolling upgrade itself; do not leave datacenters on different major versions for an extended period. Take a snapshot of each datacenter before upgrading it.

For Consul Community Edition, follow the [General Upgrade Process](/consul/docs/upgrade/instructions/general). Community Edition is not affected by the Enterprise licensing requirements described below, but does not have access to Enterprise-only features introduced in 2.1.x.

## Requirements

- All Consul servers, clients, and snapshot agents should be on Consul Enterprise version >= 2.0.0 and < 2.1.0. If they are not at the minimum version, follow the [normal upgrade procedures](/consul/docs/upgrade) to upgrade them until the version requirement is met.
- Your Consul Enterprise cluster must already use an IBM Consul Enterprise license.
- The datacenter has no unresolved Raft, membership, Autopilot, ACL replication, certificate, proxy connectivity, license, or storage errors. Resolve any existing errors before you begin the upgrade; refer to [Pre-upgrade checks](#pre-upgrade-checks).
- Envoy or Consul dataplane on your clients and gateways must be compatible with both your current release and your target 2.1.x release for the duration of the rolling upgrade. Refer to [Consul Kubernetes compatibility](/consul/docs/upgrade/k8s/compatibility) and your target release's changelog for the exact supported Envoy version range.

## Assumptions

This guide makes the following assumptions:

- You are familiar with the [General Upgrade Process](/consul/docs/upgrade/instructions/general).
- You have the ability to run Consul CLI commands.
- If ACLs are in use, then you possess a token with the permissions required for each command in this guide:
  - `consul license get` requires `operator:read`.
  - `consul snapshot save` and `consul snapshot restore` require `acl:write`.
  - `consul operator raft list-peers` requires `operator:read`.
  - `consul info` requires `agent:read` on each queried agent.
  - `consul members` filters its output per node using the token's `node:read` access; it doesn't require a single dedicated permission.
- If you run Consul API Gateway on Kubernetes, you are prepared to migrate Gateway API resources as part of this upgrade.

## Considerations

Review the [Consul 2.1.x version-specific upgrade details](/consul/docs/upgrade/version-specific#consul-2-1-x) page for the main changes in Consul 2.1.x that require special handling during the upgrade process.
