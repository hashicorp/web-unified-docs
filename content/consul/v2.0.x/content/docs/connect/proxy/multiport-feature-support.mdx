# Multiport feature support

@include 'alerts/enterprise-alert.mdx'

This page summarizes the support status of Consul service mesh features when used with [multiport services](/consul/docs/connect/proxy/multiport). Use this page to understand which multiport capabilities are generally available today, which are planned for an upcoming release, and which are not currently supported.

## Support levels

- **v2.0.x**: Generally available in the current release line.
- **v2.1.x (planned)**: Implemented on the development branch and targeted for the next minor release. Functionality may still change before release.
- **Not yet planned**: No committed timeline. These items are not on the current roadmap.
- **Not supported**: Explicitly excluded and not expected to be supported.

<Note>

Some rows below are still being validated internally and may be revised as engineering confirms final scope. Contact your Consul account team for the latest status on any item marked as not yet planned.

</Note>

<sup>1</sup> Cross-partition routing to multiport services is validated for Kubernetes deployments using Consul admin partitions. Support on other platforms has not been separately validated.

<sup>2</sup> Cluster peering adds the ability to route traffic to named ports on a peered multiport service.

<sup>3</sup> Today, only a multiport service's default port fully traverses a configured `service-router`, `service-splitter`, or `service-resolver`. Named, non-default ports connect directly to the destination service's port instead of returning an error. A patch fix in **v2.0.4** prevents connection failures for this case. Full parity, where every named port can traverse the discovery chain like the default port, is planned for **v2.1.x**.

<sup>4</sup> Intentions are currently enforced at the service level. Virtual IPs for named ports resolve to the base service for intention evaluation, rather than being evaluated independently per port.

<sup>5</sup> Envoy emits per-cluster metrics because each named port receives its own cluster name. Distributed tracing does not yet include port-level tags or spans.

<sup>6</sup> Includes a fix so that older agents that cannot decode multi-port catalog data continue to receive the correct default port value across catalog, health check, prepared query, and streaming subscription responses.

<sup>7</sup> Named ports are resolvable using DNS SRV lookups. Other DNS record types do not disambiguate between multiple ports on the same service.

<sup>8</sup> Includes a fix for prepared query responses returning stale or missing port data for multiport services when mixed-version agents are present.
