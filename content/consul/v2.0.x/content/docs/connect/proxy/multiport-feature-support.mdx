# Multiport feature support

@include 'alerts/enterprise-alert.mdx'

This page summarizes the support status of Consul service mesh features when used with [multiport services](/consul/docs/connect/proxy/multiport). Use this page to understand which multiport capabilities are generally available today, which are planned for an upcoming release, and which are not currently supported.


<Note>

This is feature is under active development and validation phase, and only supported in consul-enterprise

</Note>

## Feature support matrix

| Feature | v2.0.x | v2.1.x (planned) | Future |
| --- | --- | --- | --- |
| Cross-partition | Partial<sup>1</sup> | — | — |
| Cluster peering | — | Yes<sup>2</sup> | — |
| Upstream: transparent proxy mode | Yes | — | — |
| Upstream: non-transparent proxy mode | Yes | — | — |
| Multi-protocol (L7) | Partial<sup>3</sup> | Yes<sup>3</sup> | — |
| API gateway | — | — | To be planned |
| Terminating gateway | — | — | To be planned |
| Ingress gateway | — | — | Not planned (deprecated)<sup>8</sup> |
| Discovery chain: splitter, resolver, and router | Partial<sup>3</sup> | Yes<sup>3</sup> | — |
| Proxy and service defaults: destination port | — | Yes | — |
| Proxy and service defaults: source port | — | — | To be planned |
| Escape hatches, fault injection, and other overrides | — | — | To be planned |
| Port-specific intentions (ACLs) | Partial<sup>4</sup> | — | — |
| Per-port TLS permissiveness override | — | — | To be planned |
| Per-port metrics and tracing | Partial<sup>5</sup> | — | — |
| Port-wise health checks and reconciliation | — | Yes<sup>6</sup> | — |
| Platform: Kubernetes | Yes | — | — |
| Platform: ECS, ESM, and Terraform modules | — | — | To be planned |
| DNS compatibility | Partial<sup>7</sup> | — | — |
| DNS: localized DNS | — | — | To be planned |
| DNS: prepared queries | — | Yes | — |
| Passthrough mode (transparent proxy) | — | — | To be planned |
| Per-port watches and scale testing | — | — | To be planned |

<sup>1</sup> Validated for Kubernetes with Consul admin partitions.

<sup>2</sup> Extends named-port routing, virtual IP allocation, and DNS resolution to imported services across a cluster peering connection, including through mesh gateways.

<sup>3</sup> In v2.0.x, only the default port fully traverses a configured `service-router`, `service-splitter`, or `service-resolver`; named, non-default ports connect directly to the destination port instead. A **v2.0.4** patch prevents connection failures for this case. In v2.1.x, every named port, not just the default, is compiled into a port-aware discovery chain view and can carry its own protocol, resolver subset destination port, and routing behavior.

<sup>4</sup> Intentions are enforced at the service level. Named-port virtual IPs resolve to the base service for intention evaluation.

<sup>5</sup> Each named port gets its own Envoy cluster, enabling per-cluster metrics. Distributed tracing doesn't yet include port-level tags.

<sup>6</sup> Ensures older agents receive correct port data across catalog, health checks, prepared queries, and streaming.

<sup>7</sup> Named ports resolve via DNS SRV lookups; other record types don't disambiguate between ports. Peered multiport services can also resolve to their imported per-port virtual IPs.

<sup>8</sup> Ingress gateway is deprecated.
