# Contributing to HashiCorp Validated Designs

This guide covers how to contribute to HashiCorp Validated Designs (HVDs). Value Engineering in R&D manages all HVD content. If you have questions about anything in this guide or want to get involved, reach out in **#proj-hvd** on Slack.

## Before you start

Before making any contribution, review the published [HVDs on the developer portal](https://developer.hashicorp.com/validated-designs) to understand the tone, structure, and level of detail expected.

For help with prerequisites and permissions, post a message in the relevant slack channel.

| Channel | Scope |
| ------- | ----- |
| `#proj-hvd` | General HVD questions and access requests |
| `#talk-hvd-modules` | HVD Modules questions |

## Types of contribution

| What you want to do | How to do it |
| --- | --- |
| Edit existing HVD content | Branch or fork this repository, edit the relevant MDX file, open a PR |
| Add a new page to an existing HVD | Branch or fork this repository, create the MDX file, update `docs-nav-data.json`, open a PR |
| Submit a Validated Pattern | Submit through the VE Tech Catalog (see [Validated Patterns](#validated-patterns) below) |
| Report an issue or suggest content improvements | Create an [HVD feedback GitHub issue](https://github.com/hashicorp/web-unified-docs/issues/new?template=hvd-feedback.yml) |
| Contribute to HVD Modules | Work in the relevant module repository in the `hashicorp` GitHub org (see [HVD Modules](#hvd-modules) below) |

## What is prescriptive guidance?

HVDs provide presciptive or opinionated guidance. They provide a clear recommendation based on field experience helping enterprise customers, not a survey of all possible approaches. Keep the following principles in mind when writing:

- **Give a recommendation, not options.** Even when multiple approaches are valid, choose one and explain why.
- **Do not duplicate product documentation.** If HashiCorp docs or developer.hashicorp.com already covers something, link to it rather than repeating it. The value of an HVD is the opinion and context on top of what the docs provide.
- **Write for platform teams and consumers.** The primary audience is the team responsible for deploying and operating HashiCorp products in an enterprise environment.
- **Collaborate on contested topics.** For areas where there is no clear field consensus (branching strategies, auth method choices, and similar), coordinate through R&D and field leadership before writing the recommendation. Reach out in `#proj-hvd` to start that conversation.

## Working with content files

### File location

Content files live at:

```txt
content/validated-designs/docs/docs/<product>/<guide-type>/<slug>.mdx
```

For example:

```txt
content/validated-designs/docs/docs/vault/administration-guide/backup-and-restore-operations.mdx
content/validated-designs/docs/docs/terraform/installation-guide/architecture.mdx
```

Vault's Installation Guide has two sub-types for different platforms:

```txt
content/validated-designs/docs/docs/vault/installation-guide/vms/<slug>.mdx
content/validated-designs/docs/docs/vault/installation-guide/openshift/<slug>.mdx
```

### Frontmatter

Every MDX file requires these two frontmatter fields:

```yaml
---
page_title: Your page title
description: A concise description of what this page covers.
---
```

Do not add or edit the `created_at` or `last_modified` fields — these are auto-generated by the build and marked accordingly in the file.

### Shared partials

Fragments shared across multiple pages live in `docs/partials/`. Include them in a page with:

```mdx
@include "partial-filename.mdx"
```

Do not duplicate content that belongs in a partial. If you find yourself copying the same block into multiple files, it should be a partial.

### Guide directory metadata

Each guide directory contains an `index.yaml` with a `title` and `description` used in the navigation and page headers:

```yaml
title: 'Vault Administration Guide'
description: 'Manage and operate Vault Enterprise as a day-2 platform service.'
```

### Naming conventions

- Filenames: lowercase kebab-case, `.mdx` extension
- Image filenames: `hvd-<product>-<guide-type>-<kebab-title>.svg` (see [Diagrams](#diagrams) below)
- Guide types in paths: `installation-guide`, `administration-guide`, `user-guide`

## Updating navigation

The sidebar navigation for all HVD content is defined in a single file:

```
content/validated-designs/data/docs-nav-data.json
```

Every MDX file you add must have a corresponding entry in this file, otherwise it will not appear in the navigation. Entries follow this structure:

```json
{ "title": "Your page title", "path": "<product>/<guide-type>/<slug>" }
```

Nest entries inside the appropriate `routes` array for the product and guide type. Match the `path` exactly to the file path relative to `docs/docs/`, without the `.mdx` extension.

### Naming and storage

Name each image using this convention:

```txt
hvd-<product>-<doc-type>-<kebab-case-title>
```

Where `<doc-type>` is one of:

| Abbreviation | Guide type |
| ---- | --- |
| `ig` | Installation Guide |
| `ag` | Administration Guide |
| `ug` | User Guide |
| `vp` | Validated Pattern |

For example:

```txt
hvd-vault-ig-reference-architecture.svg
```

Store images in the repository:

```
content/validated-designs/img/<product>/<guide-type>/hvd-<product>-<guide-type>-<kebab-title>.svg
```

### Image format

Where possible use SVG format for diagrams and PNG format for images such as screenshots.

## Pull request process

1. Create a fork or branch from `main`
2. Make your changes — content edits, new files, nav updates, and images
3. Open a PR against `main` with a clear description of what changed and why
4. The HVD core team reviews and approves using the standard GitHub PR review process

> There is no separate review board, committee, or scheduled meeting — all review happens in the PR

Keep PRs focused. If you are making changes to multiple guides or multiple products, consider splitting them into separate PRs to make review easier.

## Validated Patterns

### What makes a good pattern

A Validated Pattern is a concise, outcome-focused guide for achieving a specific result with HashiCorp products. It is not a tutorial and is not general product guidance.

A good pattern:

- Addresses a single, well-defined outcome (for example, "use Vault secrets in a Terraform run")
- Assumes the reader already knows the products involved to a reasonable degree and requires no introductory material (link to docs if necessary)
- References the relevant HVD guides for prerequisites rather than duplicating them
- Focuses on enterprise capabilities and production-grade configuration, not community editions
- Includes at least one diagram
- Does not duplicate content already in product documentation

### Submission process

Submit Validated Patterns through the **VE Tech Catalog**, not directly to this repo.

**Preferred:** Use [Navi](https://navi.hashicorp.services) to submit your pattern using the Tech Catalog workflow. Navi guides you through the content requirements and formats the submission correctly.

**Alternative:** Submit your pattern using the [Tech Catalog submission template](https://github.ibm.com/ve-tech-catalog/library/issues/new?template=tech-catalog-submission.yml).

### Review process

After submission, the HVD core team:

1. Triages the submission and prioritises it against the current backlog
2. Contacts you to confirm project details and timeline
3. Reviews the content for accuracy, quality, and alignment with HVD standards
4. Promotes approved patterns into the appropriate Administration or User Guide in this repo as a dedicated MDX page

You do not need to open a PR to this repo to submit a pattern. The HVD core team handles the migration from catalog to guide.

## HVD Modules

HVD Modules are Terraform modules that codify the reference architectures in the HVD Installation Guides. Management of these modules is in separate repositories in the [`hashicorp` GitHub org](https://github.com/hashicorp) and published to the [Terraform Registry](https://registry.terraform.io).

Changes to modules (new features, bug fixes, cloud provider updates) are made in those repositories, not here. A module change does not typically require an update to the HVD guide content in this repo.

For the full list of available modules and their registry links, see the [module coverage table in README.md](README.md#module-coverage).

For questions about modules, ask in **#talk-hvd-modules** on Slack.
