# Configure Ping for agent IAM

@include 'alerts/beta.mdx'

@include 'alerts/enterprise-and-hcp.mdx'

Configure users and OIDC applications in PingFederate to use with Vault Enterprise agentic IAM.

## Before you start

- **You must have an [PingFederate](https://www.pingidentity.com/en/product/pingfederate.html) client.**

- **You must have [`curl`](https://curl.se/)** or some other tool to make API
  calls.

- **You must have [`jq`](https://jqlang.org/) installed** to use the example
  commands as written.

## Configure `PingFederate` token issuance

### Step 1 - create the default JWT access token manager for RAR

You will create the Default JWT Access Token Manager used for RAR-capable tokens.

PingFederate issues OAuth access tokens as signed JWTs. Vault, as an OAuth resource server, validates these JWTs and maps their claims to a Vault identity.

Configure the Default Access Token Manager with Authorization Details Claim Name = `authorization_details` so PingFederate can emit a populated `authorization_details` claim for RAR requests.

Do not use this Access Token Manager for autonomous or OBO output tokens. Those non-RAR flows use the separate Autonomous Access Token Manager so PingFederate omits `authorization_details` entirely.

1. Navigate through the UI to `APPLICATIONS → OAuth → Access Token Management → Create New Instance` 

1. Set the instance to have the following properties:

   | Field | Value |
   |-------|-------|
   | Instance Name | Default |
   | Instance ID | default |
   | Type | JSON Web Tokens |
   | Parent Instance | None |

1, CHeck the default fields match:

   | Field | Value |
   |-------|-------|
   | Token Lifetime | 120 |
   | Use Centralized Signing Key | ✅ checked |
   | JWS Algorithm | RSA using SHA-256 |
   | Active Symmetric Key ID | -- Select One -- (leave) |
   | Active Signing Certificate Key ID | -- Select One -- (leave) |
   | JWE Algorithm | -- Select One -- (leave) |
   | JWE Content Encryption Algorithm | -- Select One -- (leave) |
   | Active Symmetric Encryption Key ID | -- Select One -- (leave) |
   | Asymmetric Encryption Key | (blank) |
   | Asymmetric Encryption JWKS URL | (blank) |
   | Enable Token Revocation |  ☐ unchecked |

1. Click Show Advanced Fields and check the values match.

   | Field | Value |
   |-------|-------|
   | Include Key ID Header Parameter | ✅ checked |
   | Include X.509 Thumbprint Header Parameter | ☐ unchecked |
   | Default JWKS URL Cache Duration | 720 |
   | Include JWE Key ID Header Parameter | ✅ checked |
   | Include JWE X.509 Thumbprint Header Parameter | ☐ unchecked |
   | Client ID Claim Name | client_id |
   | Scope Claim Name | scope |
   | Space Delimit Scope Values | ✅ checked |
   | Authorization Details Claim Name | `authorization_details` |
   | Issuer Claim Value | (blank) |
   | Audience Claim Value | (blank) |
   | Not Before Claim Offset | (blank) |
   | Include Issued At Claim | ✅ checked |
   | JWT ID Claim Length | 22 |
   | Access Grant GUID Claim Name | (blank) |
   | Publish Keys to PingFederate JWKS Endpoint | ☐ unchecked |
   | JWKS Endpoint Path | (blank) |
   | JWKS Endpoint Cache Duration | 720 |
   | Publish Key ID X.509 URL | ☐ unchecked |
   | Publish Thumbprint X.509 URL | ☐ unchecked |
   | Expand Scope Groups | ☐ unchecked |
   | Type Header Value | (blank) |

1. On the **Session Validation** tab, leave all four options unchecked:

   - Include Session Identifier in Access Token
   - Check for Valid Authentication Session
   - Check Session Revocation Status
   - Update Authentication Session Activity

   Vault is validating the JWT itself as an OAuth resource server. These tokens are not tying PingFederate to browser sessions, so session validation would add an unnecessary dependency. If authentications are not enabled globally expect a warning on the page.

#### Access Token Attribute Contract

Next you will define which claims PingFederate allowed to issue from the Default JWT Access Token Manager. To use RAR tokens this contract includes `authorization_details`.

1. Navigate to `Applications → OAuth → Access Token Management → Default → Access Token Attribute Contract`

1. Configure the contract with these attributes:

   | Attribute Name |
   |----------------|
   | `authorization_details` |
   | `client_id` |
   | `iss` |
   | `sub` | 

   ![Access token contact](/img/agentic-ai/screenshot-ping-access-token-contact.png)

1. Save the Access Token Attribute Contract with `USER_KEY`  as the subject attribute and `authorization_details`, `client_id`, `iss`, and `sub` added to the contract.

1. Leave the Token Endpoint Attribute Contract, Resource URIs, and Access Control tabs at their defaults and finish the JWT Access Token Manager setup.

###  Step 2 - Configure the default client-credentials access-token mapping for RAR

Configure the client-credentials access-token mapping for the Default JWT Access Token Manager.

The Default Access Token Manager is the RAR-capable token manager. It includes the `authorization_details` contract attribute used by `vault-rar-client`.

This mapping allows PingFederate to issue client-credentials JWTs that can include a populated `authorization_details` claim when the RAR client supplies one in the token request.

Do not use this mapping for `vault-agent-autonomous`. The autonomous flow uses a separate client-credentials mapping for the Autonomous Access Token Manager so `authorization_details` is omitted entirely. 

1. Navigate to `APPLICATIONS → OAuth → Access Token Mappings`.

   Create the mapping with these values:

   | Field | Value |
   |-------|-------|
   | Context | Client Credentials |
   | Access Token Manager | Default |
   | Attribute Sources & User Lookup | Leave Data Sources empty |

   ![Access token mappings](/img/agentic-ai/screenshot-ping-token-mappings.png)

1. In the **Contract Fulfillment** tab Configure the following mappings.

   | Contract attribute | Source | Value |
   |--------------------|--------|-------|
   | authorization_details | No Mapping | Leave unmapped |
   | client_id | Context | ClientId |
   | iss | Text | https://localhost:9031 |
   | sub | Context | ClientId |

   <Note>
      
      The `authorization_details` is intentionally left as No Mapping here. For RAR, PingFederate populates `authorization_details` from the client-supplied `authorization_details` request parameter after configuring the `vault:path_access` authorization detail type and processor.

      For non-RAR client-credentials tokens, do not rely on No Mapping to suppress the claim. If the Access Token Manager has Authorization Details Claim Name set to `authorization_details`, PingFederate can still emit `authorization_details`: []. Non-RAR flows use the separate Autonomous Access Token Manager instead.
      
   </Note>

   ![Contract fulfillment](/img/agentic-ai/screenshot-ping-access-token-mappings-contract-fulfillment.png)

   Leave all issuance criteria fields empty.

   Do not add a source, attribute, condition, value, or error result.

1. Click **Next** to continue to the **Summary** tab.

   Before saving, confirm the summary shows:

   - Context: Client Credentials
   - Access Token Manager: Default
   - `authorization_details` set to No Mapping
   - `client_id` mapped from Context → ClientId
   - `iss` mapped from Text → https://localhost:9031
   - `sub` mapped from Context → ClientId
   - No issuance criteria

   ![Summary](/img/agentic-ai/screenshot-ping-access-token-summary.png)

1. After confirming the summary matches these values, click Save.

   After saving, the Default client-credentials mapping is ready for RAR-capable tokens issued to `vault-rar-client`.

### Step 3 - Create the autonomous JWT access token manager for non-RAR tokens

You will create the JWT Access Token Manager used for non-RAR tokens.

- `vault-agent-autonomous` uses this Access Token Manager for autonomous client-credentials tokens
- `vault-obo-client` for exchanged OBO output tokens

Unlike the Default Access Token Manager, this manager must not emit `authorization_details`. The Authorization Details Claim Name must be left blank, and `authorization_details` must not be added to the Access Token Attribute Contract.

1. Navigate to: `Applications → OAuth → Access Token Management → Create New Instance`

1. Create a second JWT Access Token Manager for the autonomous no-RAR flow.

Type tab

| Field          |    Value |
|----------------|----------|
| Instance Name  |    Autonomous |
| Instance ID    |    autonomous | 
| Type           |    JSON Web Tokens |
| Parent Instance|    None |
| Instance Configuration

Use the same JWT configuration values as the Default Access Token Manager, except for the authorization details settings below.

Field                               Value
Authorization Details Claim Name    blank

Access Token Attribute Contract

Add only these contract attributes:

- `client_id`
- iss
- sub

<Note title='Warning'>
   Do not enter `authorization_details` for this Access Token Manager. If this field is set, PingFederate can emit `authorization_details`: [] for non-RAR tokens, which causes Vault to treat the request as RAR and reject it with `RAR_NO_MATCH`.
</Note>

Completion check

Before saving, confirm:

Instance ID is autonomous

- Authorization Details Claim Name is blank
- The Access Token Attribute Contract contains `client_id`, iss, and sub
- The contract does not contain `authorization_details`

After saving, the Autonomous Access Token Manager is ready to issue clean non-RAR JWTs for autonomous and OBO flows.

<Note title='Note'>

The previous autonomous test failed because the shared Default JWT Access Token Manager had Authorization Details Claim Name set to `authorization_details`, which caused PingFederate to emit `authorization_details`: []. Vault then rejected the request with RAR_NO_MATCH. The dedicated Autonomous Access Token Manager prevents this by omitting the claim entirely.

</Note>

![Token details no-RAR](content/vault/v2.x/img/agentic-ai/screenshot-ping-access-token-no-RAR.png)

### Step 4 - Configure the Autonomous client-credentials access-token mapping

Configure the client-credentials access-token mapping for the Autonomous JWT Access Token Manager.

This mapping is used by `vault-agent-autonomous`  to issue clean non-RAR client-credentials JWTs.

The mapping fulfills only the claims needed for Vault identity resolution:

- `client_id`
- iss
- sub

It must not include `authorization_details`.

Navigate to Applications → OAuth → Access Token Mappings

Click Add Mapping.

Mapping configuration

Configure the mapping with:

| Field | Value |
| Context | Client Credentials |
| Access Token Manager | Autonomous |

Click Select.

Attribute Sources & User Lookup

Leave Data Sources empty.

No user lookup is required because the OAuth client identity is used as the JWT subject.

Click Next.

Contract Fulfillment

Configure the mappings as follows:

| Contract attribute | Source | Value | 
| `client_id` | Context | ClientId |
| `iss` | Text | https://localhost:9031 |
| `sub` | Context | ClientId |

The `authorization_details` attribute should not appear in this contract because it was not added to the Autonomous Access Token Manager.

Issuance Criteria

Leave all issuance criteria fields empty.

Do not add:
- a source
- an attribute
- a condition
- a comparison value
- an error result

Click Next.

Verify the summary

Confirm that the summary shows:

- Context: Client Credentials
- Access Token Manager: Autonomous
- No data sources
- `client_id` mapped from Context → ClientId
- `iss` mapped from Text → https://localhost:9031
- `sub` mapped from Context → ClientId
- No `authorization_details` mapping
- No issuance criteria

Click Save.

![Verify summary](content/vault/v2.x/img/agentic-ai/screenshot-ping-autonomous-client-credentials-access-token-mapping.png)

After saving, the Autonomous Access Token Manager can issue client-credentials JWTs for `vault-agent-autonomous`  without emitting `authorization_details`.

## Step 5: Create the OAuth clients and assign Access Token Managers

Create the three OAuth clients under Applications → OAuth → Clients → Add Client.

Each client should be assigned to the Access Token Manager that matches its flow:

- `vault-agent-autonomous` uses Autonomous because it must omit `authorization_details`.
- `vault-rar-client` uses Default because it must emit `authorization_details` for RAR.
- `vault-obo-client` uses Autonomous because the exchanged OBO token must omit `authorization_details`.

![vault-agent-autonomous config](/img/agentic-ai/screenshot-ping-vault-agent-autonomous-config.png)

![more config](/img/agentic-ai/screenshot-ping-vault-agent-autonomous-oauth-allowed-grant-types.png)

For each client:

- Set Client Authentication to Client Secret.
- Generate and store each client secret securely.
- Leave unrelated OIDC, redirect, refresh token, and consent settings at their defaults unless the flow requires them.
- Assign the Access Token Manager shown in the table above.

| Client ID | Grant types | Default Access Token Manager | Restrict to Default Access Token Manager | Authorization Details | 
| `vault-agent-autonomous`  | Client Credentials | Autonomous | Checked | Disabled / unchecked |
| `vault-rar-client`  | Client Credentials | Default | Checked | Enabled, select `vault:path_access`  after the RAR type is created |
| `vault-obo-client`  | Token Exchange | Autonomous | Checked | Disabled / unchecked |

<Note title=''>

   Note: The `vault-rar-client`  authorization detail type cannot be selected until the VaultPathAccessProcessor plugin is installed and the global `vault:path_access`  authorization detail type is created. If the type is not available yet, create the client first, then return to the client after Step 13 and enable `vault:path_access`  in Step 14.

</Note>

### Step 8 — Prepare Vault identity objects for the autonomous agent

Run from the test workspace:

```shell-session
$ cd ~/code/ping-vault-test
```

Create the Vault policy for the autonomous client:

```shell-session
$ vault policy write ping-autonomous-read - <<'HCL'
path "secret/data/alice" {
  capabilities = ["read"]
}
HCL
```

Create the Vault Identity entity:

```shell-session
$ ENTITY_ID=$(vault write -field=id identity/entity \
  name="vault-agent-autonomous" \
  policies="ping-autonomous-read")

echo "$ENTITY_ID"
```

Get the OAuth resource server profile config ID and build the alias accessor:

```shell-session
$ CONFIG_ID=$(vault read -field=config_id sys/config/oauth-resource-server/ping)
OAUTH_ACCESSOR="oauth-resource-server_root_${CONFIG_ID}"
echo "$OAUTH_ACCESSOR"
```

Create the entity alias for the PingFederate JWT subject:

```shell-session
$ vault write identity/entity-alias \
  name="vault-agent-autonomous" \
  canonical_id="$ENTITY_ID" \
  mount_accessor="$OAUTH_ACCESSOR"
```

Register the entity as an agent:

```shell-session
$ jq -n \
  --arg entity_id "$ENTITY_ID" \
  '{
    display_name: "vault-agent-autonomous",
    entity_id: $entity_id,
    description: "PingFederate autonomous client credentials test agent",
    owner: "Vault identity storage integration test",
    optional_authorization_details: true
  }' | vault write agent-registry/register -
```

Vault has a policy, identity entity, OAuth resource server entity alias, and Agent Registry record for the PingFederate autonomous client. This step is required because Vault resolves OAuth JWTs to Identity entities and requires an Agent Registry record for direct OAuth JWT requests.

#### OBO flow: PingFederate token exchange to Vault

This section verifies an on-behalf-of style OAuth token exchange flow from PingFederate to Vault.

In this setup, `vault-agent-autonomous` receives the original subject access token. Then `vault-obo-client`  exchanges that subject token for a new PingFederate-issued access token. Vault accepts the exchanged token when PingFederate preserves the original subject in `sub` and omits `authorization_details`.

| Component | Purpose |

Final OBO result

The working OBO flow requires three key details:

| Issue | Working fix |
| Ping rejected the subject token as Invalid Token | Use OAuth Bearer Access Token Token Processor, not JWT Token Processor 2.0 |
| Vault rejected OBO token with RAR_NO_MATCH | Do not emit `authorization_details`: [] |
| OBO output token needed clean claims | Use the autonomous Access Token Manager for OBO output |

Summary:

PingFederate successfully performs OAuth token exchange for the OBO flow. The working configuration validates the incoming PingFederate-issued subject access token with an OAuth Bearer Access Token Token Processor, preserves the original subject in sub, emits `client_id`=vault-obo-client, and issues the exchanged token through an Access Token Manager that does not emit `authorization_details`. Vault accepts the resulting token for KV v2 access.
