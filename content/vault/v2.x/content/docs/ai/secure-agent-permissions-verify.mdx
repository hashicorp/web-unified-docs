# Secure agent permissions with Verify and Vault

@include 'alerts/enterprise-and-hcp.mdx'

Vault Enterprise enables an agent or other AI application to authenticate with
an OAuth access token that carries a Rich Authorization Request (RAR) claim.
An identity provider (IdP) functions as an authorization server to issues
the RAR tokens.

This least-privilege approach implements zero trust principles by ensuring
agent credentials are ephemeral and narrowly scoped through delegation. The agent acts on behalf of a human developer and receives an effective permission set that is the intersection of three independent controls:

1. Human baseline ACL policies define what the person can do

1. Agent ceiling policies from the Vault Agent Registry cap the maximum
   the agent can ever do

1. Per-session RAR claims carried in the token specify what one session
   may access

IBM Verify functions as an authorization server to issue OAuth RAR tokens to
an agent or other AI applcation, which that agent or application can then use
to authenticate with Vault.

## How the request flow works

![Agentic AI workflow](/img/agentic-ai/diagram-agentic-iam-flow-light.svg#light-theme-only)

![Agentic AI workflow](/img/agentic-ai/diagram-agentic-iam-flow-dark.svg#dark-theme-only)

The diagram illustrates the workflow where the human user (the subject)
authenticates with an IdP (in this case, IBM Verify) and how the human user's
agent can use the delegated RAR token issued by Verify to authenticate with
Vault.

Vault enables an OAuth resource server to validate the JWT presented by the
AI agent or application (the actor). Vault knows about The AI agent or
application identity informagion through registration in the Agent Registry.

<Tip>

Review the [Rich authorization requests (RAR)](/vault/docs/ai/agent-support/rich-authorization-requests) documentation for a deeper dive into
how RAR works with Vault.

</Tip>

## Requirements

You must have the following to explore the usage involved in securing agent
permissions with Verify and Vault.

- An IBM Verify tenant. You can
  [sign up for a free trial](https://docs.verify.ibm.com/verify/docs/getting-started-signing-up-for-a-free-trial)
  to use for the purposes of evaluating the integration and steps shown
  in this documenation.

- [oauth2c](https://github.com/SecureAuthCorp/oauth2c)
  command-line tool installed and in your system `PATH`. This is a command-line
  tool that you can use to interact with OAuth 2.0 authorization servers.

- An operating Vault Enterprise or HCP Vault Dedicated server.

- A Vault token from the server with sufficient ACL policies attached to enable
  the operations described in this document.

- A terminal session with shell.

- A web browser that you can use to complete OAuth authentication flows.

- [curl](https://curl.se/) or another tool installed and in your system `PATH`
  for API request examples.

- [jq](https://jqlang.org/) installed and in your system `PATH` for
  parsing JSON-formatted API responses.

### Create authorization detail type

(Admin user)

You need to create an authorization details schema to define how information

flows.

2. Click **Authorization detail types**.

3. Click **Create**.

4. Under **General details**, select the **Custom** radio button.

5. In the **Name** field, define a name for this authorization detail type,

6. In the **Description** field, enter a description for the type.

   ![Authorization type configuration](/img/agentic-ai/screenshot-verify-app11.png)

   `authorization_details` query parameter:

   ```json
   {
     "type": "object",
     "required": [
       "type",
       "path",
       "capabilities"
     ],
     "additionalProperties": false,
     "properties": {
       "type": {
         "const": "vault:path_access"
       },
       "path": {
         "type": "string",
         "pattern": "^[A-Za-z0-9._/:-]+$"
       },
       "capabilities": {
         "type": "array",
         "uniqueItems": true,
         "items": {
           "type": "string",
           "enum": [
             "read",
             "create",
             "update",
             "delete",
             "sudo",
             "list",
             "deny"
           ]
         }
       }
     }
   }
   ```

8. Leave **Consent mapping** settings unchanged, and click **Next**.

9. For **Consent configuration** method, select **Inline HTML**.

10. For **Consent text**, enter `<div>EXAMPLE CONSENT TEXT</div>`.

## Validate token retrieval

Use the `ouauth2c` tool to get a token from Verify as a validation step.

You must get your application's client ID and client secret values to use
for this step.

### Get application details

Get your application's values by following these steps in the Verify UI.

(Admin user)

1. Click **Applications** > **Applications**.

2. Click the gear icon next to your application name to open settings.

3. Click **Sign-on**.

4. Scroll down to **Client ID** and copy the value; paste the value somewhere
   safe to use later.

5. Click the copy to clipboard icon next to **Client secret** and then paste
   the value somewhere safe to use later.

### Request a token

1. In a terminal session, export your Verify tenant name, client ID, and
   secret as the values of `IBM_VERIFY_TENANT`, `IBM_VERIFY_CLIENT_ID`,
   and `IBM_VERIFY_CLIENT_SECRET`.

    ```shell-session
    export IBM_VERIFY_TENANT=`<tenant name>`
        IBM_VERIFY_CLIENT_ID=`<client ID generated from previous step>` \
        IBM_VERIFY_CLIENT_SECRET=`<client secret generated from previous step>`
    ```

2. Request an example token with the oauth2c command-line tool.

    ```shell-session
    $ oauth2c https://"${IBM_VERIFY_TENANT}".verify.ibm.com/oauth2 \
        --pkce \
        --client-id "${IBM_VERIFY_CLIENT_ID}" \
        --client-secret "${IBM_VERIFY_CLIENT_SECRET}" \
        --response-types code \
        --response-mode query \
        --grant-type authorization_code \
        --auth-method client_secret_basic --no-browser
    ```

3. Note the URL under `Go to the following URL:` in the output. Visit that
   URL in a browser to complete the authentication flow. The workflow then
   outputs more indicators of success.

   <CodeBlockConfig hideClipboard>

   ```plaintext
   ...snip...
    SUCCESS  Obtained authorization code
   ...snip...
   SUCCESS  Exchanged authorization code for access token
   ```

   </CodeBlockConfig>

The final output string after the SUCCESS messages represents the JWT value,
which validates both the workflow and token issuance from Verify.

### Exchange agent and human tokens

You can also exchange the AI agent (actor) and human user (subject) tokens with
RAR `authorization_detail` claims with a similar workflow by providing token
values from tokens issued for both the AI agent and the human.

1. Export the AI agent token value as the AGENT_TOKEN environment variable.

    ```shell-session
    $ export AGENT_TOKEN=...
    ```

1. Export the human user token value as the HUMAN_TOKEN environment variable.

    ```shell-session
    $ export HUMAN_TOKEN=...
    ```

1. Export the DELEGATION_TOKEN environment variable to hold the output of
   the token exchange.

    ```shell-session
    $ export DELEGATION_TOKEN=$(curl --request POST \
    --url https://vv-agentic-iam-demo.ite4.idng.ibmcloudsecurity.com/oauth2/token \
    --header 'Content-Type: application/x-www-form-urlencoded' \
    --data grant_type=urn:ietf:params:oauth:grant-type:token-exchange \
    --data subject_token="${HUMAN_TOKEN}" \
    --data subject_token_type=urn:ietf:params:oauth:token-type:access_token \
    --data actor_token="${AGENT_TOKEN}" \
    --data actor_token_type=urn:ietf:params:oauth:token-type:access_token \
    --data client_id="${IBM_VERIFY_CLIENT_ID}" \
    --data client_secret="${IBM_VERIFY_CLIENT_SECRET}" \
    --data 'authorization_details=[{"type":"vault:path_access","path":"secret-v2/data/shared-secret/foo", "capabilities":["create"]}]' | jq -r '.access_token)
    ```

## Configure Vault Enterprise

Configure your Vault Enterprise to accept JWTs with `authorization_details`,
and OBO semantics as means to perform authorized operations on Vault.

### Export environment variables

You can export some environment variables to prepare for interacting with your
Vault Enterprise instance and to make configuration more convenient.

- VAULT_ADDR: The API address of your Vault Enterprise server.
- VAULT_TOKEN: Token ID with sufficient capabilities to configure Vault.
- DELEGATED_JWT: The OBO with authorization details JWT as obtained after token
  exchange via the STS client.
- ISSUER: The issuer retrieved from the Well known Open ID configuration of
  the application created in Verify.
- SUBJECT_EXT_ID: User ID of the subject user as noted in the user
  creation step.
- ACTOR_EXT_ID: User ID of the actor user as noted in the user creation step.

Replace all placeholder values with your actual values, and then export the
environment variables,

```shell-session
export VAULT_ADDR="http://127.0.0.1:8200" \
    VAULT_TOKEN="root" \
    DELEGATED_JWT="<idp-issued-jwt>"
    ISSUER="https://vv-agentic-iam-demo.ite4.idng.ibmcloudsecurity.com/oauth2" #
    SUBJECT_EXT_ID="811006P2MZ"
    ACTOR_EXT_ID="811006P2N1"
```

Enable Vault to accept OAuth resource server tokens by setting the
appropriate activation flag. The necessary features will not function
without you first performing this step.

```shell-session
$ vault write -force sys/activation-flags/oauth-resource-server/activate
Key            Value
---            -----
activated      [oauth-resource-server]
unactivated    [secrets-import secrets-sync]
```

### Create the OAuth resource server profile

Create a new OAuth resource server configuration profile in a json file
named `default-profile.json`. Update the parameters to your actual values
before you write the file.

1. Write the OAuth resource server confiugration file.

    ```shell-session
    $ cat > default-profile.json << EOF
    {
    "issuer_id": "https://hashicups-print.verify.ibm.com/oauth2",
    "use_jwks": true,
    "user_claim": "sub",
    "supported_algorithms": ["RS256"],
    "jwks_uri": "hashicups-print.verify.ibm.com/oauth2/jwks"
    }
    EOF
    ```

    <Warning>

    **IBM Verify Limitation**: The example avoids validating with the `audiences` as the STS client configured to perform the OBO token exchange with RAR `authorization_details` does not support addition of `audience` mapping in the access token mapping.

    </Warning>

2. Create the OAuth resource server profile.

    ```shell-session
    $ vault write sys/config/oauth-resource-server/e2e-profile \
        @default-profile.json
    WARNING! The following warnings were returned from Vault:
    * algorithm "RS256" is functional but consider using PS256 (RSA-PSS) for
    better security
    * profile supports only one algorithm family - consider supporting multiple
    families for flexibility
    ```

3. Read the profile to check for correctness, and make a note of the
   `config_id` value to formulate the mount accessor to associate with the
   alias of the subject and actor entities.

    ```shell-session
    $ vault read sys/config/oauth-resource-server/e2e-profile
    vault read sys/config/oauth-resource-server/e2e-profile
    Key                     Value
    ---                     -----
    audiences               [https://localhost:8200/v1]
    clock_skew_leeway       0
    config_id               de81dc66-e00d-23c6-7dfc-9cdbc5aaf97e
    enabled                 true
    issuer_id               https://hashicups-print.verify.ibm.com/oauth2
    jwks_uri                https://hashicups-print.verify.ibm.com/oauth2/jwks
    jwt_type                access_token
    no_default_policy       false
    profile_name            e2e-profile
    supported_algorithms    [RS256]
    use_jwks                true
    ```

In this example, the mount accessor is constructed as follows:

<CodeBlockConfig hideClipboard>

```plaintext
oauth-resource-server + _ + namespace ID + _ + OAuth resource server profile config_id
```

</CodeBlockConfig>

If operating in the root namespace, the mount accessor for this example profile
becomes `oauth-resource-server_root_de81dc66-e00d-23c6-7dfc-9cdbc5aaf97e`.

### Create ceiling policy

Create a ceiling policy to encompass all the possible operations you can perform in the example commands in this documentation.

Write the ceiling policy to the file `ceiling-policy.hcl`.

```shell-session
$ cat > ceiling-policy.hcl << EOF
# Allow KV2 read and write
path "secret-v2/data/shared-secret/*" {
  capabilities = ["create", "read", "update", "delete", "list"]
}

path "secret-v2/metadata/shared-secret/*" {
  capabilities = ["list"]
}

# Allow PKI operations
path "pki/issue/example-dot-com" {
  capabilities = ["create", "update"]
}

path "pki/cert/*" {
  capabilities = ["read"]
}

path "pki/certs" {
  capabilities = ["list"]
}

# Allow transit engine operations
path "transit/encrypt/app-key" {
  capabilities = ["update", "create", "read"]
}

# Allow decrypt
path "transit/decrypt/app-key" {
  capabilities = ["update", "create", "read"]
}

# Optional: allow key metadata read (safe)
path "transit/keys/app-key" {
  capabilities = ["read"]
}
EOF
```

Write the ceiling policy.

```shell-session
$ vault policy write ceiling-all ceiling-policy.hcl
Success! Uploaded policy: ceiling-all
```

1. Use the token obtained from the token exchange to perform a KV2 operation.

    ```shell-session
    $ echo '{"data": {"foo": "bar"}}' | VAULT_TOKEN=$DELEGATION_TOKEN vault write secret-v2/data/shared-secret/foo -
    Key                Value

    custom_metadata    <nil>
    deletion_time      n/a
    destroyed          false
    version            1
    ```

1. Try to perform vault secret write on the same path. This results in an update
   operation, but updates get prohibited by the current RAR policy.

    ```shell-session
    $ echo '{"data": {"foo": "bar_new"}}' | VAULT_TOKEN=$DELEGATION_TOKEN vault write secret-v2/data/shared-secret/foo -
    Error writing data to secret-v2/data/shared-secret/foo: Error making API request.

    	* permission denied
    ```

1. Try to perform the same operation by obtaining a new token with update and
   read capabilities on the token. Get a new token with update.

    ```shell-session
    $ export DELEGATION_TOKEN=$(curl --request POST \
    ```


<Note>

`vault kv put` and `vault kv get` use a special type of unauthenticated
preflight check path (`/sys/internal/ui/mounts`) internally to determine
whether the requested KV path is a KV version 1 or version 2 engine.

The request handling flow does not recognize external tokens when routing to
this unauthenticated endpoint and results in an error. This is a known bug,
and you are encouraged to use `vault read` and `vault write` commands to
work around the issue.

</Note>
