# SPIFFE auth method — overview

@include 'alerts/enterprise-only.mdx'

The `spiffe` auth method lets workloads authenticate to Vault using SPIFFE
Verifiable Identity Documents (SVIDs). You can choose either X.509 certificates
or JWTs whose trust comes from a configured trust bundle. Unlike
platform-specific auth methods (Kubernetes, AWS, Azure), SPIFFE auth works the
same way regardless of what the workload is running on: bare metal, virtual
machines (VMs), or multi-cloud Kubernetes clusters.

## Use cases for SPIFFE auth with Vault

SPIFFE auth is a fit when:

- Your workloads span heterogeneous compute sources such as bare metal, VMs, or
  multiple clouds with no single platform-native identity issuer covering
  all workloads.
- You need mTLS-based identity (X.509-SVID), not just bearer JWTs. For
  example, if you require Vault access to fit into a broader zero-trust or
  service-mesh identity model rather than a single auth token.
- You already run SPIRE or a service that generates SVIDS for workload identity
  and want Vault to consume identity from that same trust domain instead of
  maintaining a separate auth scheme.
- You need identity that federates across organizational or cloud
  boundaries through a standardized trust-domain model.

For user based interactive/browser-based authentication, review the [JWT/OIDC
auth method](/vault/docs/auth/jwt).

### SPIFFE auth vs. SPIFFE secrets engine

- Use SPIFFE auth (`auth/spiffe`) when you have SPIRE (or another SPIFFE
  issuer) running and want to log into Vault using a SVID.
- Use the SPIFFE secrets engine (`secrets/spiffe`) when you are already
  logged into Vault (via Kubernetes, AppRole, AWS, etc.) and want Vault to
  issue you a SVID. See the SPIFFE secrets engine docs for details.

## Architecture

A common point of confusion when integrating SPIFFE with Vault is
determining which system generates the identity versus which system
consumes it.

Vault cannot issue a SPIFFE identity to a workload before the workload logs in.
A SPIFFE control plane (a SPIRE Agent running on the host node, or a service
mesh) must attest the workload and issue an SVID first.

Vault is the consumer, not an issuer of the SVID. The `auth/spiffe` plugin allows
Vault to accept and validate identities generated by an external SPIFFE authority
(such as SPIRE), it does not generate SPIFFE identities itself.

```
[ External SPIFFE Issuer ] ───(0. Fetch trust bundle)───────> [ HashiCorp Vault ]
 (e.g., SPIRE Agent/Server)                                    (validates SVIDs
        |                                                        against bundle)
        │                                                               ▲
        │ 1. Issue SVID                                                 │
        ▼                                                               │
   [ Workload ] ─────────────(2. Present SVID to login)─────────────────┘
```

## Supported trust bundle formats

Vault accepts two types of SVIDs:

- **X.509-SVIDs (mTLS)**: The client presents a client certificate
  containing a SPIFFE URI (e.g.,
  `spiffe://example.org/ns/prod/sa/payment-service`) in its SAN field. Vault
  validates the certificate against the configured trust bundle.
- **JWT-SVIDs**: The client fetches a short-lived JWT from its local SPIFFE
  Workload API and sends it as a bearer token. Vault validates the signature
  against the trust bundle's JWKS and checks the `aud` claim against the
  mount's audience allow-list.

The trust bundle's file format determines which SVID types Vault can
validate. A bundle in the wrong format will not validate the other type,
even if everything else is configured correctly.

| Bundle format | Contains | Validates |
|---|---|---|
| JWKS document | X.509 CA certificate(s) and JWT signing key(s) | X.509-SVIDs and JWT-SVIDs |
| PEM-encoded X.509 certificate | X.509 CA certificate only | X.509-SVIDs only |

The SVID you choose maps directly to the `profile` parameter when you configure
the SPIFFE auth method in Vault. Each type has different use cases and trade
offs.

| Profile | Bundle format | SVID types supported | Vault gets the bundle via | Best for |
|---|---|---|---|---|
| `static` (bundle = PEM) | PEM | X.509-SVIDs only | Pasted in directly, no fetch | Air-gapped/no-network-dependency requirement, JWT-SVID not needed, strict change control on trust-anchor updates |
| `static` (bundle = JWKS) | JWKS | X.509-SVIDs and JWT-SVIDs | Pasted in directly, no fetch | Same as above, but both SVID types needed |
| `https_web_pem` | PEM | X.509-SVIDs only | Auto-fetched over standard TLS | Vault can reach the endpoint, JWT-SVID not needed, endpoint has a normal (web-PKI-trusted) certificate |
| `https_web_bundle` | JWKS | X.509-SVIDs and JWT-SVIDs | Auto-fetched over standard TLS | Vault can reach the endpoint, both SVID types needed, endpoint has a normal (web-PKI-trusted) certificate |
| `https_spiffe_bundle` | JWKS | X.509-SVIDs and JWT-SVIDs | Auto-fetched, endpoint authenticated via its own SPIFFE ID | Same as above, but you don't want to (or can't) issue the Federation endpoint a publicly-trusted TLS cert — keeps endpoint trust inside the SPIFFE fabric itself instead of web PKI |

If Vault is behind a load balancer or reverse proxy, review [load
balancer and proxy considerations](/vault/docs/auth/spiffe/spiffe#load-balancer-and-proxy-considerations)
before you configure anything. Where TLS terminates determines whether
X.509-SVID auth is viable as documented, or whether you need to rely on
JWT-SVIDs instead.

## Choose an auth method

Vault supports auth methods for various platforms. You can mix and match auth
methods to support where you workloads run, or select a single auth method that
supports all workloads.

|  | Kubernetes auth | Cloud auth (AWS/Azure/GCP) | JWT/OIDC auth | SPIFFE auth (Enterprise) |
|---|---|---|---|---|
| **Best for** | Workloads in a single k8s cluster | Workloads on a single cloud provider's compute | Workloads whose platform already issues OIDC tokens (k8s, GitHub Actions, GitLab CI, cloud workload identity) | Heterogeneous fleets — bare metal, VMs, multi-cloud, no shared native issuer |
| **Identity source** | Kubernetes API server (projected service account tokens) | Cloud provider IAM / instance metadata | An OIDC issuer's JWKS | A SPIFFE-compliant issuer (SPIRE, Istio, etc.) via node/workload attestation |
| **Credential type** | Bearer JWT | Signed identity document | Bearer JWT | X.509 (mTLS) or JWT |
| **Cross-platform** | No — single cluster | No — single cloud provider | Depends on the issuer | Yes — designed for cross-trust-domain federation |
| **License** | Community Edition | Community Edition | Community Edition | Vault Enterprise |
| **Operational cost** | Low — uses the cluster's built-in issuer | Low — uses the provider's built-in issuer | Low/medium — may need to stand up or trust an IdP | Higher, unless you already run SPIRE/a mesh — server + agents + trust bundle lifecycle |
