# Set up a Vault SCIM server

@include 'alerts/enterprise-only.mdx'

You can configure Vault Enterprise to act as a System for Cross-domain Identity
Management (SCIM) server that authenticates external identities.

## Before you start

- **Deploy a Vault Enterprise or HCP Vault Dedicated server**. SCIM support
  requires an Enterprise license.

- **Configure a supported identity or OAuth provider**. Vault authenticates
  SCIM requests through the provider you configure:

    - [Configure Microsoft Entra ID for SCIM with Vault](/vault/docs/iam/scim/idp/entraid)
    - [Configure Okta for SCIM with Vault](/vault/docs/iam/scim/idp/okta)
    - [Configure SailPoint for SCIM with Vault](/vault/docs/iam/scim/idp/sailpoint)

- **Check your permissions**. You must have admin permissions on Vault.

## Enable and configure OIDC auth method

To use Vault as a SCIM server that supports external identities authenticated
with an identity provider (IdP) OpenID Connect (OIDC) workflow, you must
[enable the OIDC auth method](/vault/docs/auth/jwt#configuration)
and create a named role on the Vault server.

<Tip>

The following example configures the OIDC auth method for Okta. Adjust the
discovery URL and credential variables as needed for your IdP.

</Tip>

```shell-session
$ vault write auth/oidc/config                                              \
    oidc_discovery_url="https://${OKTA_DOMAIN}"                             \
    oidc_client_id="$OKTA_CLIENT_ID"                                        \
    oidc_client_secret="$OKTA_CLIENT_SECRET"                                \
    default_role="vault-role-okta-default"
```

The following example creates the matching OIDC auth method role.

```shell-session
$ vault write auth/oidc/role/vault-role-okta-default                       \
    bound_audiences="$OKTA_CLIENT_ID"                                      \
    allowed_redirect_uris="$VAULT_ADDR/ui/vault/auth/oidc/oidc/callback"   \
    allowed_redirect_uris="http://localhost:8250/oidc/callback"            \
    user_claim="email"                                                     \
    oidc_scopes="profile,email"                                            \
    token_policies="default,scim-client-policy"
```

## Configure a SCIM client

You must create a SCIM client before you send SCIM protocol requests to Vault.

Each SCIM client represents one external provisioning system. The SCIM client
configuration consists of these fields:

- `client_name`: Namespace-scoped name for the external system. The name forms
  part of the endpoint URL.
- `access_grant_principal`: ID of the Vault entity that authorizes SCIM API
  requests for that client.
- `alias_mount_accessor`: Optional auth mount accessor. When set, Vault also
  creates a mount-bound entity alias for each SCIM user.

Vault enforces these limitations and rules:

- `access_grant_principal` must refer to an existing entity in the same
  namespace.
- `alias_mount_accessor`, when set, must refer to an existing non-local auth
  mount in the same namespace.
- `alias_mount_accessor` is immutable after creation.

<Note>

A SCIM client knows about only the resources it created. Pre-existing entities
remain invisible to the client unless you set `allow_user_adoption` to
`true` or link the entities with the `link-entity` endpoint of the
[SCIM API](/vault/api-docs/secret/identity/scim).

</Note>

## Auth method and token caveats

Any auth method can work for SCIM if authentication resolves to the Vault
entity set as the SCIM client's `access_grant_principal`.

Some SCIM clients support only a static bearer token. In those cases, use the
[token auth method](/vault/docs/auth/token). You can create a token tied to an
entity alias and pass that token directly to your SCIM client.

## Set up a bearer-token workflow

The following example uses the token auth method, which supports SCIM products
that require a static bearer token. You can use any auth method that maps back
to the configured entity for the SCIM client.

1. Create an access control list (ACL) policy that grants access to the SCIM
   API endpoints. A later step assigns the policy to the token for the
   SCIM client.

    ```shell-session
    $ vault policy write scim-client - <<'EOF'
    path "identity/scim/v2/*" {
      capabilities = ["create", "read", "update", "delete", "list"]
    }
    EOF
    ```

1. Create the Vault entity for the SCIM client.

    ```shell-session
    $ vault write -format=json identity/entity name="scim-client"
    ```

    Record the returned entity ID for the following step.

1. Create the SCIM client configuration.

    ```shell-session
    $ vault write identity/scim/client/example-client \
        access_grant_principal="<entity_id>"
    ```

    If you want Vault to create aliases for provisioned users as well, include
    the `alias_mount_accessor` parameter.

1. Create an alias on the `token/` mount for the SCIM client entity. List the
   auth mounts to find the accessor for `token/`:

    ```shell-session
    $ vault auth list
    ```

    Create the alias with the accessor you recorded:

    ```shell-session
    $ vault write identity/entity-alias \
        name="example-client" \
        mount_accessor="<token_mount_accessor>" \
        canonical_id="<entity_id>"
    ```

1. Create a token role that allows the entity alias `example-client`, excludes
   the default policy, and issues
   [orphan tokens](/vault/docs/concepts/tokens#token-hierarchies-and-orphan-tokens).

    ```shell-session
    $ vault write auth/token/roles/example-scim \
        allowed_entity_aliases="example-client" \
        orphan=true \
        token_no_default_policy=true
    ```

1. Create a token from the token auth method. The command specifies the entity
   alias and the `scim-client` policy, and excludes the default policy.

    ```shell-session
    $ vault token create \
        -role=example-scim \
        -entity-alias=example-client \
        -policy=scim-client \
        -no-default-policy
    ```

1. Use the returned token value as the bearer token for SCIM requests.

<Tip>

Plan token renewal or rotation around the time to live (TTL) value configured
on your token auth mount.

</Tip>

## Send SCIM requests

The following example calls the `ServiceProviderConfig` endpoint with a Vault
token in the request header:

```shell-session
$ curl \
    --header "X-Vault-Token: ${VAULT_TOKEN}" \
    --header "Content-Type: application/scim+json" \
    ${VAULT_ADDR}/v1/identity/scim/v2/ServiceProviderConfig
```

## Delete a SCIM client

When you delete a SCIM client, Vault starts an asynchronous cleanup workflow.

- Vault blocks new SCIM requests for that client.
- Vault removes the users and groups owned by that client.
- Vault continues removing the managed resources and the SCIM client
  configuration in the background.

Review the resources owned by a SCIM client before you delete it.
