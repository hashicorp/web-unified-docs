# Migrate from the cert-manager Vault issuer

@include 'alerts/enterprise-only.mdx'

Move certificate signing from the Vault issuer built into cert-manager, an
`Issuer` or `ClusterIssuer` with a `spec.vault` block, to a Vault Secrets
Operator `VaultIssuer` or `VaultClusterIssuer`. Your `Certificate` resources,
Secret names, and renewal settings stay the same. Only the `issuerRef` in each
`Certificate` changes.

The migration adds resources without removing the existing issuer, so you can
move one `Certificate` at a time and roll back by restoring its original
`issuerRef`.

The steps on this page cover two starting points:

- **Existing installation**: You already run the Vault Secrets Operator to sync
  secrets. You upgrade the release and reuse your Vault connection and
  authentication settings.
- **New installation**: You install the Vault Secrets Operator to issue
  certificates. You move the Vault connection and authentication settings from
  your existing issuer to the Helm chart.

## Before you start

- **Read [Issue certificates with cert-manager](/vault/docs/deploy/kubernetes/vso/cert-manager)**
  to understand how the Vault Secrets Operator issuers authenticate, approve
  requests, and sign certificates.

- **Use Vault Enterprise**. The Vault Secrets Operator issuers require Vault
  Enterprise.

- **Install [Helm](https://helm.sh/docs/intro/install/)** 3.7 or later.

- **Check your permissions**. You must have permission to:
  - Update Vault policies and auth roles.
  - Install or upgrade Helm releases in the Vault Secrets Operator namespace.
  - Create Vault Secrets Operator resources and update cert-manager
    `Certificate` resources.

- **Plan a change window**. When you change the `issuerRef` of a `Certificate`,
  cert-manager immediately requests a new certificate.

## Step 1: Plan the configuration

Review how the Vault Secrets Operator issuers work so that you can plan the
configuration for each existing issuer:

- **Authentication**: The issuers authenticate to Vault with a `VaultAuth`
  resource. `VaultAuth` supports the Kubernetes, JWT, AppRole, AWS, and GCP auth
  methods. Refer to
  [Vault authentication in detail](/vault/docs/deploy/kubernetes/vso/sources/vault/auth).
- **Signing path**: The issuers sign certificates with the
  `<mount>/sign/<role>` or `<mount>/issuer/<issuerRef>/sign/<role>` path of the
  PKI secrets engine.
- **Certificate lifetime**: When a `Certificate` does not set `spec.duration`,
  the PKI role's `ttl` determines the certificate lifetime.
- **Request approval**: An approver must have permission to approve requests
  for the issuers. The Helm chart grants this permission to the cert-manager
  built-in approver in
  [Step 4](#step-4-set-up-the-vault-secrets-operator).
- **Vault policy**: The Vault policy must grant the signing path and `read` on
  `sys/license/status`. Refer to
  [Step 3](#step-3-grant-access-to-vault).

## Step 2: Inventory the issuers and certificates

1. Export the existing issuers so that you can map their settings and restore
   them if needed:

   ```shell-session
   $ kubectl get issuer,clusterissuer --all-namespaces --output yaml \
       > issuer-inventory.yaml
   ```

   For each issuer that has a `spec.vault` block, record the `server`, `path`,
   `namespace`, CA bundle, and `auth` settings.

1. List the `Certificate` resources that reference each issuer. The following
   example lists the certificates that use an `Issuer` named `vault-issuer`:

   ```shell-session
   $ kubectl get certificate --all-namespaces --output json \
       | jq --raw-output '.items[]
         | select(.spec.issuerRef.name == "vault-issuer"
             and (.spec.issuerRef.kind // "Issuer") == "Issuer")
         | "\(.metadata.namespace)/\(.metadata.name)"'
   ```

1. Flag certificates that do not set `spec.duration`. The PKI role's `ttl`
   determines their lifetime. Refer to [Step 3](#step-3-grant-access-to-vault)
   to set the `ttl`.

## Step 3: Grant access to Vault

The Vault Secrets Operator authenticates to Vault with the service account in
its `VaultAuth` resource. Update Vault so the Vault Secrets Operator can sign
certificates. Do not remove the existing policy or auth role that the old
issuer uses yet. You need them to roll back.

1. Create a policy that grants the signing path and the license status path.
   Use the same PKI path as the `spec.vault.path` of your existing issuer:

   ```shell-session
   $ vault policy write pki-issuer - <<EOF
   path "pki/sign/example-dot-com" {
     capabilities = ["create", "update"]
   }

   path "sys/license/status" {
     capabilities = ["read"]
   }
   EOF
   ```

1. Attach the policy to a Vault auth role:

   <Tabs>

   <Tab heading="Existing installation" group="existing">

   Create a dedicated auth role and `VaultAuth` for the issuers, or add the
   `pki-issuer` policy to the `token_policies` of the role that an existing
   `VaultAuth` already uses.

   When you add the policy to an existing role, every Vault Secrets Operator
   resource that uses the same `VaultAuth` can also call the signing path. We
   recommend a dedicated role and `VaultAuth` for the issuers.

   To create a dedicated role for the Kubernetes auth method, bind it to the
   service account that the `VaultAuth` uses:

   ```shell-session
   $ vault write auth/kubernetes/role/pki-issuer \
       bound_service_account_names=default \
       bound_service_account_namespaces=app \
       token_policies=pki-issuer \
       audience=vault \
       token_ttl=1h
   ```

   </Tab>

   <Tab heading="New installation" group="new">

   Create an auth role for the `default` `VaultAuth` that the Helm chart creates
   in [Step 4](#step-4-set-up-the-vault-secrets-operator). For the Kubernetes
   auth method, bind the role to the `default` service account:

   ```shell-session
   $ vault write auth/kubernetes/role/pki-issuer \
       bound_service_account_names=default \
       bound_service_account_namespaces=vault-secrets-operator \
       token_policies=pki-issuer \
       audience=vault \
       token_ttl=1h
   ```

   </Tab>

   </Tabs>

   Set `bound_service_account_namespaces` to the namespace where the Vault
   Secrets Operator looks up the service account:

   - For a `VaultClusterIssuer`, the namespace of the `VaultAuth`. For the
     `default` `VaultAuth`, this is the Vault Secrets Operator namespace.
   - For a `VaultIssuer`, the namespace of the issuer, for example `app`.

1. If any of your certificates do not set `spec.duration`, set the `ttl` on the
   PKI role to the lifetime you want:

   ```shell-session
   $ vault patch pki/roles/example-dot-com ttl=2160h
   ```

## Step 4: Set up the Vault Secrets Operator

Set up the Vault Secrets Operator with the issuer resources and approval
permission for cert-manager.

<Tabs>

<Tab heading="Existing installation" group="existing">

Upgrade the release to a Vault Secrets Operator version that includes the
issuers, and enable approval permission for cert-manager.

1. Export the values of your current release:

   ```shell-session
   $ helm get values vault-secrets-operator \
       --namespace vault-secrets-operator \
       --output yaml > values.yaml
   ```

1. Upgrade the release with your current values and the approval setting.
   Replace `<TARGET_VSO_VERSION>` with the version you are upgrading to:

   ```shell-session
   $ helm upgrade                                    \
       --version <TARGET_VSO_VERSION>                \
       --namespace vault-secrets-operator            \
       --values values.yaml                          \
       --set certManager.approverRBAC.enabled=true   \
       vault-secrets-operator                        \
       hashicorp/vault-secrets-operator
   ```

   The chart upgrades the Vault Secrets Operator CRDs, including the
   `VaultIssuer` and `VaultClusterIssuer` CRDs.

   Always pass your current values with `--values`. When you run `helm upgrade`
   with `--set` and without your values, Helm resets your other settings to the
   chart defaults. Do not use `--reuse-values`. It keeps the chart defaults of
   your current version, so the approval permission does not include the
   cert-manager service account.

1. Confirm that the issuer CRDs exist:

   ```shell-session
   $ kubectl get crd vaultissuers.secrets.hashicorp.com \
       vaultclusterissuers.secrets.hashicorp.com
   ```

You can use the `VaultConnection` resources that you already have. When you
created a dedicated auth role in [Step 3](#step-3-grant-access-to-vault),
create a `VaultAuth` that uses it. Refer to
[Set up the cert-manager issuer](/vault/docs/deploy/kubernetes/vso/cert-manager/setup#step-4-create-the-connection-and-auth-resources)
for an example.

</Tab>

<Tab heading="New installation" group="new">

Install the Vault Secrets Operator with a default Vault connection, a default
auth method, and approval permission for cert-manager. The Helm chart creates
a `VaultConnection` and a `VaultAuth`, both named `default`, in the Vault
Secrets Operator namespace.

1. Map the settings of your existing issuer to Helm chart values:

   | cert-manager Vault issuer field | Helm chart value |
   | --- | --- |
   | `spec.vault.server` | `defaultVaultConnection.address` |
   | `spec.vault.caBundleSecretRef` or `spec.vault.caBundle` | `defaultVaultConnection.caCertSecret`. The Secret must be in the Vault Secrets Operator namespace and store the CA bundle in the `ca.crt` key. |
   | `spec.vault.serverName` | `defaultVaultConnection.tlsServerName` |
   | `spec.vault.auth.kubernetes.mountPath` | `defaultAuthMethod.mount`. Remove the `/v1/auth/` prefix. For example, `/v1/auth/kubernetes` becomes `kubernetes`. |
   | `spec.vault.auth.kubernetes.role` | `defaultAuthMethod.kubernetes.role`. Use the auth role from [Step 3](#step-3-grant-access-to-vault). |
   | `spec.vault.namespace` | `defaultAuthMethod.namespace` |

   To use the JWT, AppRole, AWS, or GCP auth method, set
   `defaultAuthMethod.method` and the matching values. Refer to
   [`defaultAuthMethod`](/vault/docs/deploy/kubernetes/vso/helm#h-defaultauthmethod)
   in the Helm chart reference.

1. Install the Vault Secrets Operator:

   ```shell-session
   $ helm install                                                   \
       --create-namespace                                           \
       --namespace vault-secrets-operator                           \
       --set defaultVaultConnection.enabled=true                    \
       --set defaultVaultConnection.address=https://vault.example.com:8200 \
       --set defaultVaultConnection.caCertSecret=vault-ca           \
       --set defaultAuthMethod.enabled=true                         \
       --set defaultAuthMethod.kubernetes.role=pki-issuer           \
       --set 'defaultAuthMethod.kubernetes.tokenAudiences={vault}'  \
       --set certManager.approverRBAC.enabled=true                  \
       vault-secrets-operator                                       \
       hashicorp/vault-secrets-operator
   ```

   The Vault Secrets Operator does not sync any secrets until you create
   secret resources, such as `VaultStaticSecret`.

1. Confirm that the `default` `VaultConnection` and `VaultAuth` are ready:

   ```shell-session
   $ kubectl get vaultconnection,vaultauth --namespace vault-secrets-operator
   ```

</Tab>

</Tabs>

When you enable `certManager.approverRBAC.enabled`, cert-manager approves every
request for the Vault Secrets Operator issuers. If you use
[approver-policy](https://cert-manager.io/docs/policy/approval/approver-policy/)
instead, leave the setting disabled. Grant the approver-policy service account
`approve` on the `vaultissuers.secrets.hashicorp.com/*` and
`vaultclusterissuers.secrets.hashicorp.com/*` signers, and update your
`CertificateRequestPolicy` selectors to match the Vault Secrets Operator
issuers.

## Step 5: Create the issuer

Map the issuer settings to a `VaultIssuer` or `VaultClusterIssuer`:

| cert-manager Vault issuer field | Vault Secrets Operator field | Notes |
| --- | --- | --- |
| `spec.vault.path` | `spec.mount` and `spec.role` | For example, `pki/sign/example-dot-com` becomes `mount: pki` and `role: example-dot-com`. |
| `spec.vault.path` with an issuer segment | `spec.mount`, `spec.role`, and `spec.issuerRef` | For example, `pki/issuer/example-issuer/sign/example-dot-com` adds `issuerRef: example-issuer`. |
| `spec.vault.namespace` | `spec.namespace` | When you omit this field, the issuer uses the namespace from the `VaultAuth`. |
| None | `spec.vaultAuthRef` | The `VaultAuth` to authenticate with. When you omit this field, the issuer uses the `default` `VaultAuth` in the Vault Secrets Operator namespace. |

Create the issuer that replaces your existing issuer. The following examples
omit `vaultAuthRef` to use the `default` `VaultAuth`. To use another
`VaultAuth`, set `vaultAuthRef` to its name or to `namespace/name`.

<Tabs>

<Tab heading="Replace an Issuer" group="vaultissuer">

```yaml
apiVersion: secrets.hashicorp.com/v1beta1
kind: VaultIssuer
metadata:
  name: vso-issuer
  namespace: app
spec:
  mount: pki
  role: example-dot-com
```

</Tab>

<Tab heading="Replace a ClusterIssuer" group="vaultclusterissuer">

```yaml
apiVersion: secrets.hashicorp.com/v1beta1
kind: VaultClusterIssuer
metadata:
  name: vso-cluster-issuer
spec:
  mount: pki
  role: example-dot-com
```

Every namespace can use the `default` `VaultAuth`. When the issuer uses another
`VaultAuth`, set `allowedNamespaces` on that `VaultAuth` to every namespace that
requests certificates, or to `["*"]`. Refer to
[Vault authentication and namespace access](/vault/docs/deploy/kubernetes/vso/cert-manager#vault-authentication-and-namespace-access).

</Tab>

</Tabs>

Apply the issuer and wait until the `READY` column shows `True`. Do not update
any `Certificate` until the issuer is ready:

```shell-session
$ kubectl apply --filename vso-issuer.yaml

$ kubectl get vaultissuer --namespace app

$ kubectl get vaultclusterissuer
```

## Step 6: Update one certificate

Start with the `Certificate` that has the lowest risk. Change only its
`issuerRef`:

<Tabs>

<Tab heading="Replace an Issuer" group="vaultissuer">

```shell-session
$ kubectl patch certificate web --namespace app --type merge \
    --patch '{"spec":{"issuerRef":{"group":"secrets.hashicorp.com","kind":"VaultIssuer","name":"vso-issuer"}}}'
```

</Tab>

<Tab heading="Replace a ClusterIssuer" group="vaultclusterissuer">

```shell-session
$ kubectl patch certificate web --namespace app --type merge \
    --patch '{"spec":{"issuerRef":{"group":"secrets.hashicorp.com","kind":"VaultClusterIssuer","name":"vso-cluster-issuer"}}}'
```

</Tab>

</Tabs>

cert-manager detects the issuer change and requests a new certificate from the
Vault Secrets Operator issuer. Depending on the `spec.privateKey.rotationPolicy`
of the `Certificate`, cert-manager also generates a new private key. The Secret
keeps the existing certificate until cert-manager writes the new one.

## Step 7: Verify the certificate

1. Confirm that the new `CertificateRequest` is approved and ready, and that
   the `Certificate` is ready:

   ```shell-session
   $ kubectl get certificaterequest,certificate --namespace app
   ```

1. Inspect the issued certificate:

   ```shell-session
   $ kubectl get secret web-tls --namespace app \
       --output jsonpath='{.data.tls\.crt}' \
       | base64 --decode \
       | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
   ```

   Check the subject alternative names, and check that the validity period
   matches `spec.duration` or the PKI role's `ttl`, up to the role's `max_ttl`.

1. Confirm that the Vault Secrets Operator signed the certificate. The Vault
   Secrets Operator records a `CertificateIssued` event with the message
   `Certificate issued successfully`:

   ```shell-session
   $ kubectl get events --namespace app \
       --field-selector involvedObject.kind=CertificateRequest
   ```

When the certificate is correct, repeat
[Step 6](#step-6-update-one-certificate) and this step for each remaining
`Certificate`.

When the certificate is not correct, restore the original `issuerRef` to roll
back. cert-manager requests a new certificate from the original issuer:

```shell-session
$ kubectl patch certificate web --namespace app --type merge \
    --patch '{"spec":{"issuerRef":{"group":"cert-manager.io","kind":"Issuer","name":"vault-issuer"}}}'
```

## Step 8: Remove the cert-manager Vault issuer

After you migrate every `Certificate` that references an issuer, and each
certificate completes at least one automatic renewal, remove the old issuer:

1. Delete the cert-manager `Issuer` or `ClusterIssuer`:

   ```shell-session
   $ kubectl delete issuer vault-issuer --namespace app
   ```

1. Revoke the Vault credentials that only the old issuer used, such as its auth
   role or AppRole secret ID.

1. Delete the Kubernetes Secret that stored the old issuer's credentials.

You cannot roll back to the old issuer after you complete this step without
recreating it from `issuer-inventory.yaml`.
