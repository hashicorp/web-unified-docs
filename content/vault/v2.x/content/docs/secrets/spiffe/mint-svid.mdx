# Mint, verify, and use a SVID

@include 'alerts/enterprise-only.mdx'

You can use a JWT-SVID minted by Vault to authenticate with services that
support SPIFFE.

If you are not familiar with SPIFFE, refer to the [SPIFFE
overview](/vault/docs/secrets/spiffe) to learn more about how the SPIFFE secrets
engine works in Vault.

Follow this document as written for a working example of the Vault SPIFFE
secrets engine. Following these steps on
production hosts will change their configuration. Refer to the [setup
guide](/vault/docs/secrets/spiffe/spiffe) for general configuration instructions.

Vault and the relying party used in this doc both run as local containers for
simplicity.

## Requirements

- An active Vault Enterprise license.
- Docker or [Docker Desktop](https://www.docker.com/products/docker-desktop/) installed.
- Common command-line tools available in your shell, including `curl`, `jq`,
  `awk`, `cut`, `tr`, and `base64`.

## Set up Vault

This section walks through the minimum configuration needed to get a workload
authenticating with a Vault-minted JWT-SVID. It is not a SPIFFE production or
hardening guide.

1. Export your Vault Enterprise license as an environment variable.

   ```shell-session
   $ export VAULT_LICENSE=C10WMSH0W...snip...S3ASM3STR33T
   ```

1. Start Vault.

   ```shell-session
   $ docker run -d --name vault -p 8200:8200 \
       -e VAULT_DEV_ROOT_TOKEN_ID=root \
       -e VAULT_LICENSE=$VAULT_LICENSE \
       hashicorp/vault-enterprise:latest \
       server -dev
   ```

   <Warning title="Root tokens">
   
   The dev mode server starts with an initial root token value set.
   
   Root token use should be extremely guarded in production environments because
   it provides full access to the Vault server.
   
   You can supply the root token value to start Vault in dev mode for
   convenience and to keep the steps here focused on the learning goals of
   this tutorial.
   
   </Warning>

1. Export environment variables to access Vault.

   ```shell-session
   $ export VAULT_ADDR="http://127.0.0.1:8200" VAULT_TOKEN="root"
   ```

1. Enable the engine.

   ```shell-session
   $ vault secrets enable spiffe
   Success! Enabled the spiffe secrets engine at: spiffe/
   ```

1. Configure the trust domain.

   ```shell-session
   $ vault write spiffe/config trust_domain=example.org
   ```

1. Create a role.

   ```shell-session
   $ vault write spiffe/role/workload \
       template='{"sub": "/payments-api"}' \
       ttl=1h
   ```

   `sub` represents a path. When Vault mints the JWT-SVID, it prefixes the
   configured trust domain and expands the value to
   `spiffe://example.org/payments-api`.

1. Mint a JWT-SVID.

   ```shell-session
   $ JWT_SVID=$(vault write -format=json \
       spiffe/role/workload/mintjwt \
       audience=example-relying-party | jq -r '.data.token') \
       && echo $JWT_SVID
   ```

1. Review the JWT claims.
   
   ```shell-session
   $ echo "$JWT_SVID" | cut -d. -f2 | tr '_-' '/+' | \
      awk '{ while (length($0) % 4) $0 = $0 "="; print }' | \
      base64 -d 2>/dev/null | jq .
   ```
   
   The SVID includes `sub` set to `spiffe://example.org/payments-api`, plus
   `iss`, `aud`, `iat`, `exp`, and `vault.entity.id`.

   **Example output:**

   <CodeBlockConfig hideClipboard>

   ```json
   {
     "aud": [
       "example-relying-party"
     ],
     "exp": 1786629520,
     "iat": 1786629220,
     "iss": "http://0.0.0.0:8200/v1/spiffe",
     "nbf": 1786629220,
     "sub": "spiffe://example.org/payments-api",
     "vault": {
       "entity": {
         "id": ""
       }
     }
   }
   ```

   </CodeBlockConfig>

1. Review the secrets engine OIDC configuration.

   ```shell-session
   $ curl -s $VAULT_ADDR/v1/spiffe/.well-known/openid-configuration | jq .
   ```

   **Example output:**

   <CodeBlockConfig hideClipboard>

   ```json
   {
     "issuer": "http://0.0.0.0:8200/v1/spiffe",
     "jwks_uri": "http://0.0.0.0:8200/v1/spiffe/.well-known/keys",
     "response_types_supported": [
       "id_token"
     ],
     "subject_types_supported": [
       "public"
     ],
     "id_token_signing_alg_values_supported": [
       "RS256",
       "RS384",
       "RS512",
       "ES256",
       "ES384",
       "ES512"
     ]
   }
   ```

   </CodeBlockConfig>

   The OIDC discovery document includes metadata about the issuer such as the
   issuer URL, where to find the keys (`jwks_uri`), and which signing algorithms
   are supported. An OIDC-aware client fetches the discovery document first to
   determine how to validate tokens from this issuer.

1. Review the secrets engine published keys.

   ```shell-session
   $ curl -s $VAULT_ADDR/v1/spiffe/.well-known/keys | jq .
   ```

## Log in with the JWT-SVID

To see the JWT-SVID accepted by something other than Vault, run
[Grafana](https://grafana.com/oss/grafana/) with its built-in JWT auth
pointed at the engine's JWKS endpoint. Grafana's JWT auth needs only a JWKS
URL.

<Note>

This example configuration is not suitable for a production deployment.

</Note>

1. Write the JWKS keys from Vault to a file.

   ```shell-session
   $ curl -s $VAULT_ADDR/v1/spiffe/.well-known/keys | tee jwks.json | jq .
   ```

   Grafana requires HTTPS for `jwk_set_url`. This step allows you to start
   Grafana by providing the file directly. In a production environment, you would
   do this over a TLS connection directly to Vault.

1. Start Grafana.

    ```shell-session
    $ docker run -d --name grafana -p 3000:3000 \
        -v "$(pwd)/jwks.json:/etc/grafana/jwks.json:ro" \
        -e "GF_AUTH_JWT_ENABLED=true" \
        -e "GF_AUTH_JWT_HEADER_NAME=X-JWT-Assertion" \
        -e "GF_AUTH_JWT_JWK_SET_FILE=/etc/grafana/jwks.json" \
        -e "GF_AUTH_JWT_USERNAME_CLAIM=sub" \
        -e "GF_AUTH_JWT_AUTO_SIGN_UP=true" \
        grafana/grafana-oss:latest
    ```

1. Log into Grafana with the SVID minted by Vault.

   ```shell-session
   $ curl -H "X-JWT-Assertion: $JWT_SVID" http://localhost:3000/api/user | jq
   ```

   Grafana accepts the JWT-SVID as a valid credential. A successful response
   returns the logged-in user, with `login` set to the SPIFFE ID from the `sub`
   claim.

   **Example output:**

   <CodeBlockConfig hideClipboard>

   ```json
   {
     "id": 2,
     "uid": "ffv2e0k8lrpq8e",
     "email": "spiffe://example.org/payments-api",
     "name": "",
     "login": "spiffe://example.org/payments-api",
     "theme": "",
     "orgId": 1,
     "isGrafanaAdmin": false,
     "isDisabled": false,
     "isExternal": true,
     "isExternallySynced": true,
     "isGrafanaAdminExternallySynced": false,
     "authLabels": [
       "JWT"
     ],
     "updatedAt": "2026-08-13T14:28:22Z",
     "createdAt": "2026-08-13T14:28:22Z",
     "avatarUrl": "/avatar/c63487a5cd574fa9137173ec4d919b56",
     "isProvisioned": false
   }
   ```

   </CodeBlockConfig>

   The output shows that Grafana maps the `sub` claim from your JWT-SVID to the
   `email` and `login` fields. Grafana verifies the signature against the JWKS and
   then applies `user_claim=sub` to pull the identity from the `JWT_SVID` token
   that you passed in the `X-JWT-Assertion` header.
