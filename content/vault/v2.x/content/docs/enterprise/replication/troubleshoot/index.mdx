# Troubleshoot replication

@include 'alerts/enterprise-and-hcp.mdx'

Most replication problems fall into one of four groups: the clusters cannot
reach each other, bootstrapping or a token fails, a secondary cannot catch up,
or replication is slower than the workload needs. Start with the [replication
status](/vault/docs/enterprise/replication/monitor) on the secondary. The
`connection_state` and `state` fields narrow down the cause.

## Find the cause

Match the symptom you see to a troubleshooting page:

| Symptom | Refer to |
| --- | --- |
| `connection_state` is not `ready`, or the log shows `failed to connect to primary` | [A secondary cannot connect to the primary](/vault/docs/enterprise/replication/troubleshoot/connection#a-secondary-cannot-connect-to-the-primary) |
| Connection refused errors after the primary changes leader | [A secondary loses the primary after a leader change](/vault/docs/enterprise/replication/troubleshoot/connection#a-secondary-loses-the-primary-after-a-leader-change) |
| `state` is `idle` and the log shows `a local (non-replicated) mount already exists` | [A shared mount conflicts with a local mount](/vault/docs/enterprise/replication/troubleshoot/connection#a-shared-mount-conflicts-with-a-local-mount) |
| Bootstrap fails with `tls: internal error` | [Bootstrap fails with tls internal error](/vault/docs/enterprise/replication/troubleshoot/bootstrap#bootstrap-fails-with-tls-internal-error) |
| Bootstrap fails with `tls: handshake failure` | [Bootstrap fails with tls handshake failure](/vault/docs/enterprise/replication/troubleshoot/bootstrap#bootstrap-fails-with-tls-handshake-failure) |
| `error unwrapping secondary token` | [Error unwrapping secondary token](/vault/docs/enterprise/replication/troubleshoot/bootstrap#error-unwrapping-secondary-token) |
| `x509: certificate signed by unknown authority` | [Certificate signed by unknown authority](/vault/docs/enterprise/replication/troubleshoot/bootstrap#certificate-signed-by-unknown-authority) |
| `Bad Request`, or an invalid or expired activation token | [The secondary activation token is rejected](/vault/docs/enterprise/replication/troubleshoot/bootstrap#the-secondary-activation-token-is-rejected) |
| A DR operation fails with a root token | [A DR secondary operation rejects the token](/vault/docs/enterprise/replication/troubleshoot/bootstrap#a-dr-secondary-operation-rejects-the-token) |
| `state` stays `merkle-sync`, or cycles between `merkle-diff`, `merkle-sync`, and `stream-wals` | [Merkle sync loops](/vault/docs/enterprise/replication/troubleshoot/merkle-sync) |
| The log suggests a reindex | [Reindex replication](/vault/docs/enterprise/replication/troubleshoot/merkle-sync#reindex-replication) |
| `corrupted_merkle_tree` is `true`, or Merkle syncs never resolve | [Merkle tree corruption](/vault/docs/enterprise/replication/troubleshoot/merkle-tree-corruption) |
| Secondaries fall behind under load | [Tune replication](/vault/docs/enterprise/replication/troubleshoot/tune) |

## Collect information

Before you change anything, collect the following from both clusters:

- The output of `vault read -format=json sys/replication/status`.
- The Vault operational logs from the active node of each cluster. Set
  [`log_level`](/vault/docs/configuration#log_level) to `debug` on the
  secondary for more replication detail.
- The replication metrics described in [Monitor
  replication](/vault/docs/enterprise/replication/monitor#monitor-with-telemetry).

If you open a support case, include this information.
