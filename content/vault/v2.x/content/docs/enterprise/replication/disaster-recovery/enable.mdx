# Enable DR replication

@include 'alerts/enterprise-and-hcp.mdx'

Enable disaster recovery (DR) replication between two Vault Enterprise
clusters so the secondary keeps a warm standby copy of the primary. To learn
what DR replication does and what to plan first, refer to [Disaster recovery
replication](/vault/docs/enterprise/replication/disaster-recovery).

For a guided lab, complete the [Enable disaster recovery
replication](/vault/tutorials/disaster-recovery/enable-dr-replication)
tutorial.

## Before you start

@include 'replication/before-you-start-clusters.mdx'

- **Check your permissions**. Run every command from the root namespace. On the
  primary, you must have permission to:
  - `create` and `update` on `sys/replication/dr/primary/enable`
  - `create`, `update`, and `sudo` on `sys/replication/dr/primary/secondary-token`

  On the secondary, you must have permission to:
  - `create` and `update` on `sys/replication/dr/secondary/enable`
  - `create` and `update` on `sys/replication/dr/secondary/generate-public-key`,
    if you activate with a public key

## Step 1: Enable DR replication on the primary

Run the following command on the primary cluster. The cluster is briefly
unavailable while Vault enables replication.

If a load balancer fronts the primary's cluster port, set
`primary_cluster_addr` to the load balancer address so that secondaries receive
that address in their activation tokens.

<Tabs>
<Tab heading="CLI" group="cli">

```shell-session
$ vault write -force sys/replication/dr/primary/enable
```

With a load balancer address:

```shell-session
$ vault write sys/replication/dr/primary/enable \
    primary_cluster_addr="https://<load-balancer-address>:8201"
```

</Tab>
<Tab heading="API" group="api">

```shell-session
$ curl \
    --header "X-Vault-Token: $VAULT_TOKEN" \
    --request POST \
    --data '{}' \
    $VAULT_ADDR/v1/sys/replication/dr/primary/enable
```

</Tab>
</Tabs>

Parameters:

- `primary_cluster_addr` `(string: "")`: The cluster address that the primary
  gives to secondaries. Refer to [Enable DR primary
  replication](/vault/api-docs/system/replication/replication-dr#enable-dr-primary-replication).

## Step 2: Generate a secondary activation token

Generate the token with the method you chose. The `id` value names the
secondary. It must be unique, and you use it later to revoke the secondary's
access. The token expires after the `ttl`, 30 minutes by default, and works once.

<Tabs>
<Tab heading="Wrapping token" group="wrapping-token">

Run the following command on the primary cluster:

<Tabs>
<Tab heading="CLI" group="cli">

```shell-session
$ vault write -format=json sys/replication/dr/primary/secondary-token \
    id="<secondary-id>"
```

The activation token is the `wrap_info.token` value in the response.

</Tab>
<Tab heading="API" group="api">

```shell-session
$ curl \
    --header "X-Vault-Token: $VAULT_TOKEN" \
    --request POST \
    --data '{"id": "<secondary-id>"}' \
    $VAULT_ADDR/v1/sys/replication/dr/primary/secondary-token
```

</Tab>
</Tabs>

</Tab>
<Tab heading="Public key" group="public-key">

<Tabs>
<Tab heading="CLI" group="cli">

1. Run the following command on the secondary cluster to generate its public
   key:

   ```shell-session
   $ vault write -force sys/replication/dr/secondary/generate-public-key
   ```

1. Run the following command on the primary cluster, with the public key from
   the secondary:

   ```shell-session
   $ vault write sys/replication/dr/primary/secondary-token \
       id="<secondary-id>" \
       secondary_public_key="<public-key>"
   ```

</Tab>
<Tab heading="API" group="api">

1. Run the following command on the secondary cluster to generate its public
   key:

   ```shell-session
   $ curl \
       --header "X-Vault-Token: $VAULT_TOKEN" \
       --request POST \
       $VAULT_ADDR/v1/sys/replication/dr/secondary/generate-public-key
   ```

1. Run the following command on the primary cluster, with the public key from
   the secondary:

   ```shell-session
   $ curl \
       --header "X-Vault-Token: $VAULT_TOKEN" \
       --request POST \
       --data '{"id": "<secondary-id>", "secondary_public_key": "<public-key>"}' \
       $VAULT_ADDR/v1/sys/replication/dr/primary/secondary-token
   ```

</Tab>
</Tabs>

</Tab>
</Tabs>

Parameters:

- `id` `(string: <required>)`: An opaque identifier for the secondary.
- `ttl` `(string: "30m")`: How long the activation token stays valid.
- `secondary_public_key` `(string: "")`: The secondary's public key. When you
  set it, the primary encrypts the activation token with the key instead of
  wrapping it.

Refer to [Generate DR secondary
token](/vault/api-docs/system/replication/replication-dr#generate-dr-secondary-token)
and [Generate DR secondary public
key](/vault/api-docs/system/replication/replication-dr#generate-dr-secondary-public-key).

## Step 3: Enable DR replication on the secondary

<Warning> 

This step immediately deletes all data on the secondary cluster.

</Warning>

Run the following command on the secondary cluster with the activation token
from step 2:

<Tabs>
<Tab heading="CLI" group="cli">

```shell-session
$ vault write sys/replication/dr/secondary/enable token="<activation-token>"
```

</Tab>
<Tab heading="API" group="api">

```shell-session
$ curl \
    --header "X-Vault-Token: $VAULT_TOKEN" \
    --request POST \
    --data '{"token": "<activation-token>"}' \
    $VAULT_ADDR/v1/sys/replication/dr/secondary/enable
```

</Tab>
</Tabs>

Parameters:

- `token` `(string: <required>)`: The secondary activation token.
- `primary_api_addr` `(string: "")`: The primary's API address. Set it when the
  address in the token is not reachable from the secondary, for example behind a
  load balancer.
- `ca_file` `(string: "")`: Path to a PEM-format CA file that the secondary uses
  to verify the primary's API certificate when it unwraps the token. Applies to
  the wrapping token method.
- `ca_path` `(string: "")`: Path to a directory of PEM-format CA files, for the
  same purpose as `ca_file`.

If you do not set `ca_file` or `ca_path`, the secondary uses the system CA
roots. Refer to [Enable DR
secondary](/vault/api-docs/system/replication/replication-dr#enable-dr-secondary).

After this step, the secondary uses the primary's unseal or recovery keys, and
its previous root token stops working. Requests to most paths on the secondary
return `path disabled in replication DR secondary mode`.

## Step 4: Verify the replication status

Read the DR replication status on the secondary cluster. The status endpoint
does not need a token.

<Tabs>
<Tab heading="CLI" group="cli">

```shell-session
$ vault read -format=json sys/replication/dr/status
```

</Tab>
<Tab heading="API" group="api">

```shell-session
$ curl $VAULT_ADDR/v1/sys/replication/dr/status
```

</Tab>
</Tabs>

Replication works when the secondary shows the following values:

- `mode` is `secondary`.
- `connection_state` is `ready`.
- `state` is `stream-wals`. A new secondary can show `merkle-diff` or
  `merkle-sync` briefly while it copies the initial data.
- `known_primary_cluster_addrs` lists the cluster address of the primary.
- `cluster_id` matches the `cluster_id` on the primary.

On the primary, the same endpoint shows `mode` as `primary`, `state` as
`running`, and the secondary in `secondaries` with `connection_status` as
`connected`. Refer to [Monitor
replication](/vault/docs/enterprise/replication/monitor) for every field.

If a step fails, refer to [Troubleshoot
replication](/vault/docs/enterprise/replication/troubleshoot).
