# DR operation tokens

@include 'alerts/enterprise-and-hcp.mdx'

A DR operation token authorizes disaster recovery (DR) operations on a DR
secondary cluster, such as promoting the cluster or changing its primary. You
generate it on the DR secondary from a quorum of unseal or recovery keys, the
same way you generate a root token. Treat it like a root token: generate it when
you need it, and delete it soon after.

For a hands-on walkthrough, complete the [Prepare for DR
failover](/vault/tutorials/disaster-recovery/prepare-dr-failover) tutorial.

## Key holders

The key shares come from the primary cluster. When you enable replication,
Vault replaces the secondary's seal or recovery configuration and keys with the
primary's. Clusters that use auto-unseal have recovery keys instead of unseal
keys. Refer to [Seals and key
holders](/vault/docs/enterprise/replication#seals-and-key-holders).

## Operations that need a DR operation token

The following DR secondary endpoints take a `dr_operation_token` parameter:

| Endpoint | API reference |
| --- | --- |
| `/sys/replication/dr/secondary/promote` | [Promote DR secondary](/vault/api-docs/system/replication/replication-dr#promote-dr-secondary) |
| `/sys/replication/dr/secondary/update-primary` | [Update DR secondary's primary](/vault/api-docs/system/replication/replication-dr#update-dr-secondary-s-primary) |
| `/sys/replication/dr/secondary/disable` | [Disable DR secondary](/vault/api-docs/system/replication/replication-dr#disable-dr-secondary) |
| `/sys/replication/dr/secondary/reindex` | [Reindex replication](/vault/api-docs/system/replication/replication-dr#reindex-replication) |
| `/sys/replication/dr/secondary/merkle-check` | [Merkle check](/vault/api-docs/system/replication/replication-dr#sys-replication-dr-secondary-merkle-check) |
| `/sys/replication/dr/secondary/operation-token/delete` | [Delete DR operation token](/vault/api-docs/system/replication/replication-dr#delete-dr-operation-token) |

A root token does not replace the DR operation token on these endpoints.

## Tokens that authenticate token generation

The `generate-operation-token` endpoints create a DR operation token. Vault
2.0.0 and later require a valid Vault token on every call to these endpoints,
in addition to the unseal or recovery key share. This applies to starting an
attempt, reading progress, canceling, and submitting each key share. The
requirement stops attackers from sending bogus key shares to block a legitimate
attempt. Refer to [Previously unauthenticated endpoints require
authentication](/vault/docs/updates/important-changes#sys-endpoint-auth).

A DR secondary accepts only the following tokens on these endpoints:

| Token | Where you create it |
| --- | --- |
| Batch token | On the primary cluster. |
| DR operation token | On the DR secondary, with the `generate-operation-token` endpoints. |
| Root token | On the primary cluster. Vault 2.0.0 and later accept it on a DR secondary. Refer to [DR secondaries now accept root tokens from the primary](/vault/docs/updates/important-changes#root-token-secondary). |

The token authenticates the request. It is not the DR operation token that the
request generates. Each key holder who submits a share must provide a valid
token.

## Prepare before a failover

You need an authenticating token on the DR secondary at the moment you fail
over, often when the primary is down. Create it on the primary ahead of time:

- Write a policy that grants the `generate-operation-token` paths and the DR
  operations you plan to run. The policy needs `create`, `read`, `update`, and
  `delete` on `sys/replication/dr/secondary/generate-operation-token/attempt`,
  and `create` and `update` on
  `sys/replication/dr/secondary/generate-operation-token/update`.
- Create a [batch token](/vault/docs/concepts/tokens#batch-tokens) with that
  policy on the primary. The DR secondary accepts it, including when the primary
  is down.
- Set a TTL long enough to cover the time until you replace the token, and
  replace it before it expires. A batch token cannot be renewed.
- Store the token where the people who run a failover can reach it during an
  outage.

If no valid token is available during an outage, refer to [Generate a token
without authentication](#generate-a-token-without-authentication).

## Generate a DR operation token

Call the endpoints from the root namespace. If you use the `VAULT_NAMESPACE`
environment variable, unset it first.

| Action | API |
| --- | --- |
| Start an attempt | [`POST /sys/replication/dr/secondary/generate-operation-token/attempt`](/vault/api-docs/system/replication/replication-dr#start-token-generation) |
| Read progress | [`GET /sys/replication/dr/secondary/generate-operation-token/attempt`](/vault/api-docs/system/replication/replication-dr#read-generation-progress) |
| Cancel the attempt | [`DELETE /sys/replication/dr/secondary/generate-operation-token/attempt`](/vault/api-docs/system/replication/replication-dr#cancel-generation) |
| Submit a key share | [`POST /sys/replication/dr/secondary/generate-operation-token/update`](/vault/api-docs/system/replication/replication-dr#provide-key-share-to-generate-token) |

The [`vault operator generate-root`](/vault/docs/commands/operator/generate-root)
command with the `-dr-token` flag runs the same process. Use `-init` to start,
`-nonce` to submit a share, and `-decode` with `-otp` to decode the final token.

Each attempt has a nonce and a one-time password (OTP):

- **Nonce:** Share the nonce with every key holder. Each holder submits a key
  share with it.
- **OTP:** Keep the OTP with the person who started the attempt. Vault returns
  the final token encoded with the OTP, and only the OTP decodes it. If you
  provide a PGP key instead, Vault encrypts the token with it.

Only one attempt can run at a time. Cancel the current attempt before you start
another with a different OTP or PGP key.

For step-by-step instructions, refer to [Regenerate a Vault root
token](/vault/docs/troubleshoot/generate-root-token), which uses the same
process for root tokens.

## Delete a DR operation token

A DR operation token has no TTL. It stays valid until you delete it. Delete it
with the [delete DR operation
token](/vault/api-docs/system/replication/replication-dr#delete-dr-operation-token)
endpoint when you finish the operation. On Vault 2.0.0 and later, the delete
request also needs one of the tokens in [Tokens that authenticate token
generation](#tokens-that-authenticate-token-generation).

## Generate a token without authentication

If no valid token is available, you can allow unauthenticated access to the
`generate-operation-token` endpoints. Use this option only as a last resort.

Add `generate-operation-token` to the
[`enable_unauthenticated_access`](/vault/docs/configuration#enable_unauthenticated_access)
parameter in the Vault server configuration:

```hcl
enable_unauthenticated_access = ["generate-operation-token"]
```

Vault reloads this parameter when it receives a `SIGHUP` signal, so you do not
need to restart the server. After you generate the token, remove the parameter
and send `SIGHUP` again.

<Warning>

Unauthenticated access reopens the exposure that Vault 2.0.0 closed. Anyone who
can reach the endpoints can send bogus key shares and block a legitimate
attempt. Keep the window as short as possible: enable, generate, remove, and
reload.

</Warning>

For a walkthrough, complete the [Perform a break glass DR
promotion](/vault/tutorials/disaster-recovery/break-glass-failover) tutorial.
