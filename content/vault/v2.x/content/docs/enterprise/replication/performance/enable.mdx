# Enable performance replication

@include 'alerts/enterprise-and-hcp.mdx'

Enable performance replication between two Vault Enterprise clusters so the
secondary serves client requests with data from the primary. To learn what
performance replication does and what to plan first, refer to [Performance
replication](/vault/docs/enterprise/replication/performance).

For a guided lab, complete the [Enable performance
replication](/vault/tutorials/enterprise/performance-replication) tutorial.

## Before you start

@include 'replication/before-you-start-clusters.mdx'

## Step 1: Enable performance replication on the primary

Run the following command on the primary cluster.

If a load balancer fronts the primary's cluster port, set
`primary_cluster_addr` to the load balancer address so that secondaries receive
that address in their activation tokens. If you do not set it, the primary uses
its configured `cluster_addr`.

<Tabs>
<Tab heading="CLI" group="cli">

```shell-session
$ vault write -force sys/replication/performance/primary/enable

WARNING! The following warnings were returned from Vault:

  * This cluster is being enabled as a primary for replication. Vault will be
  unavailable for a brief period and will resume service shortly.
```

With a load balancer address:

```shell-session
$ vault write sys/replication/performance/primary/enable \
    primary_cluster_addr="https://<load-balancer-address>:8201"
```

</Tab>
<Tab heading="API" group="api">

```shell-session
$ curl \
    --header "X-Vault-Token: $VAULT_TOKEN" \
    --request POST \
    --data '{}' \
    $VAULT_ADDR/v1/sys/replication/performance/primary/enable
```

**Example output:**

<CodeBlockConfig hideClipboard>

```json

  "lease_id": "",
```

Parameters:

- `primary_cluster_addr` `(string: "")`: The cluster address that the primary
  gives to secondaries. Refer to [Enable performance primary
  replication](/vault/api-docs/system/replication/replication-performance#enable-performance-primary-replication).

## Step 2: Generate a secondary activation token

Generate the token with the method you chose. The `id` value names the
secondary. It must be unique. Use the same value later to set path filters and
to revoke the secondary's access. The token expires after the `ttl`, 30 minutes
by default, and works once.

<Tabs>

Run the following command on the primary cluster:

Parameters:

- `id` `(string: <required>)`: An opaque identifier for the secondary.
- `ttl` `(string: "30m")`: How long the activation token stays valid.
- `secondary_public_key` `(string: "")`: The secondary's public key. When you
  set it, the primary encrypts the activation token with the key instead of
  wrapping it.

Refer to [Generate performance secondary
token](/vault/api-docs/system/replication/replication-performance#generate-performance-secondary-token)
and [Fetch performance secondary public
key](/vault/api-docs/system/replication/replication-performance#fetch-performance-secondary-public-key).

## Step 3: Enable performance replication on the secondary

<Warning>

This step immediately deletes all data on the secondary cluster.

</Warning>

Run the following command on the secondary cluster with the activation token
from step 2:

<Tabs>
<Tab heading="CLI" group="cli">

```shell-session
$ vault write sys/replication/performance/secondary/enable \
    token="<activation-token>"
```

**Example output:**

<CodeBlockConfig hideClipboard>

```plaintext
WARNING! The following warnings were returned from Vault:

  * Vault has successfully found secondary information; it may take a while to
  perform setup tasks. Vault will be unavailable until these tasks and initial
  sync complete.
```

</CodeBlockConfig>

</Tab>
<Tab heading="API" group="api">

```shell-session
$ curl \
    --header "X-Vault-Token: $VAULT_TOKEN" \
    --request POST \
    --data '{"token": "<activation-token>"}' \
    $VAULT_ADDR/v1/sys/replication/performance/secondary/enable
```

**Example output:**

<CodeBlockConfig hideClipboard>

```json
{
  "request_id": "e0de688d-d6b4-24f6-6a76-83defae41e75",
  "lease_id": "",
  "renewable": false,
  "lease_duration": 0,
  "data": null,
  "wrap_info": null,
  "warnings": [
    "Vault has successfully found secondary information; it may take a while to perform setup tasks. Vault will be unavailable until these tasks and initial sync complete."
  ],
  "auth": null,
  "mount_type": "system"
}
```

</CodeBlockConfig>

</Tab>
</Tabs>

Parameters:

- `token` `(string: <required>)`: The secondary activation token.
- `primary_api_addr` `(string: "")`: The primary's API address. Set it when the
  address in the token is not reachable from the secondary, for example behind a
  load balancer.
- `ca_file` `(string: "")`: Path to a PEM-format CA file that the secondary uses
  to verify the primary's API certificate when it unwraps the token. Applies to
  the wrapping token method.
- `ca_path` `(string: "")`: Path to a directory of PEM-format CA files, for the
  same purpose as `ca_file`.

If you do not set `ca_file` or `ca_path`, the secondary uses the system CA
roots. Refer to [Enable performance
secondary](/vault/api-docs/system/replication/replication-performance#enable-performance-secondary).

After this step, the secondary's previous root token stops working. Log in to
the secondary with the auth method you created on the primary.

## Step 5: Enable an auth method

Enabling performance replication on the secondary deletes all of its data,
including its original root token. Tokens do not replicate between performance
clusters, so you need an auth method to authenticate to each secondary. Create
the auth method, policy, and user on the primary.

This example uses the `userpass` auth method for simplicity.

<Tabs>
<Tab heading="CLI" group="cli">

1. Enable the userpass auth method on the primary:

   ```shell-session
   $ vault auth enable userpass
   ```

1. Create a policy on the primary for the operations you run on the secondary:

   ```shell-session
   $ vault policy write pr-admin - <<EOF
   path "sys/replication/performance/*" {
     capabilities = ["create", "read", "update", "delete", "sudo"]
   }

   path "sys/mounts" {
     capabilities = ["read"]
   }
   EOF
   ```

1. Create a user on the primary and attach the policy:

   ```shell-session
   $ vault write auth/userpass/users/<user> \
       password="<password>" \
       token_policies="pr-admin"
   ```

1. Authenticate to the secondary as that user:

   ```shell-session
   $ VAULT_ADDR=<secondary-address> vault login -method=userpass username=<user>
   ```

</Tab>
<Tab heading="API" group="api">

1. Enable the userpass auth method on the primary:

   ```shell-session
   $ curl \
       --header "X-Vault-Token: $VAULT_TOKEN" \
       --request POST \
       --data '{"type": "userpass"}' \
       $VAULT_ADDR/v1/sys/auth/userpass
   ```

1. Write the policy for the operations you run on the secondary to a file:

   ```shell-session
   $ cat > pr-admin.hcl <<EOF
   path "sys/replication/performance/*" {
     capabilities = ["create", "read", "update", "delete", "sudo"]
   }

   path "sys/mounts" {
     capabilities = ["read"]
   }
   EOF
   ```

1. Create the policy on the primary from the file:

   ```shell-session
   $ curl \
       --header "X-Vault-Token: $VAULT_TOKEN" \
       --request POST \
       --data "$(jq -n --rawfile policy pr-admin.hcl '{policy: $policy}')" \
       $VAULT_ADDR/v1/sys/policies/acl/pr-admin
   ```

1. Create a user on the primary and attach the policy:

   ```shell-session
   $ curl \
       --header "X-Vault-Token: $VAULT_TOKEN" \
       --request POST \
       --data '{"password": "<password>", "token_policies": ["pr-admin"]}' \
       $VAULT_ADDR/v1/auth/userpass/users/<user>
   ```

1. Authenticate to the secondary as that user:

   ```shell-session
   $ curl \
       --request POST \
       --data '{"password": "<password>"}' \
       <secondary-address>/v1/auth/userpass/login/<user>
   ```

   The token is the `auth.client_token` value in the response.

</Tab>
</Tabs>

The policy grants every performance replication path. Narrow it to the
endpoints your operators call.


## Step 6: (Optional) Set a path filter

Set a path filter on the primary to control which mounts and namespaces
replicate to this secondary. Use the secondary's `secondary_id` value from step
4 as the last part of the path.

For secrets engines, use the mount path. For example, `database`.
For auth methods, prefix the mount path with `auth/`. For example,
`auth/userpass`.

<Tabs>
<Tab heading="CLI" group="cli">

```shell-session
$ vault write sys/replication/performance/primary/paths-filter/<secondary-id> \
    mode="deny" \
    paths="<mount-path>"
```

**Example output:**

<CodeBlockConfig hideClipboard>

```plaintext
Success! Data written to: sys/replication/performance/primary/paths-filter/pr-secondary
```

</CodeBlockConfig>

</Tab>
<Tab heading="API" group="api">

1. Send a `POST` request to the `paths-filter` endpoint on the primary cluster to
   create or replace the path filter for the secondary.

   ```shell-session
   $ curl \
       --header "X-Vault-Token: $VAULT_TOKEN" \
       --request POST \
       ---data '{"mode": "deny", "paths": ["<path-1>", "<path-2>"]}' \
       $VAULT_ADDR/v1/sys/replication/performance/primary/paths-filter/<secondary-id>
   ```

   This API call does not return any output.

1. Send a `GET` request to the `paths-filter` endpoint on the primary cluster to
   read the current path filter for the secondary.

   ```shell-session
   $ curl --header "X-Vault-Token: $VAULT_TOKEN" \
        $VAULT_ADDR/v1/sys/replication/performance/primary/paths-filter/<secondary-id>
   ```
   
   **Example output:**
   
   <CodeBlockConfig hideClipboard>
   
   ```json
   {
     "request_id": "86a46c77-8209-ac2f-3cfa-0ab3b5b343b6",
     "lease_id": "",
     "renewable": false,
     "lease_duration": 0,
     "data": {
       "mode": "deny",
       "paths": [
         "<mount-path>/"
       ]
     },
     "wrap_info": null,
     "warnings": null,
     "auth": null,
     "mount_type": "system"
   }
   ```

   </CodeBlockConfig>

</Tab>
</Tabs>

Parameters:

- `mode` `(string: "allow")`: `allow` replicates only the listed paths. `deny`
  replicates everything except the listed paths.
- `paths` `(array: [])`: The mount and namespace paths to filter.

<Warning>
   
A write replaces the secondary's whole filter. Vault does not add the new paths
to the existing list. If you leave out a path that the filter denied, Vault
starts replicating that path to the secondary.

Keep the complete list of filtered paths in source control, or manage the
filter with the Terraform [`vault_generic_endpoint`](https://registry.terraform.io/providers/hashicorp/vault/latest/docs/resources/generic_endpoint)
resource, which writes the full list on every apply.
   
</Warning>

Refer to [Create paths
filter](/vault/api-docs/system/replication/replication-performance#create-paths-filter).
To confirm the filter, log in to the secondary and run `vault secrets list`
again. Filtered mounts no longer appear.

## Next steps

Finish the deployment:

- Add a DR secondary to the primary and to each performance secondary. Refer to
  [Enable DR
  replication](/vault/docs/enterprise/replication/disaster-recovery/enable).
- Configure automated snapshots on each cluster. Refer to
  [Snapshots](/vault/docs/enterprise/replication/performance#snapshots).
- Set up monitoring and alerts. Refer to [Monitor
  replication](/vault/docs/enterprise/replication/monitor).
