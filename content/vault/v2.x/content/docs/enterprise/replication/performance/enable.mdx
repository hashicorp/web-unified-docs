# Enable performance replication

@include 'alerts/enterprise-and-hcp.mdx'

Enable performance replication between two Vault Enterprise clusters so the
secondary serves client requests with data from the primary. To learn what
performance replication does and what to plan first, refer to [Performance
replication](/vault/docs/enterprise/replication/performance).

For a guided lab, complete the [Enable performance
replication](/vault/tutorials/enterprise/performance-replication) tutorial.

## Before you start

@include 'replication/before-you-start-clusters.mdx'

- **Create a way to log in to the secondary**. Enabling replication replaces the
  secondary's auth methods and policies with the primary's, and tokens do not
  replicate. Enable an auth method on the primary, such as
  [userpass](/vault/docs/auth/userpass), with a user whose policy grants the
  operations you run on the secondary.

- **Check your permissions**. Run every command from the root namespace. On the
  primary, you must have permission to:
  - `create` and `update` on `sys/replication/performance/primary/enable`
  - `create`, `update`, and `sudo` on
    `sys/replication/performance/primary/secondary-token`
  - `create` and `update` on
    `sys/replication/performance/primary/paths-filter/*`, if you set a path
    filter

  On the secondary, you must have permission to:
  - `create` and `update` on `sys/replication/performance/secondary/enable`
  - `create` and `update` on
    `sys/replication/performance/secondary/generate-public-key`, if you activate
    with a public key

## Step 1: Enable performance replication on the primary

Run the following command on the primary cluster.

If a load balancer fronts the primary's cluster port, set
`primary_cluster_addr` to the load balancer address so that secondaries receive
that address in their activation tokens. If you do not set it, the primary uses
its configured `cluster_addr`.

<Tabs>

<Tab heading="CLI" group="cli">

```shell-session
$ vault write -force sys/replication/performance/primary/enable
```

{/* Add the output from a lab run. */}

With a load balancer address:

```shell-session
$ vault write sys/replication/performance/primary/enable \
    primary_cluster_addr="https://<load-balancer-address>:8201"
```

{/* Add the output from a lab run. */}

</Tab>

<Tab heading="API" group="api">

```shell-session
$ curl \
    --header "X-Vault-Token: $VAULT_TOKEN" \
    --request POST \
    --data '{}' \
    $VAULT_ADDR/v1/sys/replication/performance/primary/enable
```

{/* Add the output from a lab run. */}

</Tab>

</Tabs>

Parameters:

- `primary_cluster_addr` `(string: "")`: The cluster address that the primary
  gives to secondaries. Refer to [Enable performance primary
  replication](/vault/api-docs/system/replication/replication-performance#enable-performance-primary-replication).

## Step 2: Generate a secondary activation token

Generate the token with the method you chose. The `id` value names the
secondary. It must be unique. Use the same value later to set path filters and
to revoke the secondary's access. The token expires after the `ttl`, 30 minutes
by default, and works once.

<Tabs>

<Tab heading="Wrapping token" group="wrapping-token">

Run the following command on the primary cluster:

```shell-session
$ vault write -format=json sys/replication/performance/primary/secondary-token \
    id="<secondary-id>"
```

{/* Add the output from a lab run. */}

The activation token is the `wrap_info.token` value in the response.

API equivalent:

```shell-session
$ curl \
    --header "X-Vault-Token: $VAULT_TOKEN" \
    --request POST \
    --data '{"id": "<secondary-id>"}' \
    $VAULT_ADDR/v1/sys/replication/performance/primary/secondary-token
```

{/* Add the output from a lab run. */}

</Tab>

<Tab heading="Public key" group="public-key">

1. Run the following command on the secondary cluster to generate its public
   key:

   ```shell-session
   $ vault write -force sys/replication/performance/secondary/generate-public-key
   ```

   {/* Add the output from a lab run, including the name of the field that holds the public key. */}

   API equivalent:

   ```shell-session
   $ curl \
       --header "X-Vault-Token: $VAULT_TOKEN" \
       --request POST \
       $VAULT_ADDR/v1/sys/replication/performance/secondary/generate-public-key
   ```

   {/* Add the output from a lab run. */}

1. Run the following command on the primary cluster, with the public key from
   the secondary:

   ```shell-session
   $ vault write sys/replication/performance/primary/secondary-token \
       id="<secondary-id>" \
       secondary_public_key="<public-key>"
   ```

   {/* Add the output from a lab run, including the name of the field that holds the activation token. */}

   API equivalent:

   ```shell-session
   $ curl \
       --header "X-Vault-Token: $VAULT_TOKEN" \
       --request POST \
       --data '{"id": "<secondary-id>", "secondary_public_key": "<public-key>"}' \
       $VAULT_ADDR/v1/sys/replication/performance/primary/secondary-token
   ```

   {/* Add the output from a lab run. */}

</Tab>

</Tabs>

Parameters:

- `id` `(string: <required>)`: An opaque identifier for the secondary.
- `ttl` `(string: "30m")`: How long the activation token stays valid.
- `secondary_public_key` `(string: "")`: The secondary's public key. When you
  set it, the primary encrypts the activation token with the key instead of
  wrapping it.

Refer to [Generate performance secondary
token](/vault/api-docs/system/replication/replication-performance#generate-performance-secondary-token)
and [Fetch performance secondary public
key](/vault/api-docs/system/replication/replication-performance#fetch-performance-secondary-public-key).

## Step 3: Enable performance replication on the secondary

!> This step immediately deletes all data on the secondary cluster.

Run the following command on the secondary cluster with the activation token
from step 2:

<Tabs>

<Tab heading="CLI" group="cli">

```shell-session
$ vault write sys/replication/performance/secondary/enable \
    token="<activation-token>"
```

{/* Add the output from a lab run. */}

</Tab>

<Tab heading="API" group="api">

```shell-session
$ curl \
    --header "X-Vault-Token: $VAULT_TOKEN" \
    --request POST \
    --data '{"token": "<activation-token>"}' \
    $VAULT_ADDR/v1/sys/replication/performance/secondary/enable
```

{/* Add the output from a lab run. */}

</Tab>

</Tabs>

Parameters:

- `token` `(string: <required>)`: The secondary activation token.
- `primary_api_addr` `(string: "")`: The primary's API address. Set it when the
  address in the token is not reachable from the secondary, for example behind a
  load balancer.
- `ca_file` `(string: "")`: Path to a PEM-format CA file that the secondary uses
  to verify the primary's API certificate when it unwraps the token. Applies to
  the wrapping token method.
- `ca_path` `(string: "")`: Path to a directory of PEM-format CA files, for the
  same purpose as `ca_file`.

If you do not set `ca_file` or `ca_path`, the secondary uses the system CA
roots. Refer to [Enable performance
secondary](/vault/api-docs/system/replication/replication-performance#enable-performance-secondary).

After this step, the secondary's previous root token stops working. Log in to
the secondary with the auth method you created on the primary.

## Step 4: Verify the replication status

Read the performance replication status on the secondary cluster. The status
endpoint does not need a token.

<Tabs>

<Tab heading="CLI" group="cli">

```shell-session
$ vault read -format=json sys/replication/performance/status
```

{/* Add the output from a lab run. */}

</Tab>

<Tab heading="API" group="api">

```shell-session
$ curl $VAULT_ADDR/v1/sys/replication/performance/status
```

{/* Add the output from a lab run. */}

</Tab>

</Tabs>

Replication works when the secondary shows the following values:

- `mode` is `secondary`.
- `connection_state` is `ready`.
- `state` is `stream-wals`. A new secondary can show `merkle-diff` or
  `merkle-sync` briefly while it copies the initial data.
- `known_primary_cluster_addrs` lists the cluster address of the primary.
- `secondary_id` matches the `id` you set in step 2.

Log in to the secondary and list the secrets engines. The list matches the
shared mounts on the primary and does not include the primary's local mounts.

```shell-session
$ vault secrets list
```

{/* Add the output from a lab run. */}

Refer to [Monitor replication](/vault/docs/enterprise/replication/monitor) for
every status field. If a step fails, refer to [Troubleshoot
replication](/vault/docs/enterprise/replication/troubleshoot).

## Step 5: Optional: Set a path filter

Set a path filter on the primary to control which mounts and namespaces
replicate to this secondary. Use the secondary's `secondary_id` value from step
4 as the last part of the path.

<Tabs>

<Tab heading="CLI" group="cli">

```shell-session
$ vault write sys/replication/performance/primary/paths-filter/<secondary-id> \
    mode="deny" \
    paths="<mount-path>"
```

{/* Add the output from a lab run. */}

</Tab>

<Tab heading="API" group="api">

```shell-session
$ curl \
    --header "X-Vault-Token: $VAULT_TOKEN" \
    --request POST \
    --data '{"mode": "deny", "paths": ["<mount-path>", "<namespace-path>"]}' \
    $VAULT_ADDR/v1/sys/replication/performance/primary/paths-filter/<secondary-id>
```

{/* Add the output from a lab run. */}

</Tab>

</Tabs>

Parameters:

- `mode` `(string: "allow")`: `allow` replicates only the listed paths. `deny`
  replicates everything except the listed paths.
- `paths` `(array: [])`: The mount and namespace paths to filter.

Refer to [Create paths
filter](/vault/api-docs/system/replication/replication-performance#create-paths-filter).
To confirm the filter, log in to the secondary and run `vault secrets list`
again. Filtered mounts no longer appear.
