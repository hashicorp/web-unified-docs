#### Issue

The Azure secrets engine does not prevent a role from targeting the same Azure
AD application that Vault uses as its own service principal. Both static roles
and dynamic roles with an explicit `application_object_id` are affected.

**Static roles**

The only validation performed on `application_object_id` during static role
creation is a call to `GetApplication`, which confirms the application exists in
Azure AD. There is no comparison of the target application against the engine's
configured `client_id`.

A Vault user with `create` permission on the `azure/static-roles/*` path can set
`application_object_id` to the object ID of Vault's own app registration. Vault
accepts this, calls the MS Graph `addPassword` API on its own application, and
stores the resulting credential. The user then reads
`azure/static-creds/<name>` to obtain a fresh `client_secret` for Vault's
service principal. Because the Azure secrets engine documentation requires
`Application.ReadWrite.All` for static roles and existing service principal
configurations, the stolen credential inherits this permission and grants the
attacker full control over application registrations in the tenant. Subsequent
Azure API calls made with the stolen credential bypass Vault's ACL system, audit
log, and rate limiting entirely.

**Dynamic roles**

A dynamic role with `application_object_id` set follows a structurally similar
but less severe path. When a user reads `azure/creds/<name>`, the engine calls
`addAppPassword` on the role's target application and returns the new password
as a short-lived Vault lease. A write-time guard (`checkRootCredentialTarget`)
blocks creating or updating such a role to target Vault's app registration.
However, the read-time handler (`pathSPRead`) contains no equivalent check, so
a role created before the guard was introduced — or one that bypassed it — can
still issue credentials against Vault's own application.

The dynamic case differs from the static case in two important ways:

- **No root credential exposure.** The issued credential is a freshly added
  application password, not Vault's stored `client_secret`. Vault continues to
  authenticate with its own stored credential.
- **Automatic revocation.** When the Vault lease expires, Vault calls
  `deleteAppPassword` to remove the credential from the Azure app registration.

Despite these mitigations, a working credential for Vault's app registration is
still produced and can be used to impersonate Vault's identity in Azure for the
duration of the lease.

#### Workaround

**Step 1: Audit for poisoned roles**

Before applying any code fix, audit your deployment for static roles that
already target Vault's own service principal. On Vault Enterprise, repeat
these steps for every namespace because each namespace can have its own
Azure secrets engine mounts.

First, identify all Azure secrets engine mounts in each namespace:

```shell-session
# List all secret engine mounts (run once per namespace)
$ vault secrets list -format=json | \
  jq -r 'to_entries[] | select(.value.type == "azure") | .key'
```

For each mount path returned above, audit both static and dynamic roles:

```shell-session
# List static roles for a given mount
$ vault list <mount>/static-roles

# For each static role, inspect its application_object_id
$ vault read <mount>/static-roles/<name>

# List dynamic roles for a given mount
$ vault list <mount>/roles

# For each dynamic role, inspect its application_object_id
$ vault read <mount>/roles/<name>

# Compare against the engine's configured client_id
$ vault read <mount>/config
```

Any static role whose `application_object_id` resolves to the engine's own
Azure app registration must be deleted immediately:

```shell-session
$ vault delete <mount>/static-roles/<name>
```

After deleting a static role, revoke the corresponding credentials directly in
Azure AD by removing the associated application password (client secret) from
the app registration. Do not rely on Vault lease revocation for this step.

Any dynamic role whose `application_object_id` resolves to the engine's own
Azure app registration must also be deleted:

```shell-session
$ vault delete <mount>/roles/<name>
```

For dynamic roles, also revoke all active leases so that any already-issued
credentials are removed from the Azure app registration immediately rather than
waiting for lease expiry:

```shell-session
# Revoke all leases issued by the affected dynamic role
$ vault lease revoke -prefix <mount>/creds/<name>
```

**Step 2: Upgrade**

Upgrade to a patched version of the Azure secrets engine plugin once one is
available. The patch rejects static and dynamic role creation and updates that
target Vault's own application, and blocks credential reads and rotations for
any pre-existing poisoned roles.
