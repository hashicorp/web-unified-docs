#### Issue

The Azure secrets engine does not prevent a role from targeting the same Azure
AD application that Vault uses as its own service principal. Both static roles
and dynamic roles with an explicit `application_object_id` are affected.

#### Workaround

**Step 1: Audit for poisoned roles**

Before applying any code fix, audit your deployment for static roles that
already target Vault's own service principal. On Vault Enterprise, repeat
these steps for every namespace because each namespace can have its own
Azure secrets engine mounts.

First, identify all Azure secrets engine mounts in each namespace:

```shell-session
# List all secret engine mounts (run once per namespace)
$ vault secrets list -format=json | \
  jq -r 'to_entries[] | select(.value.type == "azure") | .key'
```

For each mount path returned above, audit both static and dynamic roles:

```shell-session
# List static roles for a given mount
$ vault list <mount>/static-roles

# For each static role, inspect its application_object_id
$ vault read <mount>/static-roles/<name>

# List dynamic roles for a given mount
$ vault list <mount>/roles

# For each dynamic role, inspect its application_object_id
$ vault read <mount>/roles/<name>

# Compare against the engine's configured client_id
$ vault read <mount>/config
```

Any static role whose `application_object_id` resolves to the engine's own
Azure app registration must be deleted immediately:

```shell-session
$ vault delete <mount>/static-roles/<name>
```

After deleting a static role, revoke the corresponding credentials directly in
Azure AD by removing the associated application password (client secret) from
the app registration. Do not rely on Vault lease revocation for this step.

Any dynamic role whose `application_object_id` resolves to the engine's own
Azure app registration must also be deleted:

```shell-session
$ vault delete <mount>/roles/<name>
```

For dynamic roles, also revoke all active leases so that any already-issued
credentials are removed from the Azure app registration immediately rather than
waiting for lease expiry:

```shell-session
# Revoke all leases issued by the affected dynamic role
$ vault lease revoke -prefix <mount>/creds/<name>
```

**Step 2: Upgrade**

Upgrade to a patched version of the Azure secrets engine plugin once one is
available. The patch rejects static and dynamic role creation and updates that
target Vault's own application, and blocks credential reads and rotations for
any pre-existing poisoned roles.
