The key name (`worker-controller-generated-activation-token`) must match the value set in `secretRefs.keys.controllerGeneratedActivationToken` in your Helm values file. This command is provided as an example. Use any Secret management method that fits your workflow.

Set `controller_generated_activation_token` to the exact supported `env://BOUNDARY_WORKER_CONTROLLER_GENERATED_ACTIVATION_TOKEN` reference. Save the following complete HCL and values as `worker-values.yaml`:

```yaml
secretRefs:
  secretName: boundary-worker-secrets
  validateExisting: true
  keys:
    controllerGeneratedActivationToken: worker-controller-generated-activation-token

worker:
  config: |
    disable_mlock = true

    listener "tcp" {
      address = "0.0.0.0:9202"
      purpose = "proxy"
    }

    listener "tcp" {
      address       = "0.0.0.0:9203"
      purpose       = "ops"
      tls_disable   = "{{ .Values.tls.ops.disabled }}"
      tls_cert_file = "{{ .Values.tls.mountPath }}/tls.crt"
      tls_key_file  = "{{ .Values.tls.mountPath }}/tls.key"
    }

    worker {
      name                                  = "boundary-worker"
      initial_upstreams                     = ["boundary-controller-cluster:9201"]
      auth_storage_path                     = "/var/lib/boundary"
      controller_generated_activation_token = "env://BOUNDARY_WORKER_CONTROLLER_GENERATED_ACTIVATION_TOKEN"

      tags {
        type = ["worker", "controller-led"]
      }
    }

    events {
      audit_enabled        = true
      sysevents_enabled    = true
      observations_enabled = true
      sink "stderr" {
        name        = "all-events"
        event_types = ["*"]
        format      = "cloudevents-json"
      }
    }
  persistence:
    authStorage:
      enabled: true
      size: 1Gi
      path: /var/lib/boundary
```

With `secretRefs.validateExisting: true`, the chart looks up the Secret during an install or upgrade and fails early when the Secret or configured key is missing. Client-only `helm template` rendering cannot find an in-cluster Secret, so use a cluster-connected install or upgrade to perform this validation.

<Note>

When `secretRefs.secretName` is set, the chart validates that `worker.config` uses the correct `env://` variable name for the secret-backed field. Using a different variable name causes the chart to fail during rendering before installation completes. The required name is:

- `env://BOUNDARY_WORKER_CONTROLLER_GENERATED_ACTIVATION_TOKEN` for `controller_generated_activation_token`

If you use a different variable name, the chart fails during rendering with an error message that identifies the field and the expected variable name. Hardcoding the token directly in `worker.config` when `secretRefs.secretName` is set is also rejected.

</Note>

Install the worker Helm chart:

```shell-session
$ helm install boundary-worker hashicorp/boundary-worker \
  --namespace boundary \
  --values worker-values.yaml \
  --wait
```
