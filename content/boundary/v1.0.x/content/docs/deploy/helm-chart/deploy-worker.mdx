# Deploy workers using a Helm chart

@include 'helm/worker-chart.mdx'

Deploying the worker chart gives you a data-plane worker that registers with HCP Boundary or a self-managed Boundary control plane and proxies session traffic. To deploy a control plane first, refer to [Deploy controllers using a Helm chart](/boundary/docs/deploy/helm-chart/deploy-controller).

For OpenShift-specific installation and Route configuration, refer to [Boundary OpenShift Helm charts](/boundary/docs/deploy/openshift). Do not apply OpenShift values from that guide to a standard Kubernetes installation.

## Prerequisites

Before installing the worker chart, make sure you have:

- A Kubernetes cluster running version 1.34 or later.
- Helm 3 or later with access to the cluster.
- Network connectivity from the worker to HCP Boundary or the self-managed upstream workers or controllers, and from the worker to its targets.
- Persistent storage support only if you enable the auth storage or recording PVC. The chart can use default or named dynamic provisioning. It does not provide selectors or a `volumeName` for explicitly binding a particular pre-provisioned volume.
- A registration method and valid Boundary worker HCL configuration.
- An existing ServiceAccount only if you set `serviceAccount.name`. The chart does not create one; when the value is empty, Kubernetes uses the namespace's default ServiceAccount.
- An existing TLS Secret named `boundary-worker-tls` that contains `tls.crt` and `tls.key`. Operations listener TLS is enabled by default. If you explicitly disable it, you do not need this Secret.

Worker-led and controller-led registration require persistent auth storage so worker identity survives pod replacement. KMS-backed worker authentication is supported only with self-managed Boundary and does not require persistent auth storage.

## Add the HashiCorp Helm repository

Add the repository, refresh its index, and confirm that the chart is available:

```shell-session
$ helm repo add hashicorp https://helm.releases.hashicorp.com
$ helm repo update
$ helm search repo hashicorp/boundary-worker
```

Refer to the [Boundary worker chart on Artifact Hub](https://artifacthub.io/packages/helm/hashicorp/boundary-worker/) for official releases. Refer to the [default chart values](https://artifacthub.io/packages/helm/hashicorp/boundary-worker/?modal=values) for the values included with the selected release. You can also run `helm search repo hashicorp/boundary-worker --versions` to list versions available from your configured Helm repository.

## Prepare the worker configuration

Create `worker-values.yaml`. The chart renders `worker.config` as Helm template text and mounts the resulting HCL at `/etc/boundary/boundary-worker.hcl`.

Choose exactly one control-plane connection:

- For HCP Boundary, set top-level `hcp_boundary_cluster_id` and use worker-led or controller-led registration. Do not set `initial_upstreams` or configure a worker-auth KMS stanza.
- For self-managed Boundary, set `initial_upstreams` in the `worker` stanza. Use worker-led, controller-led, or KMS-backed authentication.

The following values configure an HCP Boundary worker for worker-led registration:

```yaml
worker:
  config: |
    disable_mlock = true
    hcp_boundary_cluster_id = "<hcp-cluster-id>"

    listener "tcp" {
      address = "0.0.0.0:9202"
      purpose = "proxy"
    }

    listener "tcp" {
      address       = "0.0.0.0:9203"
      purpose       = "ops"
      tls_disable   = "{{ .Values.tls.ops.disabled }}"
      tls_cert_file = "{{ .Values.tls.mountPath }}/tls.crt"
      tls_key_file  = "{{ .Values.tls.mountPath }}/tls.key"
    }

    worker {
      public_addr       = "<reachable-host-or-ip>:9202"
      auth_storage_path = "/var/lib/boundary"

      tags {
        type = ["worker", "ingress"]
      }
    }

    events {
      audit_enabled        = true
      sysevents_enabled    = true
      observations_enabled = true
      sink "stderr" {
        name        = "all-events"
        event_types = ["*"]
        format      = "hclog-text"
      }
    }

  persistence:
    authStorage:
      enabled: true
```

Use `host:port` for `public_addr`, without a URL scheme. The address must be reachable by clients or downstream workers. If a `LoadBalancer` address is assigned after installation, use a temporary resolvable address or update this same values file after the address is known.

For a self-managed control plane, remove `hcp_boundary_cluster_id` and add an upstream to the `worker` stanza:

```hcl
worker {
  name              = "boundary-worker"
  public_addr       = "boundary-worker.example.com:9202"
  initial_upstreams = ["boundary-controller-cluster:9201"]
  auth_storage_path = "/var/lib/boundary"
}
```

Refer to [Worker Helm chart examples](/boundary/docs/deploy/helm-chart/worker-examples) for self-managed topologies; worker-led, controller-led, and KMS-backed registration; stable DNS; session recording storage; and proxy-port changes.

Create the default operations TLS Secret before you install the chart:

```shell-session
$ kubectl create namespace boundary
$ kubectl create secret tls boundary-worker-tls \
  --namespace boundary \
  --cert=worker-ops.crt \
  --key=worker-ops.key
```

The certificate must be valid for clients that connect to the operations endpoint. To run the operations listener without TLS instead, set `tls.ops.disabled=true` and keep `tls_disable = "{{ .Values.tls.ops.disabled }}"` in the listener. The chart then uses HTTP probes and does not mount the TLS Secret.

## Install a Boundary worker

Render and inspect the resources before installing. This catches rendered configuration and TLS-alignment errors without changing the cluster. A client-only render cannot validate the existence of a Secret through Helm's `lookup`:

```shell-session
$ helm template boundary-worker hashicorp/boundary-worker \
  --namespace boundary \
  --values worker-values.yaml
```

Install using the same values file:

```shell-session
$ helm install boundary-worker hashicorp/boundary-worker \
  --namespace boundary \
  --create-namespace \
  --values worker-values.yaml \
  --wait
```

The chart always creates `<fullname>-proxy` and `<fullname>-ops` Services. For the default release name these are `boundary-worker-proxy` and `boundary-worker-ops`.

## Verify the deployment

Check the targeted worker resources and logs:

```shell-session
$ kubectl get deployment/boundary-worker-deployment \
  service/boundary-worker-proxy service/boundary-worker-ops \
  --namespace boundary
$ kubectl get pods,pvc --namespace boundary \
  --selector app.kubernetes.io/instance=boundary-worker
$ kubectl logs --namespace boundary deployment/boundary-worker-deployment
```

Confirm that the pod is Ready, logs show successful registration or the expected worker-led activation token, and the worker becomes active in Boundary. If you enabled either PVC, confirm that each enabled claim is Bound. The auth and recording claims are named `boundary-worker-auth-storage` and `boundary-worker-recording-storage` unless `fullnameOverride` changes the prefix. `nameOverride` changes the application-name label, not this resource prefix.

## Update `public_addr` for workers

Kubernetes may assign the external hostname or IP after installation when `worker.service.proxy.type` is `LoadBalancer`. If `worker.service.proxy.type` is `ClusterIP`, use a cluster-reachable address when the worker is accessed internally.

Use the following command to watch the proxy Service:

```shell-session
$ kubectl get svc boundary-worker-proxy --namespace boundary --watch
```

If the worker HCL needs the final address, update the `public_addr` field in `worker.config` or in the HCL file with the `LoadBalancer` address or internal `ClusterIP` address, then upgrade the release:

```shell-session
$ helm upgrade boundary-worker hashicorp/boundary-worker \
  --namespace boundary \
  --values worker-values.yaml \
  --rollback-on-failure \
  --wait
```

## Uninstall the worker

```shell-session
$ helm uninstall boundary-worker --namespace boundary
```

## Troubleshooting

### Worker does not become active

For HCP Boundary, verify `hcp_boundary_cluster_id` and registration authorization. For self-managed Boundary, verify `initial_upstreams`, registration settings, and network access to the upstream address. For token-based registration, verify that auth storage is enabled and mounted at the path configured by `auth_storage_path`.

### Health probes fail

The Deployment's ops container port and probes use port `9203`. Keep the ops listener on `0.0.0.0:9203` and `worker.service.ops.targetPort` at `9203`. Changing only the Service-facing `worker.service.ops.port` is supported. Probe HTTP or HTTPS is derived from `tls.ops.disabled`; make sure that value agrees with the ops listener and TLS certificate paths.

With the default `tls.ops.disabled=false`, confirm that the `boundary-worker-tls` Secret exists in the release namespace and contains `tls.crt` and `tls.key`. The probes use HTTPS and the pod cannot start until Kubernetes can mount the Secret.
