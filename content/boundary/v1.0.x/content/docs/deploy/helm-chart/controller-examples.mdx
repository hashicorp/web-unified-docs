# Controller Helm chart examples

Use these controller configuration variations: TLS setup, database migration, bootstrap admin creation, and cluster service exposure, to adapt the baseline installation in [Deploy controllers](/boundary/docs/deploy/helm-chart/deploy-controller) to your environment. Start with the baseline workflow and apply only the variations you need while preparing your values file. The examples assume PostgreSQL and KMS (key management system) access already exist.

## Create the controller Secret

Follow [Create the controller Secret](/boundary/docs/deploy/helm-chart/deploy-controller#create-the-controller-secret) to create the baseline Secret. Add the `migration-url` key only when `controller.config` references `env://BOUNDARY_PG_MIGRATION_URL`. The key name must match `secretRefs.keys.migrationUrl`.

## Create the TLS Secret

Follow [Create the TLS Secret when TLS is enabled](/boundary/docs/deploy/helm-chart/deploy-controller#create-the-tls-secret-when-tls-is-enabled). The same Secret supports the TLS variations below.

## Enable database initialization

`database.init.enabled` defaults to `true`. Keep the default for the first installation against an empty PostgreSQL database. Set it to `false` when another workflow initializes the schema or the database is already initialized.

## Enable bootstrap admin creation

`bootstrapAdmin.enabled` defaults to `true` and creates the initial global password auth method, user, account, and role. Set it to `false` if another workflow manages the initial administrator resources.

## Controller with TLS enabled

Enable TLS when you want encrypted API and ops traffic from the controller listeners. Provide a Kubernetes TLS Secret. The chart derives HTTPS probes from `tls.ops.disabled=false`.

Example values:

```yaml
tls:
  api:
    disabled: false
  ops:
    disabled: false
  secretName: boundary-controller-tls
  mountPath: /etc/boundary/tls
```

Matching HCL: set `tls_disable = false` and add `tls_cert_file` and `tls_key_file` on the API and ops listeners:

```hcl
listener "tcp" {
  address       = "0.0.0.0:9200"
  purpose       = "api"
  tls_disable   = "{{ .Values.tls.api.disabled }}"
  tls_cert_file = "{{ .Values.tls.mountPath }}/tls.crt"
  tls_key_file  = "{{ .Values.tls.mountPath }}/tls.key"
}

listener "tcp" {
  address       = "0.0.0.0:9203"
  purpose       = "ops"
  tls_disable   = "{{ .Values.tls.ops.disabled }}"
  tls_cert_file = "{{ .Values.tls.mountPath }}/tls.crt"
  tls_key_file  = "{{ .Values.tls.mountPath }}/tls.key"
}
```


## Controller with TLS disabled

Disable TLS when the controller listeners are protected by an upstream proxy or load balancer that terminates TLS, or in non-production environments where encryption is not required.

Example values:

```yaml
tls:
  api:
    disabled: true
  ops:
    disabled: true
```

Matching HCL: set `tls_disable = true` on each listener that had TLS enabled and remove the `tls_cert_file` and `tls_key_file` settings:

```hcl
listener "tcp" {
  address     = "0.0.0.0:9200"
  purpose     = "api"
  tls_disable = true
}

listener "tcp" {
  address     = "0.0.0.0:9203"
  purpose     = "ops"
  tls_disable = true
}
```

The chart always renders the probes. Their default scheme derives only from `tls.ops.disabled`, so this configuration uses `HTTP`. The chart omits the TLS Secret mount only when both listener values are `true`.

## Internal-only cluster service

If all workers run inside the cluster or connect through private networking, keep the cluster listener internal and set `public_cluster_addr` to a private DNS name or internal load balancer address reachable by workers.

Example values:

```yaml
controller:
  service:
    api:
      type: LoadBalancer
    cluster:
      type: ClusterIP
    ops:
      type: ClusterIP
```

Set the advertised cluster address in the existing `controller` stanza:

```hcl
controller {
  public_cluster_addr = "boundary-controller-cluster.boundary.svc.cluster.local:9201"
}
```

## Externally accessible cluster service

When workers run outside the cluster, the default `ClusterIP` cluster service is not reachable. Workers in another namespace can use the Service's fully qualified cluster DNS name when network policy permits it. Configure the cluster service as a `LoadBalancer` only when workers need to connect from outside the cluster.

Example values:

```yaml
controller:
  service:
    cluster:
      type: LoadBalancer
      port: 9201
      targetPort: 9201
```

Update the advertised address in the existing `controller` stanza after the load balancer is provisioned:

```hcl
controller {
  public_cluster_addr = "<LOAD_BALANCER_ADDRESS>:9201"
}
```

Watch the cluster Service until the external address is assigned:

```shell-session
$ kubectl get svc boundary-controller-cluster --namespace boundary --watch
```

Example output:

```plaintext
NAME                          TYPE           CLUSTER-IP     EXTERNAL-IP     PORT(S)          AGE
boundary-controller-cluster   LoadBalancer   10.0.0.123     <pending>       9201:31234/TCP   10s
boundary-controller-cluster   LoadBalancer   10.0.0.123     203.0.113.10    9201:31234/TCP   45s
```

Update `public_cluster_addr` in `controller.config` with the assigned address, then upgrade:

```shell-session
$ helm upgrade boundary-controller hashicorp/boundary-controller \
  --namespace boundary \
  --values controller-values.yaml \
  --rollback-on-failure \
  --wait
```

Use this pattern when workers require an endpoint reachable from outside the Kubernetes cluster. Restrict access to trusted worker networks.

## Controller with a pre-configured DNS address

If you already control the DNS name for the controller's cluster listener, set `public_cluster_addr` to that address before installation:

```hcl
controller {
  public_cluster_addr = "boundary-controller.example.com:9201"
}
```

After the cluster Service receives an external address, point the DNS record to that address. This avoids changing the controller HCL after installation, but you remain responsible for ensuring that DNS resolves to the reachable cluster listener endpoint.

## Configure migration URL

If you use a different PostgreSQL connection string for schema migrations, store it in the controller Secret and reference it from `controller.config`.

Matching HCL:

```hcl
controller {
  name = "boundary-controller"
  public_cluster_addr = "boundary-controller-cluster.boundary.svc.cluster.local:9201"
  license = "env://BOUNDARY_LICENSE"

  database {
    url = "env://BOUNDARY_PG_URL"
    migration_url = "env://BOUNDARY_PG_MIGRATION_URL"
  }
}
```

Store the value under the Secret key configured by `secretRefs.keys.migrationUrl`, which defaults to `migration-url`. The chart injects it as `BOUNDARY_PG_MIGRATION_URL` when the rendered HCL references the environment variable shown above.

## Migrate the database during an upgrade

<Warning>

Take a PostgreSQL backup before running migrations or repairs. Helm rollback does not reverse database schema changes.

</Warning>

When upgrading to a Boundary version that requires a schema change, stop the controller pods first, then run the migration Job during the Helm upgrade.

Scale controllers to zero:

```shell-session
$ helm upgrade boundary-controller hashicorp/boundary-controller \
  --namespace boundary \
  --values controller-values.yaml \
  --set controller.replicas=0 \
  --rollback-on-failure \
  --wait
```

Back up PostgreSQL after the controllers stop. Then run the migration as a one-time command-line override instead of adding it to the values file:

```shell-session
$ helm upgrade boundary-controller hashicorp/boundary-controller \
  --namespace boundary \
  --values controller-values.yaml \
  --set controller.replicas=0 \
  --set database.migrate.enabled=true \
  --rollback-on-failure \
  --wait
```

Run a repair only when the Boundary migration output directs you to a specific version:

```shell-session
$ helm upgrade boundary-controller hashicorp/boundary-controller \
  --namespace boundary \
  --values controller-values.yaml \
  --set controller.replicas=0 \
  --set database.migrate.enabled=true \
  --set database.repair.version=<version_id> \
  --rollback-on-failure \
  --wait
```


After the migration completes, reset all migration flags and restore the controller replica count:

<Note>

Set `controller.replicas` to the count required by your deployment. The following example restores the default value of `2`.

</Note>

```shell-session
$ helm upgrade boundary-controller hashicorp/boundary-controller \
  --namespace boundary \
  --values controller-values.yaml \
  --set database.migrate.enabled=false \
  --set database.repair.version="" \
  --set controller.replicas=2 \
  --rollback-on-failure \
  --wait
```

<Note>

The `--reset-values` flag resets all Helm values, including overrides applied with `--set` or `--set-file`. Clear the migration values explicitly to avoid unrelated configuration changes.

</Note>

## Change service ports

If you change listener ports, update both the HCL and chart values.

Example values:

```yaml
controller:
  service:
    api:
      port: 9210
      targetPort: 9210
```

Matching HCL:

```hcl
listener "tcp" {
  address       = "0.0.0.0:9210"
  purpose       = "api"
  tls_disable   = false
  tls_cert_file = "/etc/boundary/tls/tls.crt"
  tls_key_file  = "/etc/boundary/tls/tls.key"
}
```

The chart does not synchronize these settings automatically. Apply the same pattern for the cluster and ops listeners if those ports change.

## Troubleshooting

### Migration Job fails

If the migration Job started by `database.migrate.enabled=true` fails, the controller pods remain scaled to zero until the migration succeeds. Refer to the PostgreSQL backup you took before running migrations or repairs to restore the database, then correct the underlying issue (for example, an invalid `database.repair.version`) before setting `database.migrate.enabled=true` again and re-running `helm upgrade`.
