# Deploy controllers using a Helm chart

@include 'helm/controller-chart.mdx'

The Boundary controller Helm chart deploys a Boundary control plane backed by PostgreSQL. This page covers the controller chart only. To add data plane capacity, refer to [Deploy workers using a Helm chart](/boundary/docs/deploy/helm-chart/deploy-worker).

For Red Hat OpenShift-specific requirements and Routes, refer to [Deploy Boundary on OpenShift](/boundary/docs/deploy/openshift).

## Prerequisites

Before installing the controller Helm chart, make sure the following are available:

- A Kubernetes cluster and `kubectl` access with permission to create namespaces, Secrets, Deployments, Services, ConfigMaps, Jobs, and PodDisruptionBudgets.
- Helm 3 or later configured to access the cluster.
- A reachable PostgreSQL database for Boundary controller pods.
- A valid Boundary controller HCL configuration.
- Key management system (KMS) configuration for the `root`, `recovery`, and `worker-auth` purposes.
- The database URL, [Boundary Enterprise license](/boundary/docs/enterprise/licensing), and bootstrap administrator credentials used to create the controller Secret. The bootstrap administrator Job is enabled by default.
- A TLS certificate and private key used to create a Kubernetes TLS Secret when TLS is enabled for either the API or operations listener. TLS is enabled for both listeners by default.
- An existing ServiceAccount only when you set `serviceAccount.name`. When the value is empty, Kubernetes assigns the namespace's default ServiceAccount.

The controller chart deploys a stateless Boundary control plane. PostgreSQL stores the persistent controller state, not the controller pods.

Complete the following steps to deploy a controller using the Helm chart.

## Add the HashiCorp Helm repository

Add the Helm repository, update its index, and list the available chart versions:

```shell-session
$ helm repo add hashicorp https://helm.releases.hashicorp.com
$ helm repo update
$ helm search repo hashicorp/boundary-controller --versions
```

Refer to the [Boundary controller chart on Artifact Hub](https://artifacthub.io/packages/helm/hashicorp/boundary-controller/) for official releases and [default chart values](https://artifacthub.io/packages/helm/hashicorp/boundary-controller/?modal=values). Choose a chart version that contains the Boundary version you want to deploy. To pin that version, add `--version <chart-version>` to the `helm install` and `helm upgrade` commands.

## Create the namespace

Create the namespace before you create the Secrets that the chart uses:

```shell-session
$ kubectl create namespace boundary
```

If the namespace already exists, continue to the next step. Use this same namespace for the Secrets and Helm release throughout this guide.

## Create the controller Secret

The chart reads sensitive settings from the Kubernetes Secret specified by `secretRefs.secretName`. You can change the Secret name and its key names in your values file:

| Default key | Used for |
| --- | --- |
| `database-url` | `env://BOUNDARY_PG_URL` in `database.url` |
| `license` | `env://BOUNDARY_LICENSE` in `controller.license` |
| `admin-username` | Bootstrap administrator username |
| `admin-password` | Bootstrap administrator password |

Add `migration-url` when `controller.config` references `env://BOUNDARY_PG_MIGRATION_URL`. Configure key names with `secretRefs.keys.*`.

The environment references used by the default controller HCL are fixed. Changing the Secret name or key names does not change `env://BOUNDARY_PG_URL`, `env://BOUNDARY_LICENSE`, or `env://BOUNDARY_PG_MIGRATION_URL` inside `controller.config`.

You can create and manage the Secret using any of the following methods:

- Create it manually with Kubernetes tools by using the command below.
- Synchronize it from Vault with the [Vault Secrets Operator](https://developer.hashicorp.com/vault/docs/deploy/kubernetes/vso).
- Synchronize it from an external secret store with the [External Secrets Operator](https://external-secrets.io/latest/).

Set `secretRefs.validateExisting=true` to make Helm look up the Secret during rendering. This targeted validation checks only keys required by the rendered HCL and enabled bootstrap settings. It does not validate the Secret by default, and it does not validate credentials or connectivity.

For a first installation, create the Secret with the default key names before you install the chart:

```shell-session
$ kubectl create secret generic boundary-controller-secrets \
  --namespace boundary \
  --from-literal=database-url='postgres://<user>:<password>@<host>:5432/<database>?sslmode=require' \
  --from-literal=license='<boundary-enterprise-license>' \
  --from-literal=admin-username='<admin-username>' \
  --from-literal=admin-password='<admin-password>'
```

The database account must be allowed to initialize the Boundary schema when you leave `database.init.enabled=true`.

## Create the TLS Secret when TLS is enabled

Create a Kubernetes Secret when either `tls.api.disabled=false` or `tls.ops.disabled=false`. The Secret must contain `tls.crt` and `tls.key`, and its name must match `tls.secretName`, which defaults to `boundary-controller-tls`. You can use the Kubernetes TLS Secret type described in the [Kubernetes TLS Secrets documentation](https://kubernetes.io/docs/concepts/configuration/secret/#tls-secrets).

The following command creates the default Secret from an existing certificate and private key:

```shell-session
$ kubectl create secret tls boundary-controller-tls \
  --namespace boundary \
  --cert=tls.crt \
  --key=tls.key
```

The chart mounts the TLS Secret while either listener uses TLS. It omits the mount only when TLS is disabled for both listeners. The chart does not validate certificate contents, trust, expiration, or SANs.

## Prepare the controller configuration

The chart reads the Boundary controller HCL from the `controller.config` key in your values file. Set this value before installing the chart.

For a base controller configuration, refer to the controller configuration guidance in the [controller stanza](/boundary/docs/configuration/controller) reference.

A usable controller configuration includes:

- An API listener
- A cluster listener
- An operations listener
- A `controller` block with Secret-backed `license` and `database.url` settings
- A `public_cluster_addr` so workers can reach the cluster listener
- KMS stanzas for `root`, `recovery`, and `worker-auth`

The complete baseline HCL appears once in the installation values below. The chart renders `controller.config` as a Helm template, so expressions that reference `.Values` are evaluated during rendering.

Set `public_cluster_addr` to the stable address that workers use to reach the controller cluster listener. For workers outside the Kubernetes cluster, expose the listener through a TCP-capable load balancer or ingress path that preserves Boundary mutual TLS. Do not use an HTTP-only ingress path unless it supports TCP and TLS passthrough.

<Warning>

The inline AEAD KMS blocks in this example are for development and testing only. Boundary does not support `env://BOUNDARY_KMS_*` references in AEAD `key` fields, and the chart rejects them. Configure an external KMS provider for production as described in [Configure KMS](/boundary/docs/configuration/kms).

</Warning>

We do not recommend changing `disable_mlock = true` from the chart default. The containers run without the elevated privileges required for memory locking.

## Install a Boundary controller

Create `controller-values.yaml` containing the settings required for your environment. Update the example KMS blocks before production use, and update `public_cluster_addr` if workers will not run in the `boundary` namespace. The following baseline reads the database URL and license from the Secrets created earlier:

```yaml
secretRefs:
  secretName: boundary-controller-secrets
  validateExisting: true

serviceAccount:
  name: ""

tls:
  api:
    disabled: false
  ops:
    disabled: false

controller:
  config: |
    disable_mlock = true

    listener "tcp" {
      address       = "0.0.0.0:9200"
      purpose       = "api"
      tls_disable   = "{{ .Values.tls.api.disabled }}"
      tls_cert_file = "{{ .Values.tls.mountPath }}/tls.crt"
      tls_key_file  = "{{ .Values.tls.mountPath }}/tls.key"
    }

    listener "tcp" {
      address = "0.0.0.0:9201"
      purpose = "cluster"
    }

    listener "tcp" {
      address       = "0.0.0.0:9203"
      purpose       = "ops"
      tls_disable   = "{{ .Values.tls.ops.disabled }}"
      tls_cert_file = "{{ .Values.tls.mountPath }}/tls.crt"
      tls_key_file  = "{{ .Values.tls.mountPath }}/tls.key"
    }

    controller {
      name = "boundary-controller"
      public_cluster_addr = "{{ (printf "%s:9201" (include "boundary.controller.clusterServiceName" .)) }}"
      license = "env://BOUNDARY_LICENSE"

      database {
        url = "env://BOUNDARY_PG_URL"
      }

      graceful_shutdown_wait_duration = "10s"
    }

    kms "aead" {
      purpose   = "root"
      aead_type = "aes-gcm"
      key       = "sP1fnF5Xz85RrXyELHFeZg9Ad2qt4Z4bgNHVGtD6sFo="
      key_id    = "global_root"
    }

    kms "aead" {
      purpose   = "recovery"
      aead_type = "aes-gcm"
      key       = "8fZBjCUfN0TzjEGLQldGY4+iE9AkOvCfjh7+p0GtRBQ="
      key_id    = "global_recovery"
    }

    kms "aead" {
      purpose   = "worker-auth"
      aead_type = "aes-gcm"
      key       = "ATTK2pMjMTEJGlAkUJAePnFMlNLQaXBnhSqJHVlJeKQ="
      key_id    = "global_worker-auth"
    }

    events {
      audit_enabled        = true
      sysevents_enabled    = true
      observations_enabled = true
      sink "stderr" {
        name = "all-events"
        description = "All events sent to stderr"
        event_types = ["*"]
        format = "hclog-text"
      }
    }

  service:
    api:
      type: LoadBalancer
    cluster:
      type: ClusterIP
    ops:
      type: ClusterIP
```

Run the following command to install the release. `database.init.enabled` and `bootstrapAdmin.enabled` both default to `true`, so the install initializes the database and creates the bootstrap administrator:

```shell-session
$ helm install boundary-controller hashicorp/boundary-controller \
  --namespace boundary \
  --values controller-values.yaml \
  --wait
```

## Verify the deployment

Check the release resources after installation:

```shell-session
$ kubectl get deployment,pods,services,jobs,pdb --namespace boundary
$ kubectl logs --namespace boundary deployment/boundary-controller
```


Kubernetes generates the controller pod suffixes. Hook Jobs and their pods expire 10 minutes after completion, so they may no longer appear in this output.

Confirm that:

- The database initialization Job completes successfully when `database.init.enabled=true`.
- The bootstrap administrator Job completes successfully when `bootstrapAdmin.enabled=true`.
- The controller pods become Ready.
- The API, cluster, and ops services match your intended exposure model.
- Boundary API requests succeed against the controller API listener.
- Workers can reach `public_cluster_addr` and register successfully.

The bootstrap Job creates the password auth method and administrator account from the credentials in `boundary-controller-secrets`. Before you use the Boundary CLI to authorize workers, connect the CLI to the API Service, retrieve the generated auth method ID from Boundary, and authenticate with the bootstrap administrator credentials. Refer to [Password authentication](/boundary/docs/authentication/password) for the CLI authentication workflow.

## Upgrade the controller

To upgrade the controller deployment, run:

```shell-session
$ helm upgrade boundary-controller hashicorp/boundary-controller \
  --namespace boundary \
  --values controller-values.yaml \
  --rollback-on-failure \
  --wait
```

For upgrades that require a database migration, follow [Migrate the database during an upgrade](/boundary/docs/deploy/helm-chart/controller-examples#migrate-the-database-during-an-upgrade).

## Uninstall the controller

To remove the controller Helm release and its associated Kubernetes resources, run:

```shell-session
$ helm uninstall boundary-controller --namespace boundary
```
