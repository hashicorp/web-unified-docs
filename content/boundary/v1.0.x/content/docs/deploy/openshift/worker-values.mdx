# Worker values

You configure the Boundary worker OpenShift Helm chart with Helm values and a Boundary HCL configuration. The chart is the source of truth for supported values.

The worker chart is the same chart you use on Kubernetes, with an additional `openshift` value group. Set `openshift.enabled=true` to resolve the worker image from the Red Hat certified registry, apply a security context that complies with OpenShift security context constraints (SCCs), and publish the proxy port through an OpenShift `Route` instead of a `LoadBalancer` Service. When `openshift.enabled=false`, the chart ignores every value under `openshift` and behaves exactly as it does on Kubernetes.

The Deployment always runs a single worker replica. Boundary workers are not horizontally scaled by this chart; deploy additional Helm releases if you need more workers.

## Boundary runtime configuration

The `worker.config` contains the Boundary worker HCL. The chart writes this value into a ConfigMap and mounts it at `/etc/boundary/boundary-worker.hcl`.

The chart renders `worker.config` with Helm's `tpl` function. Helm template expressions inside the HCL are evaluated during rendering.

At container startup, the chart replaces `${POD_NAME_LOWER}` with the pod name converted to lowercase and starts Boundary with the processed configuration file.

The chart validates the following:

- When `secretRefs.secretName` is set, `controller_generated_activation_token` in `worker.config` must reference `env://BOUNDARY_WORKER_CONTROLLER_GENERATED_ACTIVATION_TOKEN`. A different `env://` reference, or a hardcoded token value, fails the render with a descriptive error.
- When `secretRefs.validateExisting=true`, the referenced Secret and its activation token key must exist in the release namespace.

Beyond these checks, the chart does not validate Boundary HCL semantics. You are responsible for configuring valid listeners, registration settings, upstreams, storage paths, and worker tags.

## OpenShift infrastructure configuration

OpenShift-specific values control the Deployment, Services, the proxy Route, PVCs, security contexts, and scheduling options. These values do not replace or generate the Boundary runtime HCL.

For example, if you change `worker.service.proxy.targetPort` to `9222`, you must also update the proxy listener port in `worker.config`.

Refer to the [configuration alignment checklist](#configuration-alignment-checklist) before you finalize any changes.

The following sections describe all available Helm values, grouped by function. Each table lists the key, default value, and a description.

## Naming and namespace values

| Key | Default | Description |
| --- | --- | --- |
| `nameOverride` | `""` | Overrides the chart-generated resource base name |
| `fullnameOverride` | `""` | Fully overrides the chart-generated resource name |
| `namespace` | `""` | Overrides the namespace the chart renders namespaced resources into. An empty value uses the Helm release namespace. |

On OpenShift, the namespace maps to an OpenShift project. The project must exist, or you must install the release with `--create-namespace`.

The proxy Route name is also derived from the resource name. When `openshift.route.proxy.host` is empty, OpenShift builds the hostname from the Route name, the project name, and the cluster ingress domain. Keep the release name, `nameOverride`, or `fullnameOverride` short so the generated hostname stays within DNS label limits.

## Image values

| Key | Default | Description |
| --- | --- | --- |
| `image.repository` | `""` | Worker image repository. When empty and `openshift.enabled=true`, the chart uses `registry.connect.redhat.com/hashicorp/boundary-enterprise`. When empty and `openshift.enabled=false`, the chart uses `hashicorp/boundary-enterprise`. |
| `image.tag` | `""` | Worker image tag. When empty and `openshift.enabled=true`, the chart appends `-ubi` to `Chart.appVersion`, currently `1.0.1-ent-ubi`. When empty and `openshift.enabled=false`, the chart uses `Chart.appVersion`, currently `1.0.1-ent`. |
| `image.pullPolicy` | `IfNotPresent` | Kubernetes image pull policy |
| `imagePullSecrets` | `[]` | Optional image pull secrets for private registries |

The Red Hat certified registry uses the `<version>-ubi` tag convention, so the chart derives the tag automatically when you do not set one. An explicit `image.repository` or `image.tag` always takes precedence. Because `registry.connect.redhat.com` requires authentication, create a pull Secret and reference it in `imagePullSecrets`, or link the Secret to the ServiceAccount used by the worker.

## Worker runtime values

| Key | Default | Description |
| --- | --- | --- |
| `worker.config` | Embedded sample HCL | Boundary worker HCL stored in a ConfigMap and mounted into the worker container. Replace placeholders before installing. |
| `worker.terminationGracePeriodSeconds` | `7200` | Pod termination grace period in seconds. Allows long-running sessions time to drain before forced termination. |

The default `worker.config` includes `disable_mlock = true`. The chart's default security model drops all Linux capabilities and disallows privilege escalation. We do not recommend changing this value, because OpenShift SCCs do not grant the `IPC_LOCK` capability that memory locking requires. If you enable swap on your nodes, address any resulting data-at-rest exposure through platform controls.

## Probe values

The chart adds liveness and readiness probes against the `/health` endpoint on the ops listener. These probes connect to the ops container port directly; they do not pass through the Route, so Route TLS termination does not affect the probe scheme.

| Key | Default | Description |
| --- | --- | --- |
| `worker.livenessProbe.scheme` | `HTTP` | Probe scheme for `/health` on the ops listener |
| `worker.livenessProbe.initialDelaySeconds` | `10` | Initial liveness probe delay |
| `worker.livenessProbe.periodSeconds` | `10` | Liveness probe period |
| `worker.livenessProbe.failureThreshold` | `3` | Liveness probe failure threshold |
| `worker.livenessProbe.timeoutSeconds` | `5` | Liveness probe timeout |
| `worker.readinessProbe.scheme` | `HTTP` | Probe scheme for `/health` on the ops listener |
| `worker.readinessProbe.initialDelaySeconds` | `10` | Initial readiness probe delay |
| `worker.readinessProbe.periodSeconds` | `10` | Readiness probe period |
| `worker.readinessProbe.failureThreshold` | `3` | Readiness probe failure threshold |
| `worker.readinessProbe.timeoutSeconds` | `5` | Readiness probe timeout |

## Proxy Service values

The proxy Service exposes the worker's session traffic listener.

| Key | Default | Description |
| --- | --- | --- |
| `worker.service.proxy.enabled` | `true` | Creates the proxy Service when enabled |
| `worker.service.proxy.type` | `LoadBalancer` | Kubernetes Service type for proxy traffic. Ignored on OpenShift when the proxy Route is enabled; see below. |
| `worker.service.proxy.port` | `9202` | Service port for proxy traffic |
| `worker.service.proxy.targetPort` | `9202` | Container port targeted by the proxy Service. Must match the proxy listener in `worker.config`. |
| `worker.service.proxy.annotations` | `{}` | Annotations added to the proxy Service. AWS load balancer annotations (`service.beta.kubernetes.io/aws-load-balancer-*`) are omitted automatically whenever the effective Service type is not `LoadBalancer`. |

When `openshift.enabled=true` and `openshift.route.proxy.enabled=true` (the default), the chart forces the proxy Service type to `ClusterIP` regardless of `worker.service.proxy.type`. The Route publishes the port externally instead, since `LoadBalancer` Services depend on a cloud provider integration that is not available in every OpenShift environment. Set `openshift.route.proxy.enabled=false` if you need `worker.service.proxy.type` to be honored instead of the Route, for example when your OpenShift cluster runs on a cloud provider that supports `LoadBalancer` Services directly.

## Operations Service values

The operations Service exposes the worker operations listener for health and metrics.

| Key | Default | Description |
| --- | --- | --- |
| `worker.service.ops.enabled` | `true` | Creates the operations Service when enabled |
| `worker.service.ops.type` | `ClusterIP` | Kubernetes Service type for operations traffic |
| `worker.service.ops.port` | `9203` | Service port for the operations endpoint |
| `worker.service.ops.targetPort` | `9203` | Container port targeted by the operations Service. Must match the ops listener in `worker.config`. |
| `worker.service.ops.annotations` | `{}` | Annotations added to the operations Service |

Unlike the proxy port, the chart does not publish a Route for the operations Service. Keep it internal unless a trusted monitoring path requires a different exposure model; if you need external access, create the Route yourself rather than exposing the operations Service through `LoadBalancer` or `NodePort`.

## OpenShift values

The `openshift` values group controls OpenShift-only behavior. The chart evaluates these values only when `openshift.enabled=true`.

| Key | Default | Description |
| --- | --- | --- |
| `openshift.enabled` | `false` | Enables OpenShift mode. When true, the chart renders the proxy Route, applies the OpenShift security contexts, and resolves the image from the Red Hat certified registry. |

### OpenShift security context values

When `openshift.enabled=true`, the chart replaces `podSecurityContext` and `containerSecurityContext` with the values under `openshift` for the worker Deployment. These values intentionally omit `runAsUser`, `runAsGroup`, and `fsGroup` so that the OpenShift SCC can assign a UID and GID from the project's allocated range.

| Key | Default |
| --- | --- |
| `openshift.podSecurityContext.runAsNonRoot` | `true` |
| `openshift.podSecurityContext.seccompProfile.type` | `RuntimeDefault` |
| `openshift.containerSecurityContext.runAsNonRoot` | `true` |
| `openshift.containerSecurityContext.allowPrivilegeEscalation` | `false` |
| `openshift.containerSecurityContext.readOnlyRootFilesystem` | `true` |
| `openshift.containerSecurityContext.capabilities.drop` | `ALL` |
| `openshift.containerSecurityContext.seccompProfile.type` | `RuntimeDefault` |

These defaults are compatible with the `restricted-v2` SCC, so the worker does not require a custom SCC or elevated privileges. Do not add `runAsUser`, `runAsGroup`, or `fsGroup` unless the ServiceAccount is bound to an SCC that permits the UID and GID you specify. Otherwise, the pod fails admission.

### Proxy Route values

| Key | Default | Description |
| --- | --- | --- |
| `openshift.route.proxy.enabled` | `true` | Creates a Route for the proxy Service and forces the proxy Service type to `ClusterIP` |
| `openshift.route.proxy.host` | `""` | Hostname for the proxy Route. An empty value lets OpenShift generate a hostname from the Route name, namespace, and cluster ingress domain. |
| `openshift.route.proxy.tls.termination` | `passthrough` | TLS termination mode for the proxy Route |
| `openshift.route.proxy.annotations` | `{}` | Annotations added to the proxy Route |

Leave `openshift.route.proxy.tls.termination` set to `passthrough`. The proxy port carries Boundary's own session TLS over raw TCP, not HTTP. `edge` or `reencrypt` termination terminates TLS at the router and breaks client-to-worker sessions. Change this only if you re-originate Boundary's protocol yourself.

The chart names the Route after the worker Service, using the `-proxy-route` suffix, for example `boundary-worker-proxy-route`.

Unlike a Kubernetes `LoadBalancer` Service, an OpenShift Route does not preserve the container's port number. The router serves every `passthrough` Route on its shared HTTPS port (`443` by default) and uses the TLS SNI (Server Name Indication) extension to reach the correct worker Service. Set `public_addr` in `worker.config` to `<route-host>:443`, not `<route-host>:9202`.

## Resource values

| Key | Default | Description |
| --- | --- | --- |
| `worker.resources.requests.cpu` | `100m` | CPU request for the worker container |
| `worker.resources.requests.memory` | `512Mi` | Memory request for the worker container |
| `worker.resources.limits.cpu` | `200m` | CPU limit for the worker container |
| `worker.resources.limits.memory` | `1Gi` | Memory limit for the worker container |

Tune resource values for your expected connection volume, recording usage, and cluster sizing. If the target project has a `LimitRange` or `ResourceQuota`, confirm that the requests and limits fall within the allowed range. Otherwise, the Deployment fails admission.

## Auth storage values

Auth storage stores worker identity and authentication material for registration models that require local persistence.

| Key | Default | Description |
| --- | --- | --- |
| `worker.persistence.authStorage.enabled` | `false` | Creates and mounts an auth storage PVC when enabled. When disabled, the chart mounts an `emptyDir` at the auth storage path. |
| `worker.persistence.authStorage.size` | `1Gi` | Size of the auth storage PVC |
| `worker.persistence.authStorage.accessMode` | `ReadWriteOnce` | Access mode for the auth storage PVC |
| `worker.persistence.authStorage.storageClass` | `""` | StorageClass for the auth storage PVC. Empty uses the cluster (project) default. |
| `worker.persistence.authStorage.path` | `/var/lib/boundary` | Mount path for auth storage. Must match `auth_storage_path` in `worker.config`. |
| `worker.persistence.authStorage.retainOnUninstall` | `true` | Preserves the auth storage PVC after `helm uninstall`. Set to `false` to delete the PVC on uninstall. |

Disable auth storage only when your worker authentication model does not require persistent local auth material, such as KMS-backed worker authentication.

## Recording storage values

Recording storage stores session recordings when recording is configured in Boundary.

| Key | Default | Description |
| --- | --- | --- |
| `worker.persistence.recording.enabled` | `false` | Creates and mounts a recording PVC when enabled |
| `worker.persistence.recording.size` | `10Gi` | Size of the recording PVC |
| `worker.persistence.recording.accessMode` | `ReadWriteOnce` | Access mode for the recording PVC |
| `worker.persistence.recording.storageClass` | `""` | StorageClass for the recording PVC. Empty uses the cluster (project) default. |
| `worker.persistence.recording.path` | `/boundary/recording` | Mount path for recording storage. Must match `recording_storage_path` in `worker.config` when recording is enabled. |
| `worker.persistence.recording.retainOnUninstall` | `true` | Preserves the recording PVC after `helm uninstall`. Set to `false` to delete the PVC on uninstall. |

If you disable recording storage, remove `recording_storage_path` from the HCL or ensure recording data does not need to persist.

## Secret reference values

The chart injects values from an existing Kubernetes Secret as environment variables into the worker container. Use this to supply sensitive values such as a controller-generated activation token without embedding them in `worker.config`.

| Key | Default | Description |
| --- | --- | --- |
| `secretRefs.secretName` | `""` | Name of an existing Kubernetes Secret to inject into the worker container. When empty, no Secret is mounted. |
| `secretRefs.validateExisting` | `false` | When true, Helm fails early if the referenced Secret does not exist or is missing the required key. |
| `secretRefs.keys.controllerGeneratedActivationToken` | `worker-controller-generated-activation-token` | Key in the Secret used for `BOUNDARY_WORKER_CONTROLLER_GENERATED_ACTIVATION_TOKEN`. Must match the key name in the Kubernetes Secret. |

To use a Secret for controller-led registration, set `controller_generated_activation_token = "env://BOUNDARY_WORKER_CONTROLLER_GENERATED_ACTIVATION_TOKEN"` in `worker.config` and point `secretRefs.secretName` at the Secret that contains the token key.

## Extra environment variables

Use `extraEnv` to inject additional environment variables into the worker container. This supports any valid Kubernetes `env` entry, including plain `name`/`value` pairs and `valueFrom` references.

| Key | Default | Description |
| --- | --- | --- |
| `extraEnv` | `[]` | List of additional environment variables injected into the worker container |

Example using a plain value:

```yaml
extraEnv:
  - name: BOUNDARY_WORKER_CONTROLLER_GENERATED_ACTIVATION_TOKEN
    value: "act_1234abcd..."
```

Example using a Secret reference:

```yaml
extraEnv:
  - name: BOUNDARY_WORKER_CONTROLLER_GENERATED_ACTIVATION_TOKEN
    valueFrom:
      secretKeyRef:
        name: boundary-worker-secrets
        key: worker-controller-generated-activation-token
```

Use `extraEnv` as an alternative to `secretRefs` when you need finer control over how Secret keys are mapped to environment variable names, or when injecting variables unrelated to activation tokens.

| Key | Default |

| `podSecurityContext.fsGroup` | `1000` |
| `podSecurityContext.fsGroupChangePolicy` | `OnRootMismatch` |
| `podSecurityContext.seccompProfile.type` | `RuntimeDefault` |
| `containerSecurityContext.runAsNonRoot` | `true` |

## ServiceAccount values

| Key | Default | Description |
| --- | --- | --- |
| `serviceAccount.create` | `false` | Creates a ServiceAccount for the worker Deployment and PVC Jobs when true. When false, the chart uses the ServiceAccount named by `serviceAccount.name`. |
| `serviceAccount.name` | `""` | Name of the ServiceAccount to use or create. When empty and `serviceAccount.create=true`, the chart uses the release fullname. |
| `serviceAccount.annotations` | `{}` | Annotations added to the ServiceAccount. Use to attach IRSA (IAM Roles for Service Accounts, `eks.amazonaws.com/role-arn`) or Workload Identity (`iam.gke.io/gcp-service-account`) annotations for cloud-provider KMS (key management system) access on managed OpenShift offerings such as ROSA (Red Hat OpenShift Service on AWS) or ARO (Azure Red Hat OpenShift). |
| `serviceAccount.automountServiceAccountToken` | `false` | Controls whether the pod service account token is mounted. Set to `true` when using IRSA or Workload Identity. |

In production, create a dedicated ServiceAccount rather than relying on `default`. The ServiceAccount also determines which SCC admits the worker pods, and it is where you link an image pull Secret for the Red Hat certified registry.

## Networking values

| Key | Default | Description |
| --- | --- | --- |
| `hostNetwork` | `false` (unset) | Runs the worker pod on the host's network namespace and sets `dnsPolicy: Default` when true. |

`hostNetwork` is intended for single-node or bare-metal OpenShift installations (for example MicroShift or CRC-based development clusters) where a Route or cloud `LoadBalancer` path is unavailable or does not route session traffic correctly. Standard multi-node OpenShift clusters should expose the proxy port through the Route described above instead of enabling `hostNetwork`. Enabling it also removes the network isolation the pod would otherwise have, so treat it as an exception for constrained environments rather than a default production setting.

## Configuration alignment checklist

Before installing or upgrading a worker on OpenShift, confirm that:

- The `openshift.enabled` value is `true` so that the chart renders the proxy Route and applies the OpenShift security contexts.
- The proxy listener port in `worker.config` matches `worker.service.proxy.targetPort`.
- The ops listener port in `worker.config` matches `worker.service.ops.targetPort`.
- The `auth_storage_path` matches `worker.persistence.authStorage.path` when auth storage is enabled.
- The `recording_storage_path` matches `worker.persistence.recording.path` when recording storage is enabled.
- The `public_addr` matches the endpoint other Boundary clients or workers can actually reach. When the proxy Route is enabled, use the Route hostname with port `443`, not the proxy Service name and port `9202`.
- The `openshift.route.proxy.tls.termination` value stays `passthrough` unless you re-originate Boundary's protocol yourself.
- Placeholder activation tokens, cluster IDs, and upstream addresses have been replaced.
- The security context values do not pin a UID or GID that the project's SCC does not allow.

## Troubleshooting

### Worker crash-loops after enabling auth storage

If the worker pod crash-loops after you enable auth storage, confirm that `auth_storage_path` in `worker.config` matches the mounted PVC path set by `worker.persistence.authStorage.path`. A mismatch between the two means the worker cannot read or write its identity material at the expected location.

### Worker pods fail admission

If the Deployment reports an SCC error such as `unable to validate against any security context constraint`, the pod requests something the project's SCC does not allow. Confirm that `openshift.enabled=true`, that you have not added `runAsUser`, `runAsGroup`, or `fsGroup` to the OpenShift security contexts, and that the ServiceAccount in `serviceAccount.name` is bound to an SCC that admits the pod.

### Clients cannot reach the worker through the Route

If clients time out or receive TLS errors connecting through the proxy Route, confirm that `openshift.route.proxy.tls.termination` is `passthrough` and that `public_addr` in `worker.config` uses the Route hostname with port `443` rather than port `9202`. Inspect the rendered Route with `oc describe route boundary-worker-proxy-route --namespace boundary`.
