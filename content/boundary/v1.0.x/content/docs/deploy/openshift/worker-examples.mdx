# Worker OpenShift Helm chart examples

Use these worker configuration variations (ingress, intermediate, and egress topologies, Route-based addressing, and registration methods) to adapt a worker to your network position. They assume a Boundary controller or HCP (HashiCorp Cloud Platform) Boundary cluster already exists.

| Topology | Accepts connections from | Typical exposure on OpenShift | Needs `public_addr` |
| --- | --- | --- | --- |
| Ingress | Downstream workers and clients | OpenShift `Route` (`passthrough` TLS) | Yes |
| Intermediate | Upstream and downstream workers | OpenShift `Route` (`passthrough` TLS) | Yes |
| Egress | Upstream or intermediate workers; connects to targets | `ClusterIP` Service with the proxy Route disabled | No |

Every example assumes `openshift.enabled=true` and Helm chart `0.2.0` or later, where OpenShift support begins. Refer to Artifact Hub for the [official worker chart releases](https://artifacthub.io/packages/helm/hashicorp/boundary-worker/) and [default values](https://artifacthub.io/packages/helm/hashicorp/boundary-worker/?modal=values). When `openshift.enabled=false`, the chart ignores every value under `openshift` and behaves exactly as it does on Kubernetes.

The `oc` commands in these examples assume the `boundary` namespace exists. If it does not, create it once before running any Secret command:

```shell-session
$ oc create namespace boundary
```

The shared worker configurations use the default TLS-enabled operations listener. Create the `boundary-worker-tls` Secret with `tls.crt` and `tls.key` in the release namespace. The operations Route is enabled by default with `reencrypt` termination, which uses separate client-to-router and router-to-worker TLS connections. For a custom client-facing certificate on a non-passthrough operations Route, set `openshift.route.ops.tls.key` and `certificate` together; `caCertificate` is optional and supplies an additional client-facing CA chain. Leave all three empty to use the ingress controller's default certificate. For the backend connection, set `destinationCACertificate` to the CA certificate that issued the worker's `tls.crt`; this separate value verifies the router-to-worker connection only when termination is `reencrypt` and `tls.ops.disabled=false`.

Match the operations Route to the listener TLS setting: use `reencrypt` or `passthrough` only with `tls.ops.disabled=false`, use `edge` only with `tls.ops.disabled=true`, or disable the operations Route. `destinationCACertificate` applies only to `reencrypt`. Disable the operations Route when you do not need external access to health and metrics.

For example, configure a custom client-facing certificate and backend trust for a `reencrypt` operations Route as follows:

```yaml
openshift:
  enabled: true
  route:
    ops:
      enabled: true
      host: boundary-worker-ops.example.com
      tls:
        termination: reencrypt
        insecureEdgeTerminationPolicy: Redirect
        key: |
          -----BEGIN PRIVATE KEY-----
          <private key for the operations Route certificate>
          -----END PRIVATE KEY-----
        certificate: |
          -----BEGIN CERTIFICATE-----
          <certificate for boundary-worker-ops.example.com>
          -----END CERTIFICATE-----
        caCertificate: |
          -----BEGIN CERTIFICATE-----
          <CA chain for the client-facing Route certificate>
          -----END CERTIFICATE-----
        destinationCACertificate: |
          -----BEGIN CERTIFICATE-----
          <CA certificate that issued the worker operations certificate>
          -----END CERTIFICATE-----
```

The proxy Route is different: it has fixed `passthrough` termination so Boundary's session TLS runs directly between the client and worker. It has no certificate value group, and none of the operations Route TLS certificate fields apply to it.

The custom certificate in the example must cover `boundary-worker-ops.example.com`. Omit `key`, `certificate`, and `caCertificate` only when the ingress controller's default certificate covers the operations Route hostname.

## Worker with ingress capabilities

An ingress worker accepts connections from downstream workers and clients. It commonly uses the controller cluster as its upstream and exposes the proxy listener publicly through an OpenShift `Route` with `passthrough` TLS termination. Set the proxy Service to `ClusterIP` when you do not also want a `LoadBalancer`.

Use the topology HCL in [Worker with ingress capabilities](/boundary/docs/deploy/helm-chart/worker-examples#worker-with-ingress-capabilities), with the following OpenShift-specific changes:

- Set `public_addr` to the proxy Route hostname with port `443`, for example `boundary-worker-proxy-boundary.apps.example.com:443`.
- Set `worker.service.proxy.type` to `ClusterIP` and enable the proxy Route.

<Note>

Unlike a Kubernetes `LoadBalancer` Service, an OpenShift Route does not preserve the container's port number. The router serves every `passthrough` Route on its shared HTTPS port (`443` by default) and uses the TLS SNI (Server Name Indication) extension to reach the correct worker Service. Set `public_addr` to `<route-host>:443`, not `<route-host>:9202`.

</Note>

Example values for a worker with ingress capabilities exposed through a Route:

```yaml
worker:
  service:
    proxy:
      type: ClusterIP

openshift:
  enabled: true
  route:
    proxy:
      enabled: true
      host: ""
    ops:
      enabled: false
```

<Note>

The proxy Route's TLS termination is always `passthrough`; there is no value to change it.

</Note>

<Note>

When `openshift.route.proxy.enabled=true` (the default once `openshift.enabled=true`), the Route publishes the proxy port externally. The chart does not change `worker.service.proxy.type` for you, so set it to `ClusterIP` as shown above; otherwise the chart also provisions a `LoadBalancer` Service alongside the Route.

</Note>

Install the worker Helm chart:

```shell-session
$ helm install boundary-worker hashicorp/boundary-worker \
  --namespace boundary \
  --create-namespace \
  --values ingress-values.yaml \
  --wait
```

If you do not already control a DNS name for the worker, wait for OpenShift to admit the Route and generate its default hostname:

```shell-session
$ oc get route boundary-worker-proxy-route --namespace boundary --watch
```

Example output:

<CodeBlockConfig hideClipboard>

```
NAME                           HOST/PORT                                        PATH   SERVICES                PORT    TERMINATION   WILDCARD
boundary-worker-proxy-route    boundary-worker-proxy-boundary.apps.example.com         boundary-worker-proxy   proxy   passthrough   None
```

</CodeBlockConfig>

Update `public_addr` in `worker.config` inside `ingress-values.yaml` with the Route hostname and port `443`, and then upgrade:

```shell-session
$ helm upgrade boundary-worker hashicorp/boundary-worker \
  --namespace boundary \
  --values ingress-values.yaml \
  --wait
```

## Worker with intermediate capabilities

A worker with intermediate capabilities relays traffic between upstream and downstream workers. It requires both `initial_upstreams` and `public_addr`, and, like an ingress worker, is typically exposed through an OpenShift Route.

Use the topology HCL in [Worker with intermediate capabilities](/boundary/docs/deploy/helm-chart/worker-examples#worker-with-intermediate-capabilities). For OpenShift, set `public_addr` to this worker's proxy Route hostname with port `443`, set `worker.service.proxy.type` to `ClusterIP`, and enable the proxy Route.

Adjust the upstream port to match how that worker is exposed: `443` if it is reachable through an OpenShift Route, or its configured proxy port (for example `9202`) if it is reachable through a plain Kubernetes Service instead.

Example values for a worker with intermediate capabilities exposed through a Route:

```yaml
worker:
  service:
    proxy:
      type: ClusterIP

openshift:
  enabled: true
  route:
    proxy:
      enabled: true
      host: ""
    ops:
      enabled: false
```

Install the worker Helm chart:

```shell-session
$ helm install boundary-worker hashicorp/boundary-worker \
  --namespace boundary \
  --create-namespace \
  --values intermediate-values.yaml \
  --wait
```

If you do not know the `public_addr` until the Route is admitted, wait for its hostname (refer to the example output shown in [Worker with ingress capabilities](#worker-with-ingress-capabilities)):

```shell-session
$ oc get route boundary-worker-proxy-route --namespace boundary --watch
```

Update `public_addr` in `worker.config` inside `intermediate-values.yaml` with the Route hostname and port `443`, then upgrade:

```shell-session
$ helm upgrade boundary-worker hashicorp/boundary-worker \
  --namespace boundary \
  --values intermediate-values.yaml \
  --wait
```

## Worker with egress capabilities

A worker with egress capabilities connects to target systems and is usually the final hop before a target. It often does not need a `public_addr` and typically does not expose the proxy port externally.

Use the topology HCL in [Worker with egress capabilities](/boundary/docs/deploy/helm-chart/worker-examples#worker-with-egress-capabilities). If its upstream worker is exposed by an OpenShift Route, use that Route hostname and port `443` in `initial_upstreams`.

Example values for a worker with egress capabilities:

```yaml
worker:
  service:
    proxy:
      type: ClusterIP
    ops:
      type: ClusterIP
openshift:
  enabled: true
  route:
    proxy:
      enabled: false
    ops:
      enabled: false
```

<Note>

The chart always renders the proxy and operations Services; there are no values to disable them. Set both Services to `ClusterIP`, and disable both Routes so neither endpoint is reachable from outside the cluster. An egress worker does not need inbound proxy traffic, since it only connects outward to targets and to its upstream worker or controller. Enable the operations Route only when a trusted external monitoring path requires it.

</Note>

Install the worker with a values file that includes the worker configuration:

```shell-session
$ helm install boundary-worker hashicorp/boundary-worker \
  --namespace boundary \
  --create-namespace \
  --values egress-values.yaml \
  --wait
```

## Worker with a pre-configured Route hostname

If you already control the DNS name for the worker, set `openshift.route.proxy.host` and `public_addr` to that hostname before installation. This avoids updating the worker HCL after installation, but you remain responsible for ensuring that DNS resolves to the cluster's ingress router.

Example values:

```yaml
worker:
  service:
    proxy:
      type: ClusterIP

openshift:
  enabled: true
  route:
    proxy:
      enabled: true
      host: boundary-worker.example.com
    ops:
      enabled: false
```

In the [worker with ingress capabilities HCL](/boundary/docs/deploy/helm-chart/worker-examples#worker-with-ingress-capabilities), set `public_addr = "boundary-worker.example.com:443"`.

A custom hostname must resolve to the cluster's ingress router, and the OpenShift ingress controller must admit the hostname. If the router rejects it, the Route stays in a `HostAlreadyClaimed` or `RouteNotAdmitted` state. Check the Route status using `oc describe route boundary-worker-proxy-route --namespace boundary`.

## Controller-led registration

Follow [Controller-led registration](/boundary/docs/deploy/helm-chart/worker-examples#controller-led-registration) for the registration workflow and shared Secret-backed configuration.

### Plaintext token

Embedding a plaintext token in `worker.config` stores it in the Helm release and ConfigMap. Use the Secret-backed method in [Controller-led registration](/boundary/docs/deploy/helm-chart/worker-examples#controller-led-registration) instead.

### Token via extraEnv

Values supplied directly through `extraEnv` are stored in the Helm release. Use the Secret-backed method in [Controller-led registration](/boundary/docs/deploy/helm-chart/worker-examples#controller-led-registration), or use `extraEnv.valueFrom.secretKeyRef` when you need a custom environment variable mapping.

### Token from an OpenShift Secret

Follow [Controller-led registration](/boundary/docs/deploy/helm-chart/worker-examples#controller-led-registration) for the HCL, `secretRefs` values, validation behavior, and installation command. On OpenShift, create the Secret with `oc` instead of `kubectl`.

Generate the activation token as an admin, using the Boundary CLI against the controller:

```shell-session
$ boundary authenticate password \
  -addr="https://<controller-api-route-host>" \
  -auth-method-id=<ampw_...> \
  -login-name=<admin-username>

$ boundary workers create controller-led \
  -addr="https://<controller-api-route-host>" \
  -name="<worker-name>"
```

The `authenticate password` command prompts you for the admin password and stores the resulting session token in your local keyring; it does not print the token to the screen. The `workers create controller-led` command picks up that stored token automatically, so you do not need to pass a `-token` flag. It prints a `controller_generated_activation_token` value in its output — this is the token to store in the Secret below. Each token is single-use: generate a new one every time you install or reinstall a worker.

Create the Secret before installing the chart:

```shell-session
$ oc create secret generic boundary-worker-secrets \
  --namespace boundary \
  --from-literal=worker-controller-generated-activation-token='<activation-token>'
```

The key name (`worker-controller-generated-activation-token`) must match `secretRefs.keys.controllerGeneratedActivationToken`. Use any Secret management method that fits your workflow, and set `openshift.enabled=true` in addition to the shared values.

## Pull the worker image from the Red Hat registry

When `openshift.enabled=true` and `image.repository` is empty, the chart resolves the image from `registry.connect.redhat.com/hashicorp/boundary-enterprise` using the `<version>-ubi` tag convention (for example, `1.0.2-ent-ubi`). That registry requires authentication, so create a pull Secret and reference it in `imagePullSecrets`.

```shell-session
$ oc create secret docker-registry redhat-registry \
  --namespace boundary \
  --docker-server=registry.connect.redhat.com \
  --docker-username="<registry-service-account-username>" \
  --docker-password="<registry-service-account-token>"
```

Example values:

```yaml
imagePullSecrets:
  - name: redhat-registry
```

Alternatively, link the pull Secret to the ServiceAccount that runs the worker Deployment. The chart does not create a ServiceAccount; the worker uses the ServiceAccount named by `serviceAccount.name`, or the namespace's `default` ServiceAccount when `serviceAccount.name` is empty:

```shell-session
$ oc secrets link default redhat-registry --for=pull --namespace boundary
```

Set `image.repository` and `image.tag` explicitly if you mirror the image into an internal registry or an OpenShift ImageStream. An explicit value always takes precedence over the chart's OpenShift default.

## Enable session recording storage

Follow [Enable session recording storage](/boundary/docs/deploy/helm-chart/worker-examples#enable-session-recording-storage) for the shared persistence and HCL configuration.

<Note>

To create RDP (Remote Desktop Protocol) session recording exports, the worker must have an FFmpeg binary at version `5.1.0` or later installed. The `libsvtav1` codec must also be present. If your selected worker image does not include FFmpeg and that codec, build a custom image that adds them, then reference it in your values file.

Build the custom image from the Red Hat UBI (Universal Base Image) base so the SCC-compatible security context in `openshift.containerSecurityContext` continues to apply, and push it to a registry the cluster can reach, for example an internal mirror or an OpenShift ImageStream. Pass the custom image in your values file:

```yaml
image:
  repository: <your-registry>/boundary-worker
  tag: "1.0.2-ent-ffmpeg-ubi"
```

Add a pull Secret if the registry requires authentication, as described in [Pull the worker image from the Red Hat registry](#pull-the-worker-image-from-the-red-hat-registry).

</Note>

<Note>

OpenShift clusters commonly provide a default `StorageClass` for the recording PVC, for example `gp3-csi` on ROSA (Red Hat OpenShift Service on AWS), or an OpenShift Data Foundation class such as `ocs-storagecluster-ceph-rbd`. Leave `worker.persistence.recording.storageClass` empty to use the cluster default, or set it explicitly if your cluster requires one.

</Note>

Set `openshift.enabled=true` in addition to the shared values.

## Change service ports

The worker Deployment declares fixed proxy and operations container ports `9202` and `9203`. Keep the operations listener and `worker.service.ops.targetPort` on `9203` because health probes use the named operations container port. If you change the proxy listener and `worker.service.proxy.targetPort`, keep them aligned.

The Route targets the Service by its named port (`proxy`), so you do not need to update `openshift.route.proxy` when you change the port number. External clients continue to reach the Route on the router's standard `443` port.

## Troubleshooting

### Session recordings fail to export

If session recording exports fail, confirm that the selected worker image includes an FFmpeg binary at version `5.1.0` or later and the `libsvtav1` codec, as described in [Enable session recording storage](#enable-session-recording-storage). If it does not, build and reference a custom image that adds the binary and codec.

### TCP connections through the proxy Route fail or time out

If clients cannot establish sessions through the proxy Route, first confirm the worker pod is Ready and that the proxy Service's selector matches the worker pod labels; the proxy Service is always rendered by the chart, so the Route always has a backend. Confirm `worker.service.proxy.targetPort` matches the proxy listener's port in `worker.config`. The proxy Route's TLS termination is always `passthrough` and cannot be changed; `edge` or `reencrypt` termination is never applied to it. Check the Route status with `oc describe route boundary-worker-proxy-route --namespace boundary`.

### Pods fail to pull the worker image

If the worker pod reports `ImagePullBackOff`, the project cannot authenticate to `registry.connect.redhat.com`. Confirm that the pull Secret exists, that it is referenced in `imagePullSecrets` or linked to the ServiceAccount named by `serviceAccount.name` (or `default` when empty), and that the resolved tag exists in the Red Hat registry. Inspect the failure using `oc describe pod <pod-name> --namespace boundary`.
