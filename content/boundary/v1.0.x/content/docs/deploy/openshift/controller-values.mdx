# Controller values

You configure the Boundary controller Helm chart with Helm values and a Boundary HCL configuration. The chart is the source of truth for supported values.

The controller chart is the same chart you use on Kubernetes, with an additional `openshift` value group. Set `openshift.enabled=true` to render OpenShift `Route` resources, apply a security context that complies with OpenShift security context constraints (SCCs), and resolve the controller image from the Red Hat certified registry. When `openshift.enabled=false`, the chart ignores every value under `openshift` and behaves exactly as it does on Kubernetes.

## Boundary runtime configuration

The `controller.config` contains the Boundary controller HCL. The chart writes the HCL values into a ConfigMap and mounts it at `/etc/boundary/controller.hcl`.

The chart does not validate Boundary controller semantics beyond a few chart-level alignment checks. You are responsible for configuring valid listeners, database settings, cluster addresses, KMS (key management system) stanzas, rate limits, and event sinks. If you enable session recording, include a `bsr` KMS stanza in addition to the `root`, `recovery`, and `worker-auth` stanzas.

The chart validates the following:

- The `tls_cert_file` and `tls_key_file` settings on the API listener are aligned with `tls.mountPath` when `tls.api.disabled=false`, and on the ops listener when `tls.ops.disabled=false`.
- The `tls_disable` setting on each listener in `controller.config` agrees with `tls.api.disabled` and `tls.ops.disabled` respectively.
- AEAD (Authenticated Encryption with Associated Data) KMS keys are not referenced through `env://BOUNDARY_KMS_*` inside `kms` blocks.
- Required Secret keys exist when `secretRefs.validateExisting=true`.
- The `controller.replicas` value is `0` when `database.migrate.enabled=true`.
- The `database.migrate.enabled` value is `true` when `database.repair.version` is set.

## OpenShift infrastructure configuration

OpenShift-specific values control the Deployment, Services, Routes, ConfigMap, Job hooks, security contexts, ServiceAccount, and scheduling options. These values do not replace or generate the Boundary runtime HCL.

For example, if you change `controller.service.api.targetPort` to `9220`, you must also update the API listener port in the `controller.config`.

Refer to the [configuration alignment checklist](#configuration-alignment-checklist) before you finalize any changes.

The following sections describe the available Helm values grouped by function. Each table lists the key, default value, and a description.

## Naming and namespace values

| Key | Default | Description |
| --- | --- | --- |
| `nameOverride` | `""` | Overrides the chart-generated resource base name |
| `fullnameOverride` | `""` | Fully overrides the chart-generated resource name |
| `namespace` | `""` | Overrides the namespace the chart renders namespaced resources into. An empty value uses the Helm release namespace. |

On OpenShift, the namespace maps to an OpenShift project. The project must exist, or you must install the release with `--create-namespace`.

Resource names also determine the generated Route hostnames. When `openshift.route.*.host` is empty, OpenShift builds the hostname from the Route name, the project name, and the cluster ingress domain. Keep the release name, `nameOverride`, or `fullnameOverride` short so that the generated hostname stays within DNS label limits.

## Image values

| Key | Default | Description |
| --- | --- | --- |
| `image.repository` | `""` | Controller image repository. When empty and `openshift.enabled=true`, the chart uses `registry.connect.redhat.com/hashicorp/boundary-enterprise`. When empty and `openshift.enabled=false`, the chart uses `hashicorp/boundary-enterprise`. |
| `image.tag` | `""` | Controller image tag. When empty and `openshift.enabled=true`, the chart appends `-ubi` to `Chart.appVersion`, currently `1.0.2-ent-ubi`. When empty and `openshift.enabled=false`, the chart uses `Chart.appVersion`, currently `1.0.2-ent`. |
| `image.pullPolicy` | `IfNotPresent` | Image pull policy |
| `imagePullSecrets` | `[]` | Optional image pull secrets for private registries |

The Red Hat certified registry uses the `<version>-ubi` tag convention, so the chart derives the tag automatically when you do not set one. An explicit `image.repository` or `image.tag` always takes precedence. Because `registry.connect.redhat.com` requires authentication, create a pull Secret and reference it in `imagePullSecrets`, or link the Secret to the ServiceAccount used by the controller.

## TLS values

The chart uses independent TLS toggles for the API and ops listeners, so you can run mixed configurations (for example, API over HTTPS with ops over plain HTTP).

| Key | Default | Description |
| --- | --- | --- |
| `tls.api.disabled` | `false` | Disables TLS on the API listener when `true`. Default is `false`, meaning TLS is enabled. |
| `tls.ops.disabled` | `false` | Disables TLS on the ops listener when `true`. Default is `false`, meaning TLS is enabled. |
| `tls.secretName` | `boundary-controller-tls` | Name of the Kubernetes TLS Secret mounted when either listener has TLS enabled |
| `tls.mountPath` | `/etc/boundary/tls` | Container path where the TLS Secret is mounted |

When you enable TLS on a listener, keep that listener's `tls_cert_file` and `tls_key_file` paths in `controller.config` aligned with `tls.mountPath`. The chart validates that each listener's `tls_disable` setting in `controller.config` agrees with `tls.api.disabled`/`tls.ops.disabled`, and fails the render on a mismatch. If a probe scheme is not explicitly set, the chart derives it from `tls.ops.disabled`.

Keep `tls.api.disabled=false` when you expose the API listener through a Route that uses `reencrypt` termination, and keep `tls.ops.disabled=false` when you do the same for the ops listener. The listener must serve HTTPS so that the OpenShift router can re-encrypt traffic to the pods.

## Secret reference values

| Key | Default | Description |
| --- | --- | --- |
| `secretRefs.secretName` | `boundary-controller-secrets` | Name of an existing OpenShift Secret that contains the values referenced by `secretRefs.keys` |
| `secretRefs.validateExisting` | `false` | When true, validates the referenced Secret and required keys during rendering |
| `secretRefs.keys.databaseUrl` | `database-url` | Key in the Secret used for `env://BOUNDARY_PG_URL` in `controller.config`. Set to the key name used in your Secret. |
| `secretRefs.keys.migrationUrl` | `migration-url` | Key in the Secret used for `env://BOUNDARY_PG_MIGRATION_URL` in `controller.config`. Required only when referenced in `controller.config`. Set to the key name used in your Secret. |
| `secretRefs.keys.license` | `license` | Key in the Secret used for `env://BOUNDARY_LICENSE` in `controller.config`. Set to the key name used in your Secret. |
| `secretRefs.keys.adminUsername` | `admin-username` | Key in the Secret whose value is used by the bootstrap admin Job. Set to the key name used in your Secret. |
| `secretRefs.keys.adminPassword` | `admin-password` | Key in the Secret whose value is used by the bootstrap admin Job. Set to the key name used in your Secret. |

The `secretRefs.keys` values are the key names inside your Secret. They are not fixed by the chart. Set each to match the actual key name you used when creating the Secret. For example, if you created the Secret with `--from-literal=pg-url=...`, set `secretRefs.keys.databaseUrl: "pg-url"`.

## Controller runtime values

| Key | Default | Description |
| --- | --- | --- |
| `controller.replicas` | `2` | Number of controller replicas in the Deployment |
| `controller.rollingUpdate.maxUnavailable` | `1` | Maximum unavailable pods during a rolling update |
| `controller.rollingUpdate.maxSurge` | `1` | Maximum extra pods during a rolling update |
| `controller.config` | Embedded sample HCL | Boundary controller HCL stored in a ConfigMap and mounted into the controller container and hook Jobs |

The default `controller.config` includes `disable_mlock = true`. The chart's default security model drops all Linux capabilities and disallows privilege escalation. We do not recommend changing this value, because OpenShift SCCs do not grant the `IPC_LOCK` capability that memory locking requires.

## Listener Service values

The chart creates separate Services for the API, cluster, and ops listeners.

On OpenShift, set all three Service types to `ClusterIP` and expose the listeners you need through Routes. `LoadBalancer` Services depend on a cloud provider integration that is not available in every OpenShift environment.

### API Service values

| Key | Default | Description |
| --- | --- | --- |
| `controller.service.api.type` | `LoadBalancer` | Service type for Boundary API traffic. Set to `ClusterIP` on OpenShift and expose the API through a Route. |
| `controller.service.api.port` | `9200` | Service port for API traffic |
| `controller.service.api.targetPort` | `9200` | Container port targeted by the API Service. Must match the API listener in `controller.config`. |
| `controller.service.api.annotations` | `{}` | Annotations added to the API Service |

### Cluster Service values

| Key | Default | Description |
| --- | --- | --- |
| `controller.service.cluster.type` | `ClusterIP` | Service type for worker registration and controller cluster traffic |
| `controller.service.cluster.port` | `9201` | Service port for cluster traffic |
| `controller.service.cluster.targetPort` | `9201` | Container port targeted by the cluster Service. Must match the cluster listener in `controller.config`. |
| `controller.service.cluster.annotations` | `{}` | Annotations added to the cluster Service |

### Ops Service values

| Key | Default | Description |
| --- | --- | --- |
| `controller.service.ops.type` | `ClusterIP` | Service type for health and metrics traffic |
| `controller.service.ops.port` | `9203` | Service port for the operations endpoint |
| `controller.service.ops.targetPort` | `9203` | Container port targeted by the ops Service. Must match the ops listener in `controller.config` |
| `controller.service.ops.annotations` | `{}` | Annotations added to the ops Service |

Keep the ops Service internal unless a trusted monitoring path requires a different exposure model.

## OpenShift values

The `openshift` values group controls OpenShift-only behavior. The chart evaluates these values only when `openshift.enabled=true`.

| Key | Default | Description |
| --- | --- | --- |
| `openshift.enabled` | `false` | Enables OpenShift mode. When true, the chart renders Routes, applies the OpenShift security contexts, and resolves the image from the Red Hat certified registry. |

### OpenShift security context values

When `openshift.enabled=true`, the chart replaces `podSecurityContext` and `containerSecurityContext` with the values under `openshift` for the controller Deployment and for every hook Job. These values intentionally omit `runAsUser`, `runAsGroup`, and `fsGroup` so that the OpenShift SCC can assign a UID and GID from the project's allocated range.

| Key | Default |
| --- | --- |
| `openshift.podSecurityContext.runAsNonRoot` | `true` |
| `openshift.podSecurityContext.seccompProfile.type` | `RuntimeDefault` |
| `openshift.containerSecurityContext.runAsNonRoot` | `true` |
| `openshift.containerSecurityContext.allowPrivilegeEscalation` | `false` |
| `openshift.containerSecurityContext.readOnlyRootFilesystem` | `true` |
| `openshift.containerSecurityContext.capabilities.drop` | `ALL` |
| `openshift.containerSecurityContext.seccompProfile.type` | `RuntimeDefault` |

These defaults are compatible with the `restricted-v2` SCC, so the controller does not require a custom SCC or elevated privileges. Do not add `runAsUser`, `runAsGroup`, or `fsGroup` unless the ServiceAccount is bound to an SCC that permits the UID and GID you specify. Otherwise, the pod fails admission.

### API Route values

| Key | Default | Description |
| --- | --- | --- |
| `openshift.route.api.enabled` | `true` | Creates a Route for the API Service |
| `openshift.route.api.host` | `""` | Hostname for the API Route. An empty value lets OpenShift generate a hostname from the Route name, namespace, and cluster ingress domain. |
| `openshift.route.api.tls.termination` | `reencrypt` | TLS termination mode for the API Route. Supported values are `edge`, `reencrypt`, and `passthrough`. |
| `openshift.route.api.tls.insecureEdgeTerminationPolicy` | `Redirect` | Handling for plain HTTP requests. Supported values are `Allow`, `Redirect`, and `None`. |
| `openshift.route.api.tls.destinationCACertificate` | `""` | CA certificate that issued the controller TLS certificate. The router uses it to verify the backend connection. |
| `openshift.route.api.annotations` | `{}` | Annotations added to the API Route, such as router timeout or balancing annotations |

The chart renders `destinationCACertificate` only when `tls.api.disabled=false`, `openshift.route.api.tls.termination` is `reencrypt`, and the value is not empty. If you use `reencrypt` termination without a destination CA certificate, the router cannot validate the backend certificate and the Route fails to serve traffic.

### Cluster Route values

| Key | Default | Description |
| --- | --- | --- |
| `openshift.route.cluster.enabled` | `true` | Creates a Route for the cluster Service. Enable it only when workers run outside the OpenShift cluster. |
| `openshift.route.cluster.host` | `""` | Hostname for the cluster Route. An empty value lets OpenShift generate a hostname. |
| `openshift.route.cluster.annotations` | `{}` | Annotations added to the cluster Route |

The cluster Route always uses `passthrough` termination, and the chart does not expose a `tls` value group for it. The cluster listener carries Boundary's own mTLS over raw TCP, so `edge` or `reencrypt` termination breaks worker-to-controller communication.

A cluster Route terminates on the router's HTTPS port. When workers connect through the Route, set `public_cluster_addr` in `controller.config` to the Route hostname and port `443`, not to the cluster Service name and port `9201`.

### Ops Route values

| Key | Default | Description |
| --- | --- | --- |
| `openshift.route.ops.enabled` | `true` | Creates a Route for the ops Service. Disable it unless a trusted external monitoring path requires it. |
| `openshift.route.ops.host` | `""` | Hostname for the ops Route. An empty value lets OpenShift generate a hostname. |
| `openshift.route.ops.tls.termination` | `reencrypt` | TLS termination mode for the ops Route |
| `openshift.route.ops.tls.insecureEdgeTerminationPolicy` | `Redirect` | Handling for plain HTTP requests |
| `openshift.route.ops.tls.destinationCACertificate` | `""` | CA certificate that issued the controller TLS certificate |
| `openshift.route.ops.annotations` | `{}` | Annotations added to the ops Route |

The ops Route exposes the health and metrics endpoints outside the cluster. Leave `openshift.route.ops.enabled=false` unless you need external monitoring access, and protect the Route when you enable it.

The chart names Routes after the controller Service, using the `-api-route`, `-cluster-route`, and `-ops-route` suffixes. For example, `boundary-controller-api-route`.

## Probe values

The chart always adds liveness and readiness probes targeting the ops container port. If a scheme is not provided, the chart derives it from `tls.ops.disabled`: `HTTPS` when `false`, `HTTP` when `true`. Because the chart validates that `tls.ops.disabled` and the ops listener's `tls_disable` setting in `controller.config` agree, the derived scheme also matches the ops listener's actual TLS behavior.

| Key | Default | Description |
| --- | --- | --- |
| `controller.livenessProbe.scheme` | `""` | Probe scheme for `/health`. If not provided, derived from `tls.ops.disabled`: `HTTPS` when `false`, `HTTP` when `true`. Override if needed. |
| `controller.livenessProbe.initialDelaySeconds` | `60` | Initial liveness probe delay |
| `controller.livenessProbe.periodSeconds` | `10` | Liveness probe period |
| `controller.livenessProbe.failureThreshold` | `3` | Liveness probe failure threshold |
| `controller.livenessProbe.timeoutSeconds` | `5` | Liveness probe timeout |
| `controller.readinessProbe.scheme` | `""` | Readiness probe scheme for `/health`. If not provided, derived from `tls.ops.disabled`: `HTTPS` when `false`, `HTTP` when `true`. Override if needed. |
| `controller.readinessProbe.initialDelaySeconds` | `15` | Initial readiness probe delay |
| `controller.readinessProbe.periodSeconds` | `10` | Readiness probe period |
| `controller.readinessProbe.failureThreshold` | `3` | Readiness probe failure threshold |
| `controller.readinessProbe.timeoutSeconds` | `5` | Readiness probe timeout |

Probes connect to the ops container port directly. They do not pass through the Route, so the Route TLS termination mode does not affect the probe scheme.

When TLS is enabled, the controller certificate must include the `DNS:<fullname>-api` SAN (Subject Alternative Name), for example `boundary-controller-api`. ## Configuration alignment checklist

Before installing or upgrading a controller, confirm that:

- The `openshift.enabled` value is `true` so that the chart renders Routes and applies the OpenShift security contexts.
- The API listener port in `controller.config` matches `controller.service.api.targetPort`.
- The cluster listener port in `controller.config` matches `controller.service.cluster.targetPort`.
- The ops listener port in `controller.config` matches `controller.service.ops.targetPort`.
- The Service types are `ClusterIP` and every listener you expose externally has a corresponding Route.
- The `public_cluster_addr` setting matches the endpoint workers can actually reach. Use the cluster Route hostname with port `443` for workers outside the cluster, or the cluster Service address with port `9201` for workers inside the cluster.
- The `tls.api.disabled` value is `false` when the API Route uses `reencrypt` termination, and `tls.ops.disabled` is `false` when the ops Route uses `reencrypt` termination; set `destinationCACertificate` for those Routes.
- The `tls_cert_file` and `tls_key_file` settings match `tls.mountPath` on each listener that has TLS enabled.
- Probe schemes are derived from `tls.ops.disabled` when not provided. Override only if the derived scheme does not match your listener configuration.
- The referenced Secret contains every key required by the current `controller.config` and bootstrap settings.
- The `terminationGracePeriodSeconds` setting exceeds `graceful_shutdown_wait_duration` in the controller HCL.
- The security context values do not pin a UID or GID that the project's SCC does not allow.

## Troubleshooting

### Controller pods fail readiness or liveness probes

If controller pods fail their readiness or liveness probes after you change TLS settings, check whether `controller.livenessProbe.scheme` or `controller.readinessProbe.scheme` matches `tls.ops.disabled` and the `tls_disable` setting on the ops listener in `controller.config` (the chart requires these to agree). When a probe scheme is not explicitly set, the chart derives it from `tls.ops.disabled` (`HTTPS` when `false`, `HTTP` when `true`). If you override the probe scheme manually, make sure it stays aligned with the ops listener whenever you change `tls.ops.disabled`.

### Controller pods fail admission

If the Deployment reports an SCC error such as `unable to validate against any security context constraint`, the pod requests something the project's SCC does not allow. Confirm that `openshift.enabled=true`, that you have not added `runAsUser`, `runAsGroup`, or `fsGroup` to the OpenShift security contexts, and that the ServiceAccount in `serviceAccount.name` is bound to an SCC that admits the pod.

### Routes return a TLS error

If the API or ops Route returns a TLS error, the router cannot verify the backend certificate. Confirm that `tls.api.disabled=false` (for the API Route) or `tls.ops.disabled=false` (for the ops Route), that the corresponding listener serves HTTPS, and that `openshift.route.api.tls.destinationCACertificate` and `openshift.route.ops.tls.destinationCACertificate` contain the CA certificate that issued the controller TLS certificate. Inspect the rendered Route using `oc describe route boundary-controller-api-route --namespace boundary`.

### Workers cannot register

If workers outside the cluster cannot register, confirm that `openshift.route.cluster.enabled=true` and that `public_cluster_addr` in `controller.config` points to the cluster Route hostname and port `443`. The cluster Route uses `passthrough` termination, so the router forwards Boundary's mTLS connection unchanged.
