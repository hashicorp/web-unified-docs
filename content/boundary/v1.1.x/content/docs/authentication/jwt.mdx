# Configure JWT authentication

Boundary can authenticate automated workloads using signed JSON Web Tokens (JWTs) with the JWT auth method. Instead of a username and password, a workload presents a signed JWT, and Boundary exchanges it for a Boundary auth token. The JWT auth method is useful for machine-to-machine authentication, such as agents or pipelines that need to access infrastructure targets.

@include 'alerts/beta.mdx'

The JWT auth method validates tokens against a JSON Web Key Set (JWKS) that you provide when you create the auth method. Boundary checks the token's issuer, audience, signing algorithm, and key ID against the auth method's configuration before issuing a Boundary auth token.

The JWT auth method does not support managed groups.

## Prerequisites

- Administrator access to Boundary.
- A signing key pair. The private key signs JWTs presented during authentication. The public key is included in the JWKS you provide to Boundary.
- The following values must match in both the JWT auth method configuration and any JWT presented for authentication:
  - **Issuer** (`iss` claim): The expected issuer URL, for example `https://my-identity-service.example.com`.
  - **Audience** (`aud` claim): The expected audience, for example `boundary`.
  - **Signing algorithm**: The algorithm used to sign the JWT, for example `RS256`.

## Create a JWT auth method

Run the following command to create a JWT auth method:

```shell-session
$ boundary auth-methods create jwt \
  -scope-id global \
  -name "my-jwt-auth-method" \
  -issuer "https://my-identity-service.example.com" \
  -jwks-json "file:///path/to/jwks.json" \
  -allowed-audience "boundary" \
  -signing-algorithm RS256
```

The `-scope-id` determines which scope contains the auth method. Set it to `global` or to an org scope ID. When you omit `-scope-id`, Boundary uses the `BOUNDARY_SCOPE_ID` environment variable, or defaults to `global`.

The `-jwks-json` flag accepts a path to a local JWKS file using the `file://` scheme, or an inline JSON string. The JWKS must contain the public key or keys that correspond to the private keys used to sign JWTs.

The command returns an auth method ID beginning with `amjwt_`. Save this value. You need it for subsequent commands.

Refer to the [auth-methods create jwt](/boundary/docs/commands/auth-methods/create#jwt) command documentation for the full list of options.

## Activate the JWT auth method

Boundary creates JWT auth methods in an `inactive` state. You must activate the auth method before workloads can authenticate with it.

```shell-session
$ boundary auth-methods change-state jwt \
  -id $JWT_AUTH_METHOD_ID \
  -state active-public
```

Use `active-public` to make the auth method visible to unauthenticated users, or `active-private` to let workloads authenticate without listing the method on the login page.

### Set the auth method as primary

Each scope has one primary auth method. When a workload authenticates with a JWT auth method for the first time, Boundary's behavior depends on whether the auth method is the scope's primary:

- **Primary auth method:** Boundary automatically creates a user (`u_...`) in the scope and links the JWT account (`acctjwt_...`) to that user. You do not need to configure anything manually.
- **Not the primary auth method:** Boundary creates the JWT account on first login, but does not create or link a user. The login fails until an administrator manually links the account to a user. Refer to [Manage users and groups](/boundary/docs/rbac/users/manage-users-groups) for instructions.

To set the JWT auth method as the primary auth method for a scope:

```shell-session
$ boundary scopes update \
  -id $SCOPE_ID \
  -primary-auth-method-id $JWT_AUTH_METHOD_ID
```

## Authenticate with the JWT auth method

After the auth method is active, a workload can exchange a signed JWT for a Boundary auth token. Choose one of the following methods to authenticate:

- [Authenticate with the CLI](#authenticate-with-the-cli)
- [Authenticate with the HTTP API](#authenticate-with-the-http-api)

### Authenticate with the CLI

Use the `-jwt-token` flag to pass the JWT using an environment variable or file reference. Do not pass the raw JWT as a flag value on the command line.

<Tabs>
<Tab heading="Environment variable">

Run the following command to authenticate using a JWT stored in an environment variable:

```shell-session
$ boundary authenticate jwt \
  -auth-method-id $JWT_AUTH_METHOD_ID \
  -jwt-token env://WORKLOAD_JWT
```

When the JWT auth method is the scope's primary auth method, you can omit the `-auth-method-id` flag and use the `BOUNDARY_AUTHENTICATE_JWT_TOKEN` environment variable instead:

```shell-session
$ BOUNDARY_AUTHENTICATE_JWT_TOKEN=$WORKLOAD_JWT \
  boundary authenticate -scope-id global
```

</Tab>
<Tab heading="File">

Run the following command to authenticate using a JWT stored in a file:

```shell-session
$ boundary authenticate jwt \
  -auth-method-id $JWT_AUTH_METHOD_ID \
  -jwt-token "file:///path/to/jwt.txt"
```

</Tab>
</Tabs>

A successful login returns a Boundary auth token in the response under `.item.attributes.token`. The resulting account ID begins with `acctjwt_`.

### Authenticate with the HTTP API

Send the signed JWT in the request body. This request does not require an `Authorization` header.

```shell-session
$ curl -sS -X POST \
  "${BOUNDARY_ADDR}/v1/auth-methods/${JWT_AUTH_METHOD_ID}:authenticate" \
  -H 'Content-Type: application/json' \
  -d '{"command":"login","attributes":{"jwt":"'"$WORKLOAD_JWT"'"}}'
```

The request body has the following form:

```json
{
  "command": "login",
  "attributes": {
    "jwt": "<signed JWT>"
  }
}
```

A successful response returns the Boundary auth token under `.attributes.token`. Use this token, not the original signed JWT, as the `Authorization: Bearer` token for subsequent Boundary API requests.

## Assign roles to JWT users

After a workload authenticates, use its Boundary user ID to assign roles and grants. The user ID begins with `u_` and appears in the login response under `.item.attributes.user_id` (CLI) or `.attributes.user_id` (API).

```shell-session
$ boundary roles add-principals \
  -id $ROLE_ID \
  -principal $JWT_USER_ID
```

Refer to [Manage access with roles](/boundary/docs/rbac/manage-roles) for instructions on creating roles and assigning grants.
