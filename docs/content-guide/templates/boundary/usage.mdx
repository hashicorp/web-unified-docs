# Configure the thing

One or two sentences naming what the page covers and why a reader would need it.

## Requirements

Describe the systems, software, permissions, and conditions a reader needs.
Boundary uses **Requirements** for conditions that must already be true and
**Prerequisites** for steps the reader must complete first.

- `<A required condition.>`
- `<Another required condition.>`

### Grouped requirement

Group related requirements under H3 headings when the list is long enough to
need them.

## First aspect of the feature

Boundary usage pages are organized by the aspects of the thing being configured
rather than by ordered steps. Give each aspect its own H2, named for the aspect
rather than for an action.

Describe how the aspect behaves and what the reader sets to change it. Link the
[reference documentation](link) for any parameter you name.

## Second aspect of the feature

Where the reader configures the same thing through more than one interface, use
tabs. Boundary's established tab groups are `cli`, `ui`, `admin`, and
`terraform`.

<Tabs>

<Tab heading="CLI" group="cli">

```shell-session
$ boundary <command> <argument>
```

</Tab>

<Tab heading="Terraform" group="terraform">

```hcl
resource "boundary_resource" "example" {
  name = "example"
}
```

</Tab>

</Tabs>

## Example configuration

Show a complete, realistic configuration rather than a fragment:

```hcl
<complete configuration>
```

workflow. When a page uses both blocks, Next steps comes last:
