# Integrate high-value content from Adam's Confluence dump into docs/content-guide

## Context

`/Users/aimeeu/Dev/adam/bob-skill-wip/content-types/` is a reorganized export of a
HashiCorp technical writer's (Adam Trujillo's) Confluence space defining a much richer
content-type taxonomy than this repo's `docs/content-guide/` currently has. Two full
exploration passes (one per side) confirmed: our system has 5 content types
(how-to/concept/overview/reference/troubleshooting), each with a template file + checklist,
consumed by `.bob/skills/create-page` and `.bob/skills/docs-review`. Adam's system has 8
types, each with a 3-tier rationale/design/template structure, and is considerably more
detailed — especially around reference content, metadata/SEO guidance, and visual aids.

The goal is not to import everything (the source is roughly 3-5x our depth and some of it
either duplicates what we already have better, like alerts, or conflicts with stated
direction, like manually-authored CLI reference). The goal is to pull the specific,
high-value, non-duplicative material — decided with the user via direct questions — into
our existing structure without disrupting the `create-page`/`docs-review` skills that
depend on it.

Note: the user has since renamed Adam's `how-to-guides/usage/` directory to
`how-to-guides/how-to/` and updated most of that directory's terminology from "Usage" to
"How-to," aligning the source material with this repo's naming. This plan already treated
Adam's Usage type as a direct source for our existing How-to type throughout (never proposed
a separate "Usage" type), so no plan changes are required by the rename — it's a confirming
change, not a conflicting one. (A few incidental "Usage" mentions remain in that directory's
page titles/links on the source side — not something this plan needs to fix, since it's
Adam's dump, not part of what gets integrated verbatim.)

**Decisions made** (via user Q&A):
- Reference stays a single content type (no split into structured/tabular/cli/irregular) —
  enrich `reference.md`'s template with Adam's structured-configuration-reference material,
  since that's the most detailed and our current template has zero example content.
- Skip importing Adam's CLI reference design — it conflicts with `content-types.md`'s
  existing statement that CLI/API reference should be autogenerated, not hand-authored.
- Add "What is" as a 6th content type — it's a genuinely distinct job (top-of-funnel
  product-landing page) from Overview (mid-funnel navigation hub), and Adam already has a
  complete template for it.
- Cherry-pick specific valuable rules into existing files rather than building a new shared
  "block library" file — smaller, lower-risk, no new architecture for the skills to learn.

Confirmed real, non-duplicative examples already exist in `content/` for a "What is"
reference doc: `content/nomad/v2.0.x/content/docs/what-is-nomad.mdx` matches Adam's
template pattern (What is X? → Key features) well and Nomad v2.0.x is already used
elsewhere in `docs-review` as a format-reference source, so it's consistent with existing
convention.

## Approach

### A. Add "What is" as a 6th content type

- **New file** `docs/content-guide/templates/what-is.md`: template (adapted from Adam's
  `explanation/what-is/index.md` + `template.md`) with sections `# What is {Product}?` →
  `## How does {Product} work?` → `## Why {Product}?` → optional paid-offerings section →
  `## Community`. Checklist derived from Adam's rationale: SEO-driven H1 ("question title
  that mimics what users may type"), lead-with-goals heading style (example from source:
  "Standardize configurations" instead of "Custom modules"), industry-vocabulary/no-hyperbole
  tone, mandatory `> **Hands-on:**` tutorial callout matching our existing blockquote
  convention (`docs/style-guide/appendix.md`'s "Links to tutorials" pattern — reuse that
  exact syntax, not Adam's slightly different "**Tutorial**"/"**Hands On:**" variants).
- **`docs/content-guide/content-types.md`**: add a "What is" bullet next to Overview/Concept
  in the Explanation section, with a one-line distinction from Overview (Overview = mid-funnel
  hub between usage/reference/concept pages; What-is = top-of-funnel "why should I care about
  this product" landing page). Add to the Page templates list.
- **`.bob/skills/create-page/SKILL.md`**: add `what-is` to the content-type enum; this
  reverts the "five known values" wording back to "six" in all four spots that were changed
  when release-notes was removed (Invocation section, Step -1, Step 0 ×2).
- **`.bob/skills/docs-review/SKILL.md`**: add `docs/content-guide/templates/what-is.md` to
  Step 1's reading list (six templates again); add a "What is" row to Step 2's doc-type
  table; add `content/nomad/v2.0.x/content/docs/what-is-nomad.mdx` as the reference example
  in Step 5's table; update Step 3's "all six" wording.
- **`.bob/skills/README.md`**: add `what-is` to the content-type list.

### B. Enrich the Reference template with structured-configuration-reference material

Rewrite `docs/content-guide/templates/reference.md`'s Template section (currently just "find
an existing page and use that as a template" — no example at all) using Adam's
structured-configuration-reference template as the primary worked example:

- `## Configuration model` — nested-list table of contents (name/data type/default/required/
  enterprise flag), linking into Specification.
- `## Complete configuration` — single fully-configured, copy-pasteable code block, comments
  only, explicitly "demonstrative, not a real-world scenario."
- `## Specification` — H3 per element in code font; the dot-notation heading convention
  (`.` for hierarchy, `[]` for HCL lists, `{}` for HCL maps — worked example:
  `Failover{}.Targets[].Service`) and the punctuation-becomes-dash anchor rule; `#### Values`
  subsection per element (Default / required-if-applicable / Data type, spelled out as
  "Boolean" not "bool", "list"/"map" not "tuple"/"object").
- `## Examples` — H3 per use case, each prefaced with a descriptive sentence.
- Keep a short paragraph distinguishing when to use this nested pattern (hierarchical/
  structured config) versus a flat reference table (non-hierarchical items like metrics or
  flags) — borrowing Adam's Tabular Reference's one key distinguishing rule without
  importing it as a separate type.
- Add "Reference is canonical" as guidance prose: when a config item changes, update the
  reference page first; other content types should link to it rather than re-describing it.
- Extend the checklist with items for: Configuration model/Complete configuration/
  Specification/Examples block presence (where applicable to structured content), and the
  dot-notation heading rule.

### C. Enrich the How-to template

Small, targeted additions to `docs/content-guide/templates/how-to.md`:

- Add the **Requirements vs. Prerequisites** distinction to the Requirements section
  guidance: requirements are conditions that must hold to proceed; prerequisites are steps
  the reader must complete first. Currently our template doesn't distinguish these.
- Add a checklist item enforcing the boundary Adam's Examples appendix states: how-to pages
  use inline command/API examples to support a step, but full standalone example
  configurations belong on the matching reference page, not duplicated here.

### D. Metadata / description guidance

- Add one Universal checklist item to `docs/content-guide/content-types.md`: `description`
  frontmatter should be approximately 130-160 characters (distinct from the on-page
  description paragraph's ~60-word target, which templates already imply). This directly
  sharpens `docs-review`'s existing but vague SEO check ("description frontmatter is missing
  or generic").
- Tighten each template's frontmatter `description` example comment to match Adam's
  per-type phrasing pattern where ours is currently vague (for example, how-to's becomes
  closer to "{Feature} to {things you can do}. Use {feature} to {goal}."; what-is's becomes
  "{Feature or thing} is {what it is} that you can use to {verbs}. Learn how {feature} can
  help you {goals}.").

### E. Visual aids additions — `ai-checklist.md` only

**Constraint: do not modify any file under `docs/style-guide/` other than `ai-checklist.md`.**
This changes how this section lands: rather than adding new sections to
`docs/style-guide/appendix.md` and `general/screenshots.md` (their natural home under normal
circumstances) with `ai-checklist.md` entries linking out to them via a `detail:` field (the
pattern every other tagged entry uses), these new rules get added to `ai-checklist.md` as
fully self-contained entries — full rule text inline, no `detail:` link, since there's no
detail page to point to. `docs-review` still picks them up automatically either way, since it
reads `ai-checklist.md` generically; only the "human-readable detail page" half of the usual
pattern is unavailable here.

Adam's alert guidance is skipped regardless (ours is already more detailed than his). His
diagrams and icon/symbol guidance is genuinely new material with no existing home:

- New `ai-checklist.md` entry: **introduce diagrams in prose, don't build legends/explainer
  text into the image itself** — better maintainability, portability, and accessibility.
  `priority: standard`, `auto-fixable: no` (judgment call).
- New `ai-checklist.md` entry: **introduce a screenshot or diagram in prose immediately
  before it; never use directional language like "above" or "the following image"** — this
  echoes the reasoning already in `top-12.md`'s "Organize content so it flows in a single
  direction" rule (already present in `ai-checklist.md` as "Organize content so that it
  flows in a single direction from beginning to end"), so phrase this as a visual-aid-specific
  extension of that existing entry rather than a duplicate. `priority: standard`,
  `auto-fixable: no`.
- New `ai-checklist.md` entry: **one image per step or concept — never a single multi-step
  composite screenshot, never a series of screenshots stacked one after another.**
  `priority: standard`, `auto-fixable: no`.
- New `ai-checklist.md` entry: **describe UI icons and symbols in words instead of trying to
  reproduce them** (source example: call it "the refresh button," not the icon glyph).
  `priority: standard`, `auto-fixable: no`.

The broken self-reference bug in `general/screenshots.md` (`Refer to [Guidelines for alert
boxes]...` pointing screenshot readers to alert guidance) is now out of scope — it lives in a
file this plan can't touch. Noting it here so it isn't silently forgotten; worth a separate,
narrower follow-up if the constraint is lifted or a maintainer wants to fix it directly.
